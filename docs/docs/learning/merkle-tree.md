# Merkle-дерево на векторах `parent`, `sibling`, `value`

Учебный материал: разбор конкретного алгоритма на дереве, устроенном так же, как дерево фконтейнера farc, — не описание реализованной или планируемой функции самого farc.

## 1. Назначение документа

Aaron W. Hsu в докладах (`../archive/08-array-trees.md` §17.3) отмечает, что деревья на базе массивов особенно естественно обрабатывать **начиная с листьев**: пока структура (`parent`/`sibling`) статична, вычисление, зависящее от поддерева, всегда можно организовать снизу вверх без рекурсии и без явного стека вызовов. Этот документ разбирает конкретный пример такого вычисления — **Merkle-дерево** (дерево хешей: хеш узла зависит от его `value` и от хешей всех его детей) — и отвечает на вопрос, который для boolean-маски (`../archive/08-array-trees.md` §5.2) не возникал: **как именно результат вычисления нескольких детей передать одному родителю**, если результат — не бит, а полноценное значение (хеш), и порядок детей значим.

Документ **не описывает**:

- Формат элемента дерева на диске (`../archive/05-data-format.md`) — используется как есть, как пример готового представления дерева.
- Механизм заполнения дерева потребителем (`../archive/09-fcontainer-write-path.md`).
- Является ли Merkle-хеширование частью формата farc — это общий алгоритм на дереве такой же формы, а не описание реализованной или планируемой функции.

Нотация — та же, что в `../archive/08-array-trees.md` §1: `=` — присваивание, `==`/`!=` — сравнение, `or`/`and` — логика; это не APL и не подразумевает цикл там, где написано выражение над вектором целиком.

## 2. Постановка задачи

Дано дерево из `n` узлов в представлении farc (`../archive/05-data-format.md` §3): `parent[i]`, `sibling[i]`, `value[i]` (плюс `type`/`size`, которые здесь не важны — считаем `value[i]` произвольной байтовой строкой, включая пустую для узлов-контейнеров). Инвариант: `parent[i] <= i`, `sibling[i] <= i` (родитель и левый сосед физически созданы раньше).

Нужно вычислить вектор `hash[i]` такой, что:

```
hash[i] = H(0x00 ∥ value[i])                                        если i — лист
hash[i] = H(0x01 ∥ value[i] ∥ hash[c_0] ∥ hash[c_1] ∥ ... ∥ hash[c_{k-1}])   если i — внутренний узел,
                                                                       c_0 .. c_{k-1} — дети i, слева направо
```

`H` — любая криптографическая хеш-функция (SHA-256 и т.п.), `∥` — конкатенация байтов. Префиксы `0x00`/`0x01` перед листовым и внутренним содержимым — стандартная защита от **second-preimage attack** (RFC 6962, Certificate Transparency): без разделения типов узел-лист с содержимым `hash[a] ∥ hash[b]` было бы неотличим по хешу от внутреннего узла с детьми `a`, `b`. Здесь и далее это боковая деталь — суть задачи не в выборе `H`, а в том, **как собрать входы `H` для внутреннего узла**.

Два свойства усложняют задачу относительно propagation маски (`../archive/08-array-trees.md` §5.2):

1. **Порядок детей значим.** `H(a∥b) != H(b∥a)` почти всегда — в отличие от `or`/`and`/`+`, конкатенация не коммутативна. Значит, нельзя просто писать в `hash[parent[i]]` результат для каждого ребёнка по очереди, как в `mask[parent[i]] = mask[parent[i]] or mask[i]` — нужно знать **позицию** ребёнка среди братьев.
2. **Арность произвольна.** У узла может быть 0, 1 или сотни детей — `hash[parent[i]]` не одна ячейка-аккумулятор, а требует буфера переменной длины.

## 3. Как результат ребёнка передаётся родителю: precomputed slot, а не merge

Ключевая идея: **место, куда ребёнок кладёт свой хеш, вычисляется заранее и не зависит от значений** — только от структуры дерева (`parent`, `sibling`). Это ровно то же разделение, что в компиляторе Hsu между обходом (структура) и собственно вычислением (`../archive/08-array-trees.md` §16, дисс. Hsu §5.2 — traversal отделён от структурных изменений). Здесь: сначала считаем **разметку буфера** (кто где пишет), потом — **сами хеши** (что пишет).

### 3.1. Число детей — `nchildren`

Гистограмма родителей, без учёта самоссылки корня — это ровно идиома *Counting Rank of Index Operations* из компилятора Hsu (`../hsu-dissertation/03-compiler-passes.md#counting-rank-of-index-operations-38`), применённая не к индексирующим узлам, а к дереву целиком:

```
nchildren = [0, 0, ..., 0]                    // длина n
для всех i != parent[i]:
    nchildren[parent[i]] += 1
```

Как и в §3.8 дисс. Hsu, это — гистограмма (scatter-add с повторяющимися индексами), не сортировка и не обход.

### 3.2. Позиция среди братьев — `rank`

Уже выведено в `../archive/08-array-trees.md` §3.6 (propagation вдоль `sibling`, а не вдоль `parent`):

```
rank[i] = 0,                    если sibling[i] == i
rank[i] = rank[sibling[i]] + 1, иначе
```

Поскольку `sibling[i] <= i`, это вычисляется **одним проходом по возрастанию `i`** (тот же приём, что в `../archive/08-array-trees.md` §5.3 для `propagateDown`) — при вычислении `rank[i]` значение `rank[sibling[i]]` уже готово.

### 3.3. Смещение сегмента — `offset` (CSR-разметка)

Дети одного родителя должны лежать в общем буфере `childHash` **подряд**, чтобы читать их как один непрерывный диапазон. Это классическая раскладка CSR (compressed sparse row): `offset[p]` — начало сегмента родителя `p`, обычная **исключающая префиксная сумма** по `nchildren`:

```
offset[0] = 0
offset[p] = offset[p-1] + nchildren[p-1],   p = 1 .. n-1
```

Размер буфера `childHash` — `offset[n-1] + nchildren[n-1]`, то есть `n-1` (у каждого узла, кроме корня, ровно один слот где-то в этом буфере).

### 3.4. Слот ребёнка — чистая структура, без значений

```
slot[i] = offset[parent[i]] + rank[i],   для всех i != parent[i]
```

`slot[i]` — единственная и заранее известная ячейка `childHash`, куда узел `i` запишет свой хеш **ровно один раз**, и в неё не пишет никто другой (пары `(parent[i], rank[i])` попарно различны по построению rank). Именно так результат вычисления ребёнка передаётся родителю: не через ассоциативный merge в общую ячейку (как `or` для маски), а через **разрозненную запись (scatter) в предвычисленный персональный слот**, после чего родитель читает свой сегмент `childHash[offset[p] : offset[p] + nchildren[p]]` как готовый, упорядоченный слева направо массив хешей детей — без гонок и без необходимости знать заранее, кто из детей допишется первым.

## 4. Собственно вычисление: `hash[i]`

`nchildren`, `rank`, `offset`, `slot` — чистая структура, считается один раз для статичного дерева и не зависит от `value`. Вычисление `hash[i]` — единственный шаг, где нужен реальный порядок «сначала дети, потом родитель».

### 4.1. Последовательная версия — один проход, `O(n)`

Farc гарантирует `parent[i] <= i` (`../archive/05-data-format.md` §3) — родитель физически создан раньше любого ребёнка, то есть **id любого ребёнка строго больше id его родителя**. Значит, проход по **убыванию** `i` гарантирует: когда мы обрабатываем узел `p`, все узлы с `id > p`, включая всех детей `p`, уже обработаны и записали свой хеш в `childHash`. Это прямое обобщение `propagateUp` из `../archive/08-array-trees.md` §5.3 (там — распространение одного бита вверх за один проход по убыванию, здесь — распространение целого значения через precomputed slot вместо merge):

```go
// H(prefix, parts...) — заглушка: реальная криптографическая хеш-функция
// (например, sha256.Sum256) от конкатенации prefix и всех parts.
func merkleHashes(parent, sibling []uint32, value [][]byte, n int) (hash [][]byte, childHash [][]byte) {
    nchildren := make([]int, n)
    for i := 0; i < n; i++ {
        if parent[i] != uint32(i) {
            nchildren[parent[i]]++
        }
    }
    offset := make([]int, n)
    for p := 1; p < n; p++ {
        offset[p] = offset[p-1] + nchildren[p-1]
    }
    rank := make([]int, n)
    for i := 0; i < n; i++ { // sibling[i] <= i — можно по возрастанию
        if sibling[i] != uint32(i) {
            rank[i] = rank[sibling[i]] + 1
        }
    }

    childHash = make([][]byte, offset[n-1]+nchildren[n-1])
    hash = make([][]byte, n)

    for i := n - 1; i >= 0; i-- { // parent[i] <= i — обязательно по убыванию
        if nchildren[i] == 0 {
            hash[i] = H(0x00, value[i])
        } else {
            children := childHash[offset[i] : offset[i]+nchildren[i]] // уже полностью заполнен
            hash[i] = H(0x01, value[i], children...)
        }
        if parent[i] != uint32(i) {
            childHash[offset[parent[i]]+rank[i]] = hash[i]
        }
    }
    return hash, childHash
}
```

Сложность — `O(n)` время, `O(n)` память (`childHash` + вспомогательные векторы), но **чисто последовательно**: `hash[i]` зависит от `hash` всех детей `i`, обработанных на этом же проходе, и внутри одного прохода это истинная цепочка зависимостей — как и boolean-версия в §5.3, эта версия не векторизуется и не раздаётся по ядрам, потому что порядок обработки узлов сам является частью корректности алгоритма.

### 4.2. Параллельная версия — по уровням, от листьев к корню

Это версия, которая отвечает на исходное наблюдение из доклада Hsu: если данные уже размечены **по уровням глубины**, дерево можно обрабатывать не последовательным проходом по `id`, а как серию **синхронных, полностью независимых внутри одного уровня шагов**, начиная с самого глубокого уровня (листьев) и поднимаясь к корню.

Последовательный проход по `id` (§4.1) заменяется на проход **по уровням `depth`** — точно так же, как в `../archive/08-array-trees.md` §8.2 (шаг 2) уже вычисляется `size` поддерева: «идя по уровням от самого глубокого к первому, добавлять `size[i]` в `size[parent[i]]`». Merkle-хеш — то же накопление снизу вверх по уровням, только объединяющая операция — не `+`, а `H(0x01, value[i], childHash[i-сегмент])`, а передача результата — не суммирование в общую ячейку, а scatter в `slot[i]` (§3.4):

```
depth = propagation по parent (../archive/08-array-trees.md §6.2, или pointer doubling §5.4 за O(log d))

для level = max(depth) downto 0:
    // всё, что ниже level, уже посчитано — вычисление внутри уровня полностью параллельно
    для всех i с depth[i] == level (параллельно, SIMD/GPU):
        если nchildren[i] == 0:
            hash[i] = H(0x00, value[i])
        иначе:
            hash[i] = H(0x01, value[i], childHash[offset[i] : offset[i]+nchildren[i]])
        если parent[i] != i:
            childHash[slot[i]] = hash[i]
```

Почему это корректно и почему именно так, а не иначе:

- **Синхронизация только между уровнями, не внутри уровня.** Все узлы одного уровня `depth[i] == level` независимы друг от друга: ни один из них не является предком или потомком другого (по определению глубины), поэтому чтения `childHash[offset[i]:...]` и записи `childHash[slot[i]]` внутри одного уровня не пересекаются — можно исполнять параллельно (SIMD-полосой или на GPU-ядрах), без блокировок.
- **К моменту обработки уровня `level` его дети (уровень `level+1`) уже полностью посчитаны** — обход идёт строго от максимальной глубины к нулю, поэтому когда для узла `i` читается `childHash[offset[i] : offset[i]+nchildren[i]]`, все слоты этого диапазона уже записаны на предыдущем шаге (детьми, у которых `depth = level+1`).
- **Критический путь — `O(depth)` шагов, а не `O(n)`.** Внутри шага работа полностью параллельна (`O(широта уровня)` независимых операций), а всего шагов ровно столько, сколько уровней в дереве. Это ровно классификация *Reduce — Logarithmic (Tree Reduction)* из Table 2 диссертации Hsu (`../hsu-dissertation/01-apl-and-background.md#16-производительность-и-модель-памяти-215`): Merkle-хеширование дерева — частный случай tree reduction, критический путь которого определяется глубиной дерева, а не числом узлов. Для сбалансированного дерева `depth = O(log n)` — тот самый логарифмический критический путь; для сильно несбалансированного (например, длинная цепочка из одиночных детей) — вплоть до `O(n)`, то есть параллельная версия ничего не проигрывает последовательной в худшем случае и выигрывает в среднем и хорошем.
- **`depth` — предвычисляется отдельно и один раз.** Это тот же вектор, что и для boolean propagation (`../archive/08-array-trees.md` §6.2), либо его же ускоренный вариант через pointer doubling (§5.4) за `O(log d)` проходов вместо `O(d)` — сам расчёт `depth` не входит в критический путь хеширования, это подготовительный структурный шаг, как `nchildren`/`rank`/`offset`/`slot` в §3.
- **Группировка узлов «по уровню» — уже готовый побочный продукт.** Если дерево уже переупорядочено в BFS-порядок (`../archive/08-array-trees.md` §9, level-order), узлы одного уровня и так лежат смежным диапазоном — перебор `i` с `depth[i] == level` вырождается в срез массива, без фильтрации.

## 5. Пример на сквозном дереве

Дерево из `../archive/08-array-trees.md` §2 (13 узлов, два канала). Обозначим `hK` — хеш узла `K` (символически, без реальных байтов хеш-функции):

```
h8  = H(0x00, value8)                              // video   (лист)
h10 = H(0x00, value10)                             // audio   (лист)
h11 = H(0x00, value11)                              // video   (лист)
h12 = H(0x00, value12)                              // video   (лист)

h6  = H(0x01, value6,  h8, h10)                     // stream(0): дети в порядке rank — video, затем audio
h9  = H(0x01, value9,  h11)                          // stream(1): один ребёнок
h7  = H(0x01, value7,  h12)                          // stream(0) второго канала

h4  = H(0x01, value4,  h6, h9)                       // streams канала 1
h5  = H(0x01, value5,  h7)                           // streams канала 2

h2  = H(0x01, value2,  h4)                           // channel(1)
h3  = H(0x01, value3,  h5)                           // channel(2)

h1  = H(0x01, value1,  h2, h3)                       // channels
h0  = H(0x01, value0,  h1)                           // root — итоговый Merkle-корень дерева
```

По уровням (то, как это считалось бы параллельной версией §4.2, от глубокого к мелкому): уровень 4 — `{8, 10, 11, 12}` (все листья, параллельно), уровень 3 — `{6, 9, 7}`, уровень 2 — `{4, 5}`, уровень 1 — `{2, 3}`, уровень 0 — `{1}`, наконец корень `{0}`. Шесть уровней — шесть последовательных шагов вместо тринадцати последовательных при обходе по `id`.

`h0` — единственное значение, зависящее от содержимого и структуры всего дерева: изменение любого `value[i]` или перестановка любых двух братьев (например, поменять местами `video` и `audio` под `stream(0)`, узел 6) меняет `h6`, а значит и все хеши по цепочке предков вплоть до `h0` — именно за счёт того, что `rank` зафиксировал порядок при построении `childHash`.

## 6. Практические следствия

- **Порядок детей — часть входных данных хеша, а не деталь реализации.** Если порядок братьев для домена не значим (например, набор потоков в канале логически неупорядочен), либо явно сортируют `childHash`-сегмент по некоторому каноническому ключу перед хешированием (тогда `rank` для этой цели не используется вовсе, а слот определяется этим ключом), либо смиряются с тем, что перестановка братьев меняет корень — и то и другое нужно решить на уровне домена, алгоритм сам по себе от этого решения не зависит.
- **`sibling` не отбрасывается раньше времени.** `../archive/08-array-trees.md` §3.7/§8.4 отмечает, что после перевода дерева в DFS-порядок `sibling` избыточен (порядок братьев следует из порядка массива). Для Merkle-хеширования это верно ровно в той же мере: `rank` можно получить и из DFS-позиции без хранения `sibling`, но пока дерево в порядке создания (растущий фконтейнер, `../archive/05-data-format.md` §2), `sibling` — единственный источник порядка братьев.
- **Инкрементальность.** Поскольку `hash[i]` зависит только от `value[i]` и хешей **прямых** детей (не всего поддерева целиком через `value`), при добавлении нового узла в конец растущего дерева (append, `../archive/08-array-trees.md` §11.2) пересчитать нужно только цепочку хешей от нового узла до корня (`O(depth)` узлов) — не всё дерево заново. Это тот же bottom-up traversal idiom, применённый не ко всем узлам, а к одной ветке.
