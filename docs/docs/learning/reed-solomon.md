# Reed-Solomon: восстановление данных после потери части блоков

Учебный материал: как устроено помехоустойчивое кодирование Рида-Соломона (erasure coding) и как им пользуются на практике. **В farc сегодня не используется и не планируется в ближайших итерациях** — документ существует, чтобы идея была под рукой, если и когда встанет вопрос восстановления данных, а не только их обнаруженного повреждения.

## 1. Зачем это farc (и почему не сейчас)

Сегодня farc умеет только **обнаруживать** повреждение, но не **восстанавливать** данные: CRC32 по трём частям заголовка и по контенту/TOC (`../archive/03-storage-format.md` §7, §9) ловит битую секцию, после чего весь фблок помечается `bad`, а запись переносится на следующий подходящий фблок (`../archive/00-requirements.md`, `../archive/04-storage-operations.md` §7.3, write-verify). Это надёжно, но одностороннее решение: единица отказа — фблок целиком, единственное действие при отказе — списать его и писать заново. Ни один существующий механизм не пытается **восстановить** содержимое повреждённого или утраченного фблока из другой информации.

Reed-Solomon (далее RS) — это ровно инструмент для второго: не обнаружение (для этого хватает CRC32), а **реконструкция** утраченных данных из части избыточности, вычисленной заранее. Практическое применение для farc, если оно когда-нибудь понадобится, — не внутри одного фблока, а **между хранилищами**: несколько Storage (дисков) хранят данные так, что потеря одного или двух целиком (не только отдельного фблока) не означает потерю данных — это тот же принцип, что RAID6 или erasure-coded объектные хранилища (Ceph, MinIO, Backblaze) используют вместо полного зеркалирования.

Почему не сейчас — сознательное решение, не забытая деталь:

- **Самодостаточность фблока** (`../archive/00-requirements.md`) — сегодня каждый фблок читается независимо, без данных из других фблоков или хранилищ. Erasure coding между хранилищами по определению это нарушает: чтобы восстановить фблок хранилища A, нужны данные хранилищ B и C. Введение RS потребовало бы явно пересмотреть это требование для нового, отдельного режима отказоустойчивости — не патча поверх текущего формата.
- **Один писатель на хранилище, независимая изоляция** (ADR-005, `../archive/00-requirements.md`) — сегодня хранилища ничего не знают друг о друге во время записи. Кодирование по нескольким хранилищам требует координации записи между ними (то же логическое смещение, синхронный прогресс), а это — новый протокол, которого сейчас нет.
- Цена — CPU на кодирование/декодирование и дисковый/сетевой трафик на восстановление (§6) — оправдана только при реальном требовании пережить потерю целого диска, а не отдельного повреждённого участка, для которого уже есть write-verify и `bad`-пометка.

Дальше — как это работает, независимо от того, когда (и будет ли) это использовано в farc.

## 2. Постановка задачи: k данных + m избыточности = n частей

Есть `k` частей данных (data shards) — например, `k` дисков с частями одного и того же логического блока. RS строит ещё `m` частей избыточности (parity shards), так что получается `n = k + m` частей всего, и выполняется ключевое свойство — **MDS (Maximum Distance Separable)**: **любые `k` из `n` частей достаточны, чтобы восстановить исходные `k` частей данных**, независимо от того, какие именно `m` частей потеряны.

Пример: `k=4`, `m=2` (аналог RAID6, но не ограничено двумя избыточными частями) — 6 частей всего, любые 4 из 6 достаточны. Можно потерять **любые** 2 части одновременно (в любом сочетании — два data shard, два parity shard, или один и один) и полностью восстановить исходные 4.

Отличие от простого зеркалирования (репликации): чтобы пережить потерю 2 из 6 копий данных репликацией, нужно 3-кратное копирование (200% оверхед). Такой же уровень отказоустойчивости через RS `k=4, m=2` стоит 50% оверхеда (`n/k = 6/4 = 1.5×` вместо `3×`) — но за счёт вычислений при кодировании/декодировании и более дорогого восстановления (нужно прочитать `k` частей, а не одну копию, §6).

## 3. Как это работает: линейная алгебра над конечным полем

### 3.1. Почему не обычная арифметика

Идея RS — представить данные как вектор и умножить его на специально подобранную матрицу так, чтобы результат обладал MDS-свойством. Для этого нужна арифметика, в которой у любого ненулевого числа есть обратное (можно делить), а результат сложения/умножения байтов не переполняется и не теряет точность, — обычная арифметика с переносом (`uint8`, `float`) для этого не годится: переполнение `uint8` и округление `float` разрушают алгебраические свойства, на которых держится восстановление.

Решение — **конечное поле Галуа** `GF(2^8)` (256 элементов, ровно один байт на элемент — удобно для байт-ориентированных данных). Сложение в `GF(2^8)` — побитовый XOR (без переноса, обратимо само на себя: `a XOR a = 0`). Умножение — полиномиальное умножение по модулю неприводимого многочлена степени 8 (например, `x^8+x^4+x^3+x^2+1`, стандарт для RS в хранилищах и QR-кодах), реализуется на практике через предвычисленные таблицы логарифмов/антилогарифмов (`log`/`exp` таблицы по 256 элементов) — умножение через таблицы превращается в `exp[log[a] + log[b] mod 255]`, то есть в две табличные подстановки и одно сложение по модулю. Ключевое свойство поля: у любого `a != 0` есть обратный элемент `a⁻¹` такой, что `a * a⁻¹ = 1` — именно это делает возможным обращение матриц (§4.2), то есть само восстановление.

Для понимания линейной алгебры ниже детали `GF(2^8)` не важны — их можно на время подменить обычной арифметикой по модулю небольшого простого числа `GF(p)` (например, `GF(7)`), чтобы увидеть структуру без таблиц Галуа; реальные реализации используют `GF(2^8)` ради побайтовой упаковки данных и SIMD-дружественности (§6).

### 3.2. Кодирующая матрица (Vandermonde)

Данные разбиваются на `k` шардов (shard — блок байтов одинакового размера; при разных исходных размерах — дополняются нулями). Шард — не обязательно один байт, вся арифметика применяется **побайтово и независимо** к каждой позиции внутри шардов (то есть можно представлять шард как один "символ" для алгебры и повторить операцию по всем байтам шарда параллельно).

Строится матрица `n × k`:

```
        ⎡ 1        0        0    ...  0   ⎤   ← единичная k×k — из неё
        ⎢ 0        1        0    ...  0   ⎥     дешифрованные data-шарды
        ⎢ ...                             ⎥     получаются "как есть"
G   =   ⎢ 0        0        0    ...  1   ⎥
        ⎢ c₀⁰      c₁⁰      c₂⁰  ... c_{k-1}⁰ ⎥  ← m строк снизу — Vandermonde,
        ⎢ c₀¹      c₁¹      c₂¹  ... c_{k-1}¹ ⎥     дают parity-шарды
        ⎣ ...                                ⎦
```

Верхние `k` строк — единичная матрица (систематическое кодирование: сами данные не преобразуются, копируются как есть в первые `k` частей результата). Нижние `m` строк — **матрица Вандермонда**: `j`-й столбец `i`-й нижней строки — это `cⱼ` в степени `i`, где `c₀, c₁, ..., c_{k-1}` — любые `k` попарно различных ненулевых элементов поля (обычно просто `1, 2, ..., k` в арифметике поля). Свойство матрицы Вандермонда, которое и обеспечивает MDS: **любые `k` строк из `n` линейно независимы** — это в точности означает, что систему можно однозначно решить, какие бы `k` частей ни выжили.

**Кодирование**: `parity = V × data`, где `data` — вектор из `k` шардов, `V` — нижние `m` строк матрицы (та самая часть Вандермонда), `parity` — `m` новых шардов. Вместе `data ∪ parity` — это `n = k+m` шардов, готовых к раздаче по независимым хранилищам/дискам.

## 4. Восстановление

### 4.1. Erasure (известны позиции потерь) — типичный случай для хранилищ

Ключевое упрощение для систем хранения: **какие именно части потеряны — уже известно** (тот же диск не отвечает, тот же файл отсутствует, либо не прошла CRC32-проверка отдельного шарда) — это называется **erasure** (стирание), в отличие от **error** (ошибка в неизвестной позиции, §4.3). Для erasure декодирование значительно проще.

Пусть выжило ровно `k` из `n` шардов (если выжило больше — берём любые `k`, лишние не нужны). Возьмём соответствующие `k` строк исходной матрицы `G` (§3.2) — получим квадратную `k × k` подматрицу `G'`. По построению `G'` обратима (MDS-свойство — любые `k` строк независимы), поэтому:

```
data = G'⁻¹ × survived
```

где `survived` — вектор из `k` выживших шардов (в том порядке, в котором взяты соответствующие строки `G'`). Обращение матрицы `k × k` над `GF(2^8)` — единственная дорогая операция при восстановлении, и она не зависит от размера шардов — размер шардов лишь умножает число одинаковых операций (одна и та же матрица `G'⁻¹` применяется к каждому байту шарда независимо, что тривиально векторизуется, §6).

После восстановления `data` при необходимости пересчитываются и утраченные parity-шарды — обычным кодированием (§3.2) из уже восстановленных `data`.

### 4.2. Численный пример (`k=4, m=2`, арифметика упрощена до целых для наглядности)

Пусть данные — 4 шарда `d₀=5, d₁=3, d₂=9, d₃=1` (в реальности — байтовые массивы, здесь — по одному числу на шард для простоты; в `GF(2^8)` арифметика другая, но структура рассуждения та же). Пусть parity считаются как `p₀ = d₀+d₁+d₂+d₃` и `p₁ = d₀+2d₁+3d₂+4d₃` (упрощённая, не настоящая Вандермонда над полем — только чтобы показать идею):

```
p₀ = 5+3+9+1 = 18
p₁ = 5+2·3+3·9+4·1 = 5+6+27+4 = 42
```

Шесть частей: `[d₀=5, d₁=3, d₂=9, d₃=1, p₀=18, p₁=42]`. Пусть потеряны `d₁` и `d₂` (два data-шарда) — выжили `d₀=5, d₃=1, p₀=18, p₁=42`. Составляем систему из соответствующих строк:

```
d₀            = 5      →  1·d₀ + 0·d₁ + 0·d₂ + 0·d₃ = 5
d₃            = 1      →  0·d₀ + 0·d₁ + 0·d₂ + 1·d₃ = 1
d₀+d₁+d₂+d₃   = 18     →  1·d₀ + 1·d₁ + 1·d₂ + 1·d₃ = 18
d₀+2d₁+3d₂+4d₃= 42     →  1·d₀ + 2·d₁ + 3·d₂ + 4·d₃ = 42
```

Подставляя известные `d₀=5, d₃=1`: из третьего уравнения `d₁+d₂ = 18-5-1 = 12`; из четвёртого `2d₁+3d₂ = 42-5-4 = 33`. Решая систему `d₁+d₂=12` и `2d₁+3d₂=33`: `d₂ = 33-2·12 = 9`, `d₁ = 12-9 = 3` — совпадает с исходными значениями. Ровно это и делает обращение `4×4`-матрицы `G'⁻¹` за один шаг вместо ручной подстановки — при реальном `GF(2^8)` и байтовых шардах то же самое проделывается сразу для всех байтов шарда одной и той же обратной матрицей.

### 4.3. Error correction (позиция неизвестна) — другой режим, для хранилищ обычно не нужен

Если бы позиции повреждения были **неизвестны** (не erasure, а error — например, часть байтов внутри шарда молча испортилась, но какая именно неизвестно), потребовался бы полноценный decoder с вычислением синдромов и локатором ошибок (алгоритм Берлекэмпа-Мэсси или Берлекэмпа-Уэлча для нахождения позиций, затем алгоритм Форни для величин ошибок, затем поиск корней локатора — Chien search). Такой режим используется там, где нет дешёвого способа заранее узнать, какая часть повреждена — CD/DVD, QR-коды, спутниковая/радиосвязь. Для систем хранения он обычно избыточен: CRC32 (или аналог) уже дёшево и надёжно локализует повреждённый шард целиком, превращая error в erasure ещё до вызова RS-декодера — то же самое разделение ролей, что CRC32 (`../archive/03-storage-format.md`) и его собственное восстановление в farc сегодня не делают, а могли бы делать вместе, если бы RS был добавлен.

## 5. Как этим пользоваться на практике

Библиотеки для RS-кодирования есть под большинство языков, писать реализацию с нуля для продакшна не нужно и не стоит (тонкости конечного поля, таблиц логарифмов и матричных инверсий легко испортить незаметно для корректности, но заметно для производительности). Для Go — распространённая и активно поддерживаемая реализация: [`klauspost/reedsolomon`](https://github.com/klauspost/reedsolomon) (SIMD-ускорение AVX2/AVX512/GFNI на amd64, NEON на arm64, есть и pure-Go fallback).

Типичный API такой библиотеки (не специфично для farc — общая форма, которую стоит ожидать от любой реализации):

- `New(dataShards, parityShards int) Encoder` — создать кодер на конкретные `k` и `m` (генерирующая матрица строится один раз и переиспользуется).
- `Encode(shards [][]byte) error` — на входе `n` слотов, из которых первые `k` заполнены данными, остальные `m` — пустые буферы; после вызова все `n` заполнены (посчитаны parity).
- `Verify(shards [][]byte) (bool, error)` — проверить, что имеющиеся `n` шардов согласованы (не заменяет CRC на уровне отдельного шарда, а проверяет согласованность data/parity между собой).
- `Reconstruct(shards [][]byte) error` — на входе `n` слотов, часть — `nil` (утрачены), остальные — данные; после вызова все `n` восстановлены. Часто есть отдельный `ReconstructData`, восстанавливающий только `k` дата-шардов без пересчёта parity, если parity не нужен получателю.
- `Split(data []byte) ([][]byte, error)` / `Join(dst io.Writer, shards [][]byte, outSize int)` — вспомогательные функции нарезки произвольного байтового потока на `k` шардов фиксированного размера (с паддингом) и обратной сборки.

Выбор `k`/`m` — компромисс, не универсальное значение:

- **Отказоустойчивость** = `m` (сколько шардов можно потерять одновременно) — не зависит от `k`.
- **Оверхед по месту** = `n/k = (k+m)/k` — растёт с `m`, падает с ростом `k` при фиксированном `m` (например, `k=10, m=4` даёт ту же устойчивость к потере 4 частей, что и `k=4, m=4`, но с оверхедом `1.4×` вместо `2×`).
- **Стоимость восстановления** — растёт с `k`: чтобы восстановить один утраченный шард, нужно прочитать **любые `k`** выживших (не один, как при репликации) — это трафик и время, особенно если шарды разнесены по сети (между дата-центрами/дисками). Большой `k` снижает оверхед по месту, но увеличивает стоимость и время восстановления, и увеличивает вероятность одновременно не набрать `k` выживших шардов, если отказы не полностью независимы.
- **Стоимость кодирования** — растёт с `k × m` (размер матрицы) на каждый закодированный блок данных; для очень больших `k` рассматривают многоуровневые/локально восстанавливаемые коды (не RS в чистом виде) — вне рамок этого документа.

Практические ориентиры из индустрии (не предписание для farc, просто чтобы было к чему привязать порядок величин): Backblaze использует `k=17, m=3` в своих storage pods (оверхед ~1.18×, переживает потерю любых 3 из 20 дисков); Ceph по умолчанию предлагает профили вроде `k=4, m=2` или `k=6, m=3`; большинство объектных хранилищ выбирают `m` в диапазоне 2–4 в зависимости от требуемой доступности и берут `k` настолько большим, насколько позволяет приемлемая стоимость и время восстановления.

## 6. Производительность

Кодирование и декодирование — это умножение матрицы `m×k` (или `k×k` при восстановлении) на вектор шардов, где каждый "элемент" вектора — не число, а целый шард (массив байт), и операция применяется **побайтово и независимо** ко всем позициям шарда сразу. Это делает RS исключительно SIMD- и GPU-дружественным по той же причине, по которой массивные операции APL хорошо ложатся на векторные архитектуры (`../hsu-dissertation/01-apl-and-background.md` §1.6, Table 1/2): одна и та же операция над конечным полем (табличное умножение + XOR-сложение) повторяется независимо по огромному числу байтовых позиций — классический **SIMD map с константным критическим путём**, не связанный зависимостями между позициями внутри шарда. Современные реализации используют инструкции `GFNI` (Galois Field New Instructions, начиная с Intel Ice Lake) для умножения в `GF(2^8)` напрямую в кремнии, без табличных подстановок — на таком железе RS-кодирование достигает пропускной способности в единицы–десятки ГБ/с на ядро.
