# 2. Архитектура компилятора и представление AST (3.1–3.4, стр. 47–96)

## 2.1. Overview (3.1) — 11 проходов

Компилятор Co-dfns построен «в духе» Nanopass: единый линейный поток данных, где входной AST проходит серию трансформаций IR→IR, каждая следующая IR лишь немного отличается от предыдущей. Но в отличие от Nanopass, компилятор радикально отказывается от его инфраструктуры: нет `define-language`/`define-pass`, нет обёрток над record-типами. Это **одна функция**, состоящая из последовательности APL-выражений, сгруппированных по проходам; IR кодируется прямо как inverted table (SoA), и каждый проход идиоматически трансформирует данные этой таблицы.

Проходы компилятора, в порядке выполнения:

1. Перевод AST (depth vector) в **parent vector** — [§2.2](#22-от-record-type-до-parent-vector-32).
2. Вычисление **ближайшего лексического контура** (referent) для каждого узла — [§2.4](#24-вычисление-ближайшего-лексического-контура-34).
3. **Lift functions** — поднятие вложенных функций на верхний уровень дерева.
4. **Wrap expressions** — оборачивание выражений (явные return/continue узлы).
5. **Lift guard test expressions** — поднятие тестовых выражений guard-конструкций.
6. Подсчёт **ранга операций индексирования**.
7. **Flatten expressions** — уплощение вложенных выражений.
8. Назначение каждой переменной **слота фрейма**.
9. Упорядочивание фреймов функций по глубине в **лексическом стеке**.
10. Фиксация **экспортируемых имён** модуля/namespace.
11. **Лексическое разрешение** переменных до конкретного фрейма и слота.

Проходы 3–11 подробно разобраны в [файле 3](03-compiler-passes.md). Вместе они демонстрируют полный набор элементарных операций, достаточных для произвольного анализа и модификации структуры дерева — без рекурсии, ветвления или ADT.

## 2.2. От record-type до parent vector (3.2)

Автор последовательно отвергает несколько представлений AST, прежде чем приходит к parent vector + SoA. Сами структуры данных (parent/depth vector, path coordinate matrix, DFS/BFS-порядок, LCA, операции изменения дерева) уже подробно разобраны в справочнике проекта — см. [`archive/08-array-trees.md`](../archive/08-array-trees.md). Здесь — только мотивация выбора в порядке изложения диссертации.

**Record-type representation** (3.2.1) — классическое дерево с указателями parent↔children. Хорошо приспособлено к CPU: удобны рекурсивный обход, добавление/удаление/обновление узлов через GC, статическая типизация через ADT. На векторных машинах (GPU, SIMD) все его достоинства становятся недостатками: ветвление (pattern matching) плохо векторизуется, указатели дают произвольный (non-contiguous) доступ к памяти, каждое ребро требует полноразмерного указателя (пример: узел + 2 указателя = 192 бита на узел). Автор формулирует 8 желательных свойств для векторных программ (без рекурсии, без ветвления, малые типы, непрерывное размещение, последовательный доступ, минимум памяти, минимум зависимостей по данным, использование SIMD) — record-type representation не удовлетворяет почти ни одному.

**Линеаризация как таблица** (3.2.2) — дерево сериализуется в depth-first pre-order в вектор/таблицу, где позиция элемента = его node id (восходит к книге Айверсона 1962 года).

**Depth vector representation** (3.2.3) хранит для каждого узла его глубину; компактно (битов на элемент требуется по глубине дерева, не по числу узлов), непрерывный доступ к памяти. Два недостатка: вставка узла в середину требует копирования большого куска вектора; чтобы найти родителя/детей, нужно неявно «сканировать» вектор — скрытая зависимость по порядку элементов.

**Path matrices** (3.2.5) — для каждого узла хранится полный путь до корня (матрица N×D, D — глубина дерева). Снимает зависимость по порядку: любые два узла сравнимы напрямую, хорошая локальность (путь узла — один столбец). Цена — O(N×D) памяти, избыточная при росте дерева; отвергнут как основное представление, остаётся теоретическим инструментом для отдельных операций.

**Parent vector representation** (3.2.6) — итоговый компромисс: вектор `p`, `p[i]` — id родителя узла `i`, корни указывают сами на себя (`p[i]=i`, самоссылка вместо null устраняет ветвление при проверке границ). Большинство манипуляций деревом не требуют полной сравнимости любых двух узлов (как в path matrix) — важнее движение вверх/вниз или между соседями. Parent vector даёт линейную память, частичный (не полный) порядок, упрощает добавление узлов (часто достаточно дописать в конец) и удаление. Дополнительный sibling vector для полного упорядочивания в этой работе не используется.

## 2.3. Converting from Depth Vector to Parent Vector (3.3)

**Задача.** Парсер строит AST как depth vector `d` (компактно и просто конструируется рекурсивным спуском во время парсинга), но компилятор работает с parent vector `p` — нужен явный переход `d → p`.

Формально: родитель узла `i` — ближайший слева узел `j` (`j<i`) с `d[j]=d[i]-1`, при минимальном `i-j` («ближайший слева узел на единицу мельче глубиной»).

**Наивная реализация** — для каждого узла `i` строится булев вектор совпадения глубины `d[⍳i]=d[i]-1`, применяется OR-scan справа налево (разворот + сканирование), сумма даёт индекс первого совпадения — ближайшего родителя слева. Обобщение на весь вектор — через внешнее произведение `∘.>⍨d` (булева матрица «глубже ли узел i, чем узел j») с нижней треугольной маской `∘.≥⍨⍳≠d` (только позиции слева от диагонали) → матрица кандидатов-родителей, построчный OR-scan + сумма дают `p` целиком. Вычисление полностью безрекурсивно, построено на outer product + scan. Недостаток: асимптотика квадратична и по памяти, и по времени (доминирует внешнее произведение N×N), хотя критический путь (parallel depth) линеен — классический trade-off «пространство vs время» в векторном стиле.

**Улучшенная реализация**, устраняющая квадратичность: родитель узла глубины `d` обязан иметь глубину `d-1`, и каждый узел глубины `d` появляется в векторе `d` между своим родителем и следующим узлом того же/меньшего уровня. Узлы группируются по глубине оператором Key (`⊢∘⊂⌸d`) — вектор (nested) списков id узлов на каждом уровне глубины, в порядке depth-first pre-order. Для каждой пары соседних уровней глубины (`i-1` и `i`) применяется **Interval Index** (`⍸`-подобная операция): она находит, в какой интервал между соседними элементами группы `i-1` попадает каждый элемент группы `i` — то есть ищет ближайшего «старшего соседа слева» среди кандидатов на меньшую глубину.

Итоговое выражение реализуется через **попарную (pairwise) редукцию** по группам, результат пишется в предварительно инициализированный `p←⍳≠d` (все узлы изначально — корни). Сложность: сама редукция линейна (запись в `p` по индексам `≠d`, отсортированным); группировка по Key — сортировка по небольшому диапазону целых, тоже линейна. Итог: **O(≠d) память и время на последовательной машине**. Для параллельной машины: записи в `p` независимы; критический путь Interval Index — `O(⍟(≠α))`, критический путь группировки — `O(⍟(≠d))`, итоговый критический путь всего алгоритма — `O((⍟m)+⍟≠d)`, где `m` — максимальный размер ветви (branch) AST. Это решение значительно эффективнее «наивного» на обеих архитектурах, при этом код проще/короче (хотя чуть менее «очевиден»).

## 2.4. Вычисление ближайшего лексического контура (3.4)

**Задача.** После перехода к parent vector компилятор должен для каждого узла записать id ближайшего охватывающего узла-функции — его лексический контур/область видимости. В dfns существует взаимно-однозначное соответствие между лексическими контурами и пользовательскими функциями/namespace — эта разметка нужна для всех последующих проходов, прежде всего для лексического разрешения ([§3.13](03-compiler-passes.md#lexical-resolution-313)). Результат — новый столбец `r` длины `p` (значения — тоже node id).

Автор явно называет это «простейшей демонстрацией фундаментальной концепции обхода AST в компиляторе» и сравнивает два подхода:

**Традиционный top-down (рекурсивный) обход.** Левый аргумент `α` — текущий ближайший лексический узел, правый `ω` — поддерево для разметки; на листе — пометить текущим `α`; на функциональном узле — обновить `α` на id этого узла и рекурсивно спуститься; иначе — спуститься с прежним `α`. Хорошо работает на одном потоке: единственная переменная надёжно «переносится» через стек вызовов. На параллельных машинах проблематично: (1) параллельное обновление сложных структур (таблиц соответствий) вызывает дублирование данных либо накладные расходы синхронизации по мере продвижения вглубь; (2) top-down обход требует динамически менять степень параллелизма по ходу спуска (на каждом уровне дерева — разное число веток) — нерегулярные, труднопредсказуемые паттерны параллелизма, а именно предсказуемость критична для мелкозернистого SIMD/GPU (в отличие от крупнозернистого SMP, где work-stealing справляется с динамическим параллелизмом, но с инженерными издержками).

**Bottom-up обход через parent vector.** Компилятор инвертирует направление: вместо родителя со списком детей (естественно ведёт к top-down) — у каждого узла один указатель на родителя (естественно ведёт к обходу от листьев к корню). Каждый узел параллельно (независимо, в лок-степе, без синхронизации между потоками) идёт вверх по `p` к корню, пока не найдёт узел нужного типа (функцию). Число активных «потоков»/векторных полос постоянно (равно числу узлов), а не растёт/сокращается по мере обхода, как в top-down (где параллелизм экспоненциально растёт от 1 до 8 по уровням дерева в примере автора).

Алгоритм строится на **traversal idiom**: `I@{t[ω]≠3}⍣≡⍤p` — для вектора id узлов `ω` заменять `ω[i]` на `p[ω[i]]`, пока предикат «не функция» (`t[ω]≠3`, тип 3 = функциональные узлы) истинен, применяя это до **неподвижной точки** (`⍣≡`). Все узлы дерева шагают вверх по родителям параллельно, до тех пор пока не найдут функцию, итеративно, без рекурсии, за число раундов, равное глубине самой глубокой функции. Финальный код прохода — одна строка: `r←I@{t[ω]≠3}⍣≡⍤p`.

Асимптотика: критический путь итерации константен (SIMD), число итераций ограничено глубиной самой глубокой функции в AST — на практике почти константа (глубина AST обычно мала даже при больших объёмах исходников). Худший случай — очень глубокое дерево с малым фактором ветвления.

**Ключевой приём, на котором держится техника**: node id одновременно являются валидными индексами в любой из колонок AST — id реифицированы как явно вычислимые числа, а не непрозрачные указатели. Это позволяет производить произвольную арифметику/индексацию по id узлов, что и делает возможными компактные векторные идиомы (traversal idiom, wrap expressions, lifting) без отдельного слоя абстракций над деревом.
