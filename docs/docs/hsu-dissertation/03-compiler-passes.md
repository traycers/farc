# 3. Проходы компилятора 3.5–3.13 (стр. 96–143)

Все проходы работают над AST в виде SoA: колонки `p` (parent), `t` (type), `k` (kind/подтип), `n` (name/node-data — отрицательные значения — имена, неотрицательные — id узлов), `r` (referent — ближайший контур, см. [§2.4](02-ast-representation.md#24-вычисление-ближайшего-лексического-контура-34)). Каждый проход — одно-несколько безусловных APL-выражений над этими векторами целиком, без циклов и ветвлений по отдельным узлам: булевы маски, `⍸` (Where), `⌸`/Key-группировки, `/` (Replicate), сортировки, `@` (At — точечная замена по индексам).

## Lifting Functions (3.5)

**Задача в обычном компиляторе.** Лямбда-поднятие (lambda lifting) — превращение вложенных функциональных литералов в top-level функции, со ссылкой на прежнем месте. В рекурсивном компиляторе делается обходом сверху вниз с накоплением списка «поднятых» определений.

**Безрекурсивная реализация.** Выбираются все нерутовые узлы-функции: `i←⍸(t=3)∧p≠⍳≠p`. Функциональные узлы **копируются в конец** векторов (`p,←(≠p)+⍳≠i`), а их прежние позиции превращаются в узлы-переменные (`t[i]←10`, `k[i]←1`), указывающие на новые копии через `n`. Это гарантирует нужный порядок для переменных (обязаны стоять на прежнем месте) без единой перестановки элементов, а функции (без требований к порядку) добавляются простой конкатенацией — массовое, параллельное, непрерывное выделение памяти. Дочерние связи новых функций и поле `r` поправляются через «redirect vector» `j` (`⍳≠p` с позициями `i`, заменёнными на `n[i]`), применяемый как индекс-функция к `p` и `r`.

**Зачем это Co-dfns.** dfns-функции — не first-class объекты (нет замыканий в общем смысле), но синтаксически лексически вложены. Чтобы дальнейшие проходы (фреймы, лексический стек) работали с плоским списком функций, каждая со своим контуром (`r`), все функции нужно вытащить на верхний уровень, сохранив связь «какая переменная теперь стоит там, где раньше было тело функции».

## Wrapping Expressions (3.6)

**Задача в обычном компиляторе.** dfns не имеет явного `return`; выполнение — последовательность операторов с неявным ранним возвратом: функция возвращает значение первого истинного guard'а, первого связывающего выражения либо последнего выражения. Традиционный компилятор при трансляции такой семантики вставляет явные узлы `return`/`continue`.

**Безрекурсивная реализация.** Выбираются узлы, требующие обёртывания: непосредственные statement-дети функциональных узлов и consequent-часть guard-узлов (не test-часть) — маска по типу+родителю, плюс группировка (Key) для выбора «последнего узла в группе братьев» (не-return, т.е. финальные binding-узлы, не возвращающие значение, если не последние). Новые return-узлы нужно **вставить в середину** колонок (в отличие от 3.5, где вставка была в конец) — 4 фазы:

1. выбор узлов для обёртывания (`i`);
2. **расширение** векторов через Replicate (`/`) с репликационным вектором из 1 и 2 (2 — для оборачиваемых узлов, дублирует позицию, освобождая слот перед ними для нового return-узла) — сохраняется вектор `m`, кодирующий относительные смещения;
3. пересчёт указателей (`p`, `r`, `i`, `n`) через redirect-вектор из префиксной суммы (`+\`) над `m` — классическая идиома «разжатия»/scatter после Replicate;
4. установка типа/kind новых узлов и подвешивание `i` под новосозданные `i-1` узлы (return-узлы получают тип «expression» со значением 0/¯1, `k` — через ИЛИ масок «не top-level» и «не финальный binding»).

**Зачем это Co-dfns.** Без явных return-узлов невозможно однозначно «сплющить» (flatten, [3.9](#flattening-expressions-39)) вложенные выражения с сохранением семантики раннего выхода — плоский список операторов должен явно маркировать, какие из них производят возвращаемое значение функции.

## Lifting Guard Test Expressions (3.7)

**Задача в обычном компиляторе.** Guard (`test : consequent`) в AST хранится как узел с двумя детьми. Обычный компилятор при линеаризации условных операторов явно разворачивает тест в отдельную инструкцию перед веткой.

**Безрекурсивная реализация.** Тестовые выражения поднимаются из позиции ребёнка guard-узла в позицию **непосредственного левого брата** guard-узла — подготовка к flattening (3.9). Реализация в 4 шага: (1) выбор тест-узлов `i` (самый левый ребёнок, в отличие от 3.6), соответствующий guard `x = p[i]`; (2) `p[i]←p[x]` — тесты получают тех же родителей, что и guard'ы; (3) поскольку тест оказывается *правым* соседом guard'а вместо нужного левого, узлы `i` и `x` **меняются местами** в колонках `t`, `k`, `n` (достаточно менять только `n` теста — у guard'а поле `n` пусто; дешёвая операция, т.к. `p[i]≡p[x]` и `r[i]≡r[x]`); (4) пересчёт `p` для детей переставленных узлов через redirect-таблицу `((x,i)@(i,x)⊢⍳≠p)[p]`.

**Зачем это Co-dfns.** Чисто структурная нормализация перед flattening: если тест остаётся вложенным ребёнком guard-узла, последующее «разглаживание» не сможет линейно упорядочить тест относительно других top-level выражений функции — тест обязан появиться в исполняемом порядке раньше самого guard'а.

## Counting Rank of Index Operations (3.8)

**Задача в обычном компиляторе.** У индексирующих выражений (`x[i;j;...]`) число индексных позиций произвольно (в отличие от фиксированной арности обычных операторов). Компилятор должен где-то зафиксировать это число, иначе после сплющивания станет невозможно понять, сколько последовательных top-level выражений относится к одной операции индексации.

**Безрекурсивная реализация.** Аналитический (не структурный) проход: одной строкой `n[p≠(t[p]=2)∧k[p]=3]+←1` в поле `n` каждого индексирующего узла записывается число его непосредственных детей. Идиома опирается на семантику модифицированного присваивания APL по индексному вектору с повторяющимися значениями: при `n[i]+←1` с дублирующимися индексами (родитель повторяется столько раз, сколько у него детей) соответствующий элемент `n` инкрементируется многократно устойчиво — фактически вычисляется **гистограмма** числа детей на родителя.

**Зачем это Co-dfns.** После flattening (3.9) индексирующие узлы теряют явную древесную структуру, и без сохранённого счётчика ранга бэкенд не сможет восстановить, сколько подряд идущих плоских выражений составляли индексную операцию.

## Flattening Expressions (3.9)

**Задача в обычном компиляторе.** Аналог linearization/построения списка трёхадресных инструкций из дерева выражений (ANF-подобное преобразование). Все вложенные подвыражения тела функции должны стать плоской последовательностью узлов в порядке фактического исполнения.

**Безрекурсивная реализация.** Схема «выбор → перестановка → коррекция», но перестановочная фаза нетривиальна из-за требования полного порядка внутри функции. Специфика APL: statement'ы функции исполняются слева направо, но **внутри выражения** — справа налево. После поднятия всех узлов выражения на top-level функции (`p[i]←p[x]`, где `x` — id объемлющего statement-узла, вычисляемый тем же traversal-идиомом, что и для `r`), узлы остаются в исходном depth-first pre-order. Но для правильного порядка исполнения нужен обратный порядок **внутри** каждого statement'а с сохранением порядка **между** statement'ами. Ключевое наблюдение: искомый порядок = «развернуть весь список узлов, затем стабильно отсортировать по id объемлющего statement'а» (сортировка стабильна, а statement'ы уже упорядочены по возрастанию id). Перестановочный вектор `j` строится как `(⌽i)[⍋⌽x]`, колонки переставляются простым индексированием, `p` пересчитывается через ту же технику redirect-таблицы.

**Зачем это Co-dfns.** Плоское, лишённое вложенности представление тела функции — необходимое условие для сопоставления имён со слотами фреймов (3.10) и для кодогенерации, исполняемой в стековой/последовательной модели без рекурсивного спуска по дереву на этапе кодогенерации.

## Associating Frame Slots and Variables (3.10)

**Задача в обычном компиляторе.** Построение таблицы символов/фреймов активации: каждой уникальной связке «переменная + лексический контур» присваивается числовой слот в массиве активации (frame) — аналог вычисления смещений локальных переменных относительно указателя кадра стека.

**Безрекурсивная реализация.** Строится таблица `rn` — пары (контур `r[b]`, имя `n[b]`) для узлов-связываний (`t=1`). Таблица `e` — уникальные строки `rn` в отсортированном порядке (`∪∘⍋∘,¨rn`, логарифмический критический путь по числу связываний). По гистограмме первой колонки `e` (число уникальных имён на функцию) строится вектор `s` — порядковый номер слота внутри функции для каждого имени в `e` (идиома `ϵ⍳¨` — enclose-then-index-generator по группам, через Key), с добавлением значения ¯1 как «слота по умолчанию» (нужен позже в 3.13).

**Зачем это Co-dfns.** Каждая dfn-функция получает собственный фрейм (массив слотов); слот — адрес переменной внутри активации. Без таблицы `e`/`s` невозможно компактно закодировать, в какую ячейку фрейма конкретное связывание должно писать значение.

## Placing Frames into a Lexical Stack (3.11)

**Задача в обычном компиляторе.** Вычисление лексической глубины (nesting level) каждой функции — аналог статических цепочек (static links) или display-таблиц для доступа к переменным внешних областей видимости.

**Безрекурсивная реализация.** Каждая dfn-функция соответствует ровно одному лексическому контуру, глубина функции = длина цепочки в `r` до корня. Вычисляется итеративной fixpoint-идиомой `_←{z←d[i]+←ω≠z←r[ω]}⍣≡i`: стартуя с id всех функциональных узлов `i`, на каждой итерации инкрементируется счётчик глубины `d` для узлов, ещё не достигших корня (`ω≠z`), и `ω` заменяется на `r[ω]` — подъём на уровень вверх; итерация — до неподвижной точки (`⍣≡`). Результат `d` прореживается до вектора `f` — лексическая глубина только для строк `e` (уникальных связываний), default ¯1.

**Зачем это Co-dfns.** Вектор `f` — номер фрейма в лексическом стеке для каждого связывания/переменной; нужен, чтобы во время выполнения (или в 3.13) знать, на сколько уровней вверх по стеку фреймов подняться, чтобы найти нужное связывание.

## Recording Exported Names (3.12)

**Задача в обычном компиляторе.** Аналог сохранения таблицы публичных символов модуля (экспорт-секции). Поскольку лексическое разрешение (3.13) «потребляет» явные символические имена, заменяя их парами (frame, slot), информацию о том, какие имена видны извне (top-level bindings namespace), нужно сохранить заранее — иначе она будет безвозвратно потеряна.

**Безрекурсивная реализация.** Самый простой проход во всём компиляторе: одна строка `xn←n⌿⍨(t=1)∧k[r]=0` — маска «связывающий узел, чей ближайший объемлющий контур — функция верхнего namespace (`kind=0`)» применяется к `n` через Replicate.

**Зачем это Co-dfns.** Подготовка к 3.13: после разрешения имена как строки исчезают из дерева (заменяются числовыми frame/slot-парами), а экспортируемые top-level имена нужны позже — например, для внешнего доступа к пространству имён по имени функции/переменной.

## Lexical Resolution (3.13)

**Семантика dfns, которую нужно реализовать.** Функции допускают forward reference на связывания, объявленные ниже по тексту; выражения ссылаются на связывания и слева, и справа; имя может связываться повторно (переприсваивание — единственная форма `x←e` одновременно связывает и мутирует); операнды операторов резолвятся в точке вызова оператора, свободные ссылки внутри операнда — в точке вызова производных функций; свободные ссылки резолвятся в точке *вызова*, а не *определения* функции (в отличие от классических замыканий с лексическим захватом на момент определения); связывания удаляются по возврату из объемлющей dfn (безопасно — dfn не может вернуть функцию как first-class значение, значит не останется висячих ссылок). Видимость имён сравнима с Python (без first-class процедур), но с ВЧ-функциями и свободными ссылками. Тонкий случай: ссылка на имя *до* первого связывания этого имени в теле функции считается свободной ссылкой на внешний контур (в отличие от Python, где локальное связывание «затеняет» имя на всё тело, даже до присваивания). Чтобы это моделировать без явного порядка выполнения по узлам, автор вводит приём: каждая функция концептуально начинает с неявных статичных операторов вида `x←x` для каждого связывания, затеняющего внешнее одноимённое связывание — тем самым каждое имя внутри функции всегда резолвится к одному и тому же фрейму на всём протяжении тела.

**Цель прохода.** Разрешение сопоставляет каждой ссылке (и каждому связыванию) пару (frame, slot): для связываний — слот, который они мутируют в собственном фрейме; для ссылок на имена — фрейм и слот, где реально лежит нужное связывание (возможно, выше по лексическому стеку). Значения `f` и `s` из 3.10–3.11 уже дают это отображение для строк таблицы `e` (уникальных связываний); задача — распространить его на **все** узлы-ссылки (variable-узлы с обычными именами, не `α`/`ω`/`αα`/`ωω`).

**Безрекурсивная реализация — поиск с фиксированной точкой.** Строится `v` — id всех имён-ссылок, и `y` — объединённый список id ссылок и связываний (`v,b`), для которых ищется «текущая позиция поиска» `x` (изначально имя лежит в собственном контуре `n[y]`). Буфер `i` изначально заполнен «не найдено» (значение = число строк `e`) — индекс в объединённую таблицу `f`/`s`. Поисковая итерация: на каждом шаге по `ω` (текущая таблица «id + позиция поиска») вычисляется `z` — таблица на уровень выше (`r[I@0⊢ω]`, поднимая контур поиска для не-найденных ссылок), проверяется наличие пары (контур, имя) из `z` в отсортированной `e` (`e⍳⊂¨x I@1⊢z`); найденные заполняются в `i`. После каждой итерации таблица **фильтруется**, оставляя только ещё не найденные ссылки (`z/⍨c=i[1⌷z]`) — оптимизация против повторного логарифмического поиска для уже разрешённых имён. Цикл — до неподвижной точки (`⍣≡`), число итераций ограничено максимальной «лексической дистанцией» между ссылкой и связыванием (числом вложенных фреймов), на практике — глубиной вложенности функций в исходнике. Для имён поиск стартует в собственном контуре (`⍳≠x`), для связываний — на уровень выше: связывание, будучи неявным `x←x`, обязано резолвиться не в текущий (ещё не занятый) слот, а в связывание из объемлющей области, реализуя семантику «forward reference/shadow». После сходимости `i` содержит валидный индекс в `f`/`s` для каждого элемента `y`; итоговые `f`/`s` записываются обратно как колонки дерева, узлам, не являющимся ссылками/связываниями, присваивается ¯1.

**Сложность.** Доминирует поиск `e⍳⊂¨...`, полная сложность `O((≢rn)×⍥≠e)` (логарифмический критический путь на итерацию), число итераций фикспоинта ограничено максимальной лексической глубиной программы — на практике константно для типичного кода.

**Зачем это Co-dfns.** Кульминационный проход главы 3 — превращает синтаксическое дерево с текстовыми именами в исполняемую форму, где каждое обращение к переменной жёстко привязано к конкретной ячейке конкретного фрейма активации, без поиска имени по строке или обхода цепочки областей видимости в рантайме. Поскольку dfns не имеют полноценных замыканий (функция не переживает возврат из объемлющей функции как значение), достаточно доступа через стек фреймов (не через кучу с захватом переменных) — это радикально упрощает и семантику языка, и её параллельную, безрекурсивную реализацию на GPU.
