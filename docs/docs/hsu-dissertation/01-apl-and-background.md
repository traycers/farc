# 1. APL, Co-dfns и Nanopass (главы 1–2, стр. 1–46)

## 1.1. Тезис и заявленные вклады (Introduction)

Компилятор построен целиком через композицию data-parallel операторов над n-мерными прямоугольными массивами, используя APL как модель и нотацию, **без специализированных абстракций данных для деревьев**. Обычные идиомы array-программирования применяются напрямую как идиомы трансформации деревьев — никаких новых domain-specific техник, конструкций или языковой поддержки.

Заявленные вклады:

- array-модели программирования достаточно мощны для трансформаций дерева, ранее считавшихся сложными для параллелизации;
- выигрыш в runtime и памяти одновременно на CPU и GPU;
- устранение разрыва CPU↔GPU: дорогие анализы можно выполнять на GPU без перекладывания данных туда-сюда;
- масштабирование по размеру данных на обеих архитектурах;
- асимптотическая сложность вычисляется механически, почти без участия человека;
- ни одна из техник не является domain-specific — все примитивы переносимы в другие домены программирования.

Компилятор написан для языка **Co-dfns** — production-синтаксиса dfns интерпретатора Dyalog APL, лексически скопированного, динамически типизированного, с функциями высшего порядка, но без первоклассных процедур.

Ключевое сравнение — с **Nanopass framework** (Racket/Chez Scheme): компилятор Hsu значительно короче и проще семантически, не требуя тулинга/рантайма/библиотек/спецсинтаксиса, но сохраняет преимущества Nanopass по декомпозиции на маленькие проходы.

## 1.2. Array-модель данных (2.1.1)

APL моделирует **все данные как массив** = **shape (форма) + values (значения)**, значения упорядочены согласно форме. Все формы прямоугольны, значения — дискретные объекты (тоже массивы). Форма — упорядоченный набор неотрицательных целых:

- 0 измерений (точка) → **скаляр**, rank 0;
- 1 измерение → **вектор**;
- 2 измерения → **матрица**;
- 3+ измерений → куб / «noble arrays».

**Rank** = длина shape. Значения располагаются в **row-major order**. Форма сама — массив ранга 1.

**Индексация.** Индекс — вектор длины shape со значениями в `[0, n)`; пустой элемент индекса выбирает весь диапазон по измерению — так массив «режется» на под-массивы (**cells**; для матрицы **major cells** — строки-векторы).

**Depth (глубина)** — насколько глубоко вложен массив, до скалярных значений. Примитивный скаляр (число/символ) — depth 0. Формально: 0, если единственное значение массива — он сам; иначе `x = 1 + max(|depth| всех значений)`, результат `x` при согласованной глубине у всех значений, иначе `-x` (несогласованная глубина). Shape, rank и depth — три ортогональных понятия. Модель называют **«floating model»**: атомарные единицы сами считаются массивами ранга 0.

## 1.3. Синтаксис APL-выражений (2.1.2)

Упрощённая грамматика (стр. 14):

```
Atom     := literal | Index | ( Expression )
Index    := Atom [ Expression ; ... ]
Expr     := Atom | App | Binding
App      := Func Expression | Atom Func Expression
Func     := FnAtom | Func oper | Func oper FnAtom | Func [ Expr ]
Binding  := Name ← Expression | Name Func ← Expression
```

Два типа применения — **функции** и **операторы**, оба могут быть **монадическими** (один аргумент) или **диадическими** (два аргумента). Композиция значений и функций — **справа налево**; композиция функций через операторы — **слева направо**. Операторы принимают функции как операнды (обычно; иногда и значения).

Литералы: `1` — скаляр, `1 2 3` — вектор, `'abc'` — вектор символов. Индексация: `A[I]`, `M[I;J]`, `M[I;]` (все столбцы), `M[;]` (вся матрица). Присваивание — единый примитив `←`, включая множественное присваивание по индексам: `X[0 2 4 6]←¯5`.

Каждый примитив-символ кодирует обычно до двух операций (монадическую и диадическую), концептуально связанных: `÷` диадически — деление, монадически — обратное число.

**Scalar primitives** (сложение, умножение, deление, abs, равенство): базовая операция на скаляре единообразно «поднимается» (lifting) на массивы любой формы; монадически — форма результата = форма аргумента; диадически с равными формами — поэлементно; с разными формами — **scalar extension** (скаляр реплицируется под форму другого аргумента).

**Mixed primitives** — всё остальное, форма результата может отличаться от формы аргументов (пример — `ρ`, shape: монадически возвращает форму, диадически меняет форму — `4 5ρι20`). **Grade Up** (`⍋`) — перестановочный вектор сортировки, всегда возвращает вектор.

**Операторы** (второй порядок) не амбивалентны: каждый — либо монадический, либо диадический. Применённый к операнду(-ам), возвращает **derived function**. Пример: reduction (`/` — по последнему измерению, `⌿` — по первому) сворачивает по указанному измерению, устраняя его из результата.

## 1.5. Идиоматичный APL (2.1.4) — «8 паттернов и антипаттернов»

APL можно писать «как любой другой язык», но сообщество выработало концепцию **idiomatic APL** — стилистические идеалы (Eisenberg 1987, Perlis 1977): читаемость для опытных, краткость, скорость исполнения, платформонезависимость, агностицизм к размеру данных, надёжность, доменная масштабируемость. Идиоматичный код легче анализировать машине — компиляторы/интерпретаторы легче распознают паттерны и оптимизируют.

Восемь осей напряжения (Hsu 2017):

1. **Brevity over Verbosity** — краткость важнее многословности; production-код пишется не с оглядкой на новичков.
2. **Macro Perspectives over Micro Perspectives** — глобальные обходы/паттерны делаются синтаксически явными, детали низкого уровня скрываются.
3. **Transparency over Abstraction** — минимум библиотечных абстракций; «продвинутый» код парадоксально прозрачнее, использует больше «голого» APL.
4. **Idioms over Libraries** — вместо стандартной библиотеки — культура однострочных идиом (исторически публиковались книгами, не библиотеками).
5. **Data Encoding over Control Flow Embedding** — минимум control flow; логика кодируется через форму/тип массивов. Цитата М. Кромберга: «APL is read left to right and executed right to left».
6. **Structural Information over Nominal Information** — именование зарезервировано для важных/глобальных концепций; lexical scoping появился только в конце 1990-х; первоклассные процедуры так и не прижились.
7. **Implicit Semantics over Explicit Semantics** — язык максимально скрывает тип/форму синтаксически; reduction имеет неявный seed, в отличие от fold в Scheme.
8. **Syntax Design over Semantics** — синтаксическая красота ставится выше семантической стройности; классический пример — избегание явного base-case в рекурсии/выражении, даже ценой неожиданных результатов на «бесполезных» входах.

Дополнительно: «spiritually functional» код (эффекты — крупные, на верхнем уровне); **semantic density** (имена из домена задачи); избегание циклов/итераций в пользу bulk-операций над целыми массивами; избегание избыточной indirection.

Отдельно: интерпретируемый APL демонстрирует высокую производительность относительно полностью скомпилированного оптимизированного C-кода (Lochbaum 2018b, Whitney 2009); array/linear-algebra подход применяется и в graph processing (Kepner & Gilbert 2011), и в column-store БД (Whitney 2009).

**Модель памяти.** Почти все реализации APL хранят значения одним непрерывным (contiguous) регионом памяти в row-major порядке — доступ при исполнении идиоматичного кода почти всегда строго последовательный (самый быстрый паттерн на CPU/GPU), даже bulk-индексация со strided-доступом эффективнее произвольного доступа по указателям GC-heavy ADT-моделей. Ключевое следствие: **идиоматичный APL не требует сборки мусора вовсе** — достаточно stack-based модели живости, что особенно важно для allocation-heavy трансформаций деревьев.

## 1.7. Язык Co-dfns (2.2)

**dfns**-синтаксис (John Scholes, 1990-е) — анонимные функции, расширяющие APL-выражения синтаксисом error/conditional guards. Функция — пара `{ }` с statement'ами, исполняемыми слева направо, сверху вниз; разделители — перевод строки или `⋄`. Statement — `Expr`, `FnBind`, `Guard` или `Error Guard`.

- **Guard**: `тест : следствие` — тест должен быть булевым скаляром; если 1 — возвращается следствие; если 0 — переход к следующему statement.
- **Error Guard** (`::`): левая часть — вектор кодов ошибок для перехвата (0 = любая); барьер ошибок исполнения.
- Если последняя операция statement — binding, выполнение идёт дальше; иначе результат statement — значение функции.

Каждая dfns неявно связывает `α`/`ω` (левый/правый аргументы). Использование `αα`/`ωω` делает dfns **оператором**. `∇` связано со значением самой функции (рекурсия), `∇∇` — со значением оператора. Единственное дополнение к обычному APL во входных данных компилятора — top-level namespace через `:Namespace ... :EndNamespace` (синтаксис Dyalog).

dfns лексически вложены, свободные переменные разрешаются по правилам lexical scoping (детали разрешения — [§3.13](03-compiler-passes.md#lexical-resolution-313)). Сам компилятор не эксплуатирует эти правила для собственной реализации, но обязан корректно их обрабатывать во входных программах.

## 1.8. Nanopass Framework (2.3)

**Nanopass** (Andy Keep, 2013) — фреймворк для проектирования компиляторов вокруг множества маленьких проходов, связанных data-flow образом; каждый проход — небольшая трансформация структуры дерева. Хотя компилятор Hsu синтаксически не похож на Nanopass, фреймворк **значительно повлиял на архитектуру** компилятора (маленькие концептуальные операции, последовательно работающие над AST) и служит **бенчмарком для сравнения**.

Две основные абстракции Nanopass поверх Scheme/Racket:

1. Синтаксис спецификации **промежуточных представлений** — обёртка над record-типами, с бонусом описывать IR как diff относительно уже определённого представления.
2. **Pattern matching** — трансформация одного IR («language») в другое через клаузы паттерн-матчинга; тривиальные (identity) случаи диспетчеризуются автоматически, обеспечивается автоматический recursive descent (catamorphism).

Дополнительно — проверки целостности данных на этапе компиляции (частичные преимущества статической типизации внутри untyped Scheme/Racket).

**Важный результат Andy Keep**: производительность Nanopass оказалась достаточно хороша, чтобы не серьёзно повлиять на производительность компилятора Chez Scheme — множество маленьких проходов с синтаксической поддержкой не обязательно требует пропорциональной деградации производительности относительно monolithic-дизайна.

Преимущества Nanopass, которые он унаследует концептуально (не синтаксически) в компиляторе Hsu: лёгкость работы с проходами и общим дизайном; маленькие проходы легче понимать и отлаживать; декаплинг проходов упрощает их взаимодействие вместо перемешивания эффектов в крупных проходах.
