# Бинарный формат TOC

## 1. Назначение документа

Документ описывает секцию «TOC» фконтейнера (`03-storage-format.md` §8.2): оглавление, позволяющее находить и обходить узлы дерева (`05-data-format.md`) без чтения секции «Данные» целиком, и вести поиск по отдельным атрибутам узлов (время, вид кадра и т.п.) без обхода дерева.

TOC состоит из двух частей:
- **Базовый TOC** — оглавление по элементам дерева, индексируемое напрямую по `id` (см. §2). Уже описан в общем виде в `05-data-format.md` §4; здесь фиксируется его размещение внутри секции TOC.
- **Производные индексы** — SoA-структуры поверх базового TOC для поиска по конкретным атрибутам (§3–§4).

Документ **не описывает**:
- Общий формат элемента дерева (`type`, `parent`, `sibling`, `size`, `value`) — см. `05-data-format.md`.
- Доменные типы узлов и их семантику (video/audio-дерево) — см. `07-media-tree.md`.
- Расположение секции TOC внутри фблока, `toc_size`, CRC — см. `03-storage-format.md` §8.2, §9.

## 2. Базовый TOC

Массив элементов той же формы, что и в «Данных», но вместо `value` — `offset` (`05-data-format.md` §4):

| Поле        | Тип    | Значение |
|-------------|--------|----------|
| `type`      | uint16 | Как в «Данных». |
| `parent`    | uint32 | Как в «Данных». |
| `sibling`   | uint32 | Как в «Данных». |
| `size`      | uint32 | Размер `value` в «Данных», в байтах. |
| `offset`    | uint64 | Смещение `value` от начала секции «Данные». |

Размер элемента фиксирован (**22 байта**), поэтому базовый TOC индексируется напрямую: запись узла `id` находится по смещению `id × 22` от начала базового TOC. Обход дерева (`parent`/`sibling`) и пропуск узлов с нераспознанным `type` (`05-data-format.md`, «Пропуск неизвестного типа») выполняются по базовому TOC без чтения «Данных».

## 3. Производные индексы

Базовый TOC даёт доступ по `id` и обход дерева, но не даёт быстрый поиск по значению атрибута («кадр около момента T», «ближайший ключевой кадр») — для этого пришлось бы линейно сканировать базовый TOC. Производные индексы — дополнительные SoA-таблицы, которые решают именно эту задачу.

### 3.1. Форма

Один индекс — набор параллельных массивов одинаковой длины (`M` строк):

| Колонка | Тип | Значение |
|---------|-----|----------|
| `node_id` | uint32 | `id` узла, к которому относится строка (обычно — родителя атрибутного узла, см. пример в §4). |
| `value` | зависит от индекса | Значение атрибута (например, время для `frame_time_index`, §4). |
| companion-колонки (0..N) | зависит от индекса | Данные для фильтрации без обхода дерева (например, `channel_id`, `stream_id`). |

Массив-колонки допускают SIMD-скан (сравнение диапазона времени, поиск по каналу и т.п.) — в этом и есть причина SoA здесь, в отличие от дерева и базового TOC, которые остаются AoS (`05-data-format.md` §2).

### 3.2. Членство и сквозной характер

Строка индекса существует для узла тогда и только тогда, когда его `type` входит в множество типов, участвующих в этом индексе. Поскольку типы уникальны по семантике и ветке (`07-media-tree.md` §3 — `frame_kind_video` ≠ `frame_codec_audio`, `frame_data` ≠ `data`), участие определяется однозначно самим `type`, без дополнительного признака scope.

Индекс — **один на весь фконтейнер** (не по каналу, не по потоку, не по ветке video/audio): строки разных каналов/потоков идут в одном массиве вперемешку. Если нужна фильтрация по каналу/потоку — это companion-колонка той же длины, а не отдельный экземпляр индекса.

### 3.3. Построение

Индексы не заполняются потоками-писателями конкурентно вместе с деревом — SoA небезопасна для параллельной записи в несколько массивов сразу (`05-data-format.md` §2, то же рассуждение, что и для дерева). Построение разделено на два этапа:

1. **Во время записи фконтейнера.** На каждый узел, создаваемый писателем, — атомарный инкремент счётчика `(type, индекс)`, в который узел попадает. Счётчики дают точный итоговый размер каждого индекса **до** его фактической постройки. Это позволяет на лету проверять, что базовый TOC + все производные индексы поместятся в оставшееся место фблока (`03-storage-format.md` §8.3, максимальный размер фконтейнера); если нет — операция записи, приводящая к превышению, отклоняется.
2. **При финализации** (переход фблока `in_progress` → `ready`). Единственный процесс проходит по дереву последовательно (как читатель) и строит сами массивы индексов за один проход — аналогично тому, как Storage единолично пишет каталог фблока (ADR-005). Конкурентная запись дерева к этому моменту уже завершена.

## 4. Пример: индекс времени кадров (`frame_time_index`)

Участвующий тип — `frame_time` (единственный тип, несущий время кадра, `07-media-tree.md` §5).

| Колонка | Тип | Значение |
|---------|-----|----------|
| `node_id` | uint32 | `id` узла `frame` — родителя данного `frame_time` (не самого `frame_time`), чтобы от найденной строки сразу перейти к `frame_data`/`frame_kind_video`/`frame_codec_audio`. |
| `time` | uint64 | `value` узла `frame_time` (копия — сам индекс читается без обращения к дереву). |
| `channel_id` | uint16 | Компаньон-колонка: номер канала (`07-media-tree.md` §4), для фильтрации «кадры около времени T в канале N» без обхода `parent` до `channel`. |
| `stream_id` | uint16 | Компаньон-колонка: номер потока, аналогично `channel_id`. |

Аналогичного вида индекс для `frame_kind_video` («быстрый поиск ближайшего ключевого кадра») отличается только колонкой `value` (маркер `I`/`P` вместо времени) и множеством участвующих типов.

## 5. Заголовок секции TOC

`toc_size` (эпилог, `03-storage-format.md` §9) отвечает только за одно: найти начало секции TOC от конца фблока (`fblock_size - 20 - toc_size`). Он не описывает, что внутри секции — базовый TOC и производные индексы (§2–§4) физически идут один за другим внутри уже найденной секции, и их границы нужно фиксировать отдельно, **внутри** самой секции TOC, а не полем эпилога.

Для этого секция TOC начинается с небольшого фиксированного заголовка:

| Поле | Тип | Значение |
|------|-----|----------|
| `base_toc_count` | uint32 | Число элементов базового TOC (= число узлов дерева). Размер базового TOC — `base_toc_count × 22` байт (§2), идёт сразу после заголовка. |
| `index_count` | uint16 | Число производных индексов, следующих за базовым TOC. |
| `index_dir[]` | `index_count` записей | Директория индексов, см. ниже. |

Одна запись `index_dir[]`:

| Поле | Тип | Значение |
|------|-----|----------|
| `index_tag` | uint16 | Идентификатор индекса (например, `frame_time_index`). |
| `row_count` | uint32 | Число строк индекса (посчитано счётчиками при записи, §3.3). |
| `offset` | uint64 | Смещение начала индекса от начала секции TOC. |

Размер и раскладка строки индекса (набор колонок, их типы) определяются по `index_tag` — так же, как `type` определяет форму `value` для узла дерева (`07-media-tree.md`); сам заголовок TOC этого не описывает.

Порядок секции TOC целиком: `[заголовок TOC][базовый TOC][индекс 1][индекс 2]...`.

## 6. Открытые вопросы

- Точный список нужных индексов сверх `frame_time_index` (по каналу/потоку отдельно от companion-колонок, по ключевым кадрам, другие) — зависит от паттернов чтения, не все определены.
- Тип `value` для нечисловых атрибутов (например, маркер `I`/`P` у `frame_kind_video`, код кодека у `frame_codec_audio`) — фиксированный enum или иначе, согласовать с `07-media-tree.md` §6.
- Ширина счётчиков `(type, индекс)` при конкурентной записи (атомарные uint32/uint64, переполнение) — вопрос реализации WritePool, не формата; связано с открытым вопросом о выделении `id`/`sibling` в `05-data-format.md` §6.
