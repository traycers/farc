# Бинарный формат TOC

## 1. Назначение документа

Документ описывает секцию «TOC» фконтейнера (`03-storage-format.md` §8.2): оглавление, позволяющее находить и обходить узлы дерева (`05-data-format.md`) без чтения секции «Данные» целиком, и вести поиск по отдельным атрибутам узлов (время, вид кадра и т.п.) без обхода дерева.

TOC состоит из двух частей:
- **Базовый TOC** — оглавление по элементам дерева, индексируемое напрямую по `id` (см. §2). Общая форма элемента и набор `type` уже описаны в `05-data-format.md` §3–§3.1; здесь фиксируется его размещение внутри секции TOC.
- **Производные индексы** — SoA-структуры поверх базового TOC: отфильтрованные по `role` индексы атрибутов (§3.1–§3.3, §4) и полные колоночные проекции полей самого базового TOC без фильтрации (§3.4).

Документ **не описывает**:
- Общий формат элемента дерева (`type`, `role`, `parent`, `sibling`, `size`, `value`) — см. `05-data-format.md`.
- Доменные типы узлов и их семантику (video/audio-дерево) — см. `07-media-tree.md`.
- Расположение секции TOC внутри фблока, `toc_size`, CRC — см. `03-storage-format.md` §8.2, §9.

## 2. Базовый TOC

Массив элементов той же формы, что и в «Данных», но вместо `value` — `offset` (`05-data-format.md` §3):

| Поле        | Размер  | Значение |
|-------------|---------|----------|
| `type`      | 1 байт  | Как в «Данных». |
| `role`      | 2 байта | Как в «Данных». |
| `parent`    | 4 байта | Как в «Данных». |
| `sibling`   | 4 байта | Как в «Данных». |
| `size`      | 4 байта | Размер `value` в «Данных», в байтах. |
| `offset`    | 8 байт  | Смещение `value` от начала секции «Данные». |

Размер элемента фиксирован (**23 байта**), поэтому базовый TOC индексируется напрямую: запись узла `id` находится по смещению `id × 23` от начала базового TOC. Как и в «Данных» (`05-data-format.md` §3), `id` не хранится явно в записи — он равен позиции записи в базовом TOC. Обход дерева (`parent`/`sibling`) и пропуск узлов с нераспознанной `role` (`05-data-format.md`, «Пропуск неизвестной роли») выполняются по базовому TOC без чтения «Данных».

## 3. Производные индексы

Базовый TOC даёт доступ по `id` и обход дерева, но не даёт быстрый поиск по значению атрибута («кадр около момента T», «ближайший ключевой кадр») — для этого пришлось бы линейно сканировать базовый TOC. Производные индексы — дополнительные SoA-таблицы, которые решают именно эту задачу.

### 3.1. Форма

Один индекс — набор параллельных массивов одинаковой длины (`M` строк):

| Колонка | Тип | Значение |
|---------|-----|----------|
| `node_id` | uint32 | `id` узла, к которому относится строка (обычно — родителя атрибутного узла, см. пример в §4). |
| `value` | зависит от индекса | Значение атрибута (например, время для `frame_time_index`, §4). |
| companion-колонки (0..N) | зависит от индекса | Данные для фильтрации без обхода дерева (например, `channel_id`, `stream_id`). |

Массив-колонки допускают SIMD-скан (сравнение диапазона времени, поиск по каналу и т.п.) — в этом и есть причина SoA здесь, в отличие от дерева и базового TOC, которые остаются AoS (`05-data-format.md` §2).

### 3.2. Членство и сквозной характер

Строка индекса существует для узла тогда и только тогда, когда его `role` входит в множество ролей, участвующих в этом индексе. Поскольку роли уникальны по семантике и ветке (`07-media-tree.md` §3 — `frame_kind_video` ≠ `frame_codec_audio`, `frame_data` ≠ `data`), участие определяется однозначно самой `role`, без дополнительного признака scope. `type` (физическое представление, §3.1) для этого не используется — несколько ролей могут делить один и тот же `type` (например, `frame_time` и `params_version` — обе `timestamp`), и это не создаёт неоднозначности членства.

Индекс — **один на весь фконтейнер** (не по каналу, не по потоку, не по ветке video/audio): строки разных каналов/потоков идут в одном массиве вперемешку. Если нужна фильтрация по каналу/потоку — это companion-колонка той же длины, а не отдельный экземпляр индекса.

### 3.3. Построение

Индексы не заполняются потоками-писателями конкурентно вместе с деревом — SoA небезопасна для параллельной записи в несколько массивов сразу (`05-data-format.md` §2, то же рассуждение, что и для дерева). Построение разделено на два этапа:

1. **Во время записи фконтейнера.** На каждый узел, создаваемый писателем, — атомарный инкремент счётчика `(role, индекс)`, в который узел попадает. Счётчики дают точный итоговый размер каждого индекса **до** его фактической постройки. Это позволяет на лету проверять, что базовый TOC + все производные индексы поместятся в оставшееся место фблока (`03-storage-format.md` §8.3, максимальный размер фконтейнера); если нет — операция записи, приводящая к превышению, отклоняется.
2. **При финализации** (переход фблока `in_progress` → `ready`). Единственный процесс проходит по дереву последовательно (как читатель) и строит сами массивы индексов за один проход — аналогично тому, как Storage единолично пишет каталог фблока (ADR-005). Конкурентная запись дерева к этому моменту уже завершена.

### 3.4. Полные колоночные проекции базового TOC

В отличие от индексов §3.1–§3.3 (которые существуют только для узлов с нужной `role`, §3.2), полная колоночная проекция покрывает **все** `base_toc_count` узлов без фильтрации — это тот же базовый TOC (§2), только в форме SoA вместо AoS, для читателей, которым нужен SIMD-скан по одному из полей базового TOC (`type`, `role`, `parent`, `sibling`, `size`, `offset`), а не построчный обход.

Полная проекция — до шести независимых массивов, по одному на поле базового TOC:

| Массив | Размер элемента | Длина |
|---|---|---|
| `type[]` | 1 байт | `base_toc_count` |
| `role[]` | 2 байта | `base_toc_count` |
| `parent[]` | 4 байта | `base_toc_count` |
| `sibling[]` | 4 байта | `base_toc_count` |
| `size[]` | 4 байта | `base_toc_count` |
| `offset[]` | 8 байт | `base_toc_count` |

Как и в базовом TOC, `id` узла не хранится отдельным массивом — он равен позиции в каждом из шести массивов (`type[id]`, `role[id]`, ...). Колонка `node_id` (§3.1) здесь не нужна: фильтрации нет, и позиция уже однозначно определяет узел.

Каждый нужный столбец регистрируется как собственная запись `index_dir[]` (§5) со своим `index_tag` (например, `toc_col_type`, `toc_col_role`, `toc_col_parent`, `toc_col_sibling`, `toc_col_size`, `toc_col_offset`) и `row_count = base_toc_count`. Сам базовый TOC (§2) при этом не меняется — читатель, не знающий этих тегов, просто не видит соответствующие записи директории и продолжает работать с базовым TOC как раньше; расширение целиком укладывается в существующий механизм `index_dir[]`, без отдельной версии формата.

Построение проще, чем у обычных производных индексов (§3.3): счётчик на этапе записи не нужен — итоговый размер уже известен и равен `base_toc_count` из заголовка TOC. При финализации единственный процесс идёт по базовому TOC последовательно и для узла `id` пишет `type[id]`, `role[id]`, `parent[id]`, `sibling[id]`, `size[id]`, `offset[id]` — прямая запись по индексу без бегущего курсора (в отличие от §3.3, где позиция строки в отфильтрованном индексе не совпадает с `id`). Запись по разным слотам независима, поэтому проход можно выполнять параллельно несколькими потоками без координации между ними.

## 4. Пример: индекс времени кадров (`frame_time_index`)

Участвующая роль — `frame_time` (единственная роль, несущая время кадра, `07-media-tree.md` §5).

| Колонка | Тип | Значение |
|---------|-----|----------|
| `node_id` | uint32 | `id` узла `frame` — родителя данного `frame_time` (не самого `frame_time`), чтобы от найденной строки сразу перейти к `frame_data`/`frame_kind_video`/`frame_codec_audio`. |
| `time` | timestamp | `value` узла `frame_time` (копия — сам индекс читается без обращения к дереву; физически 8 байт, как и в дереве, `05-data-format.md` §3.1). |
| `channel_id` | uint16 | Компаньон-колонка: номер канала (`07-media-tree.md` §4), для фильтрации «кадры около времени T в канале N» без обхода `parent` до `channel`. |
| `stream_id` | uint16 | Компаньон-колонка: номер потока, аналогично `channel_id`. |

Аналогичного вида индекс для `frame_kind_video` («быстрый поиск ближайшего ключевого кадра») отличается только колонкой `value` (маркер `I`/`P` вместо времени) и множеством участвующих ролей.

## 5. Заголовок секции TOC

`toc_size` (эпилог, `03-storage-format.md` §9) отвечает только за одно: найти начало секции TOC от конца фблока (`fblock_size - 20 - toc_size`). Он не описывает, что внутри секции — базовый TOC и производные индексы (§2–§4) физически идут один за другим внутри уже найденной секции, и их границы нужно фиксировать отдельно, **внутри** самой секции TOC, а не полем эпилога.

Для этого секция TOC начинается с небольшого фиксированного заголовка:

| Поле | Тип | Значение |
|------|-----|----------|
| `base_toc_count` | uint32 | Число элементов базового TOC (= число узлов дерева). Размер базового TOC — `base_toc_count × 23` байт (§2), идёт сразу после заголовка. |
| `index_count` | uint16 | Число производных индексов, следующих за базовым TOC. |
| `index_dir[]` | `index_count` записей | Директория индексов, см. ниже. |

Одна запись `index_dir[]`:

| Поле | Тип | Значение |
|------|-----|----------|
| `index_tag` | uint16 | Идентификатор индекса (например, `frame_time_index`). |
| `row_count` | uint32 | Число строк индекса (посчитано счётчиками при записи, §3.3). |
| `offset` | uint64 | Смещение начала индекса от начала секции TOC. |

Размер и раскладка строки индекса (набор колонок, их типы) определяются по `index_tag` — так же, как `role` определяет форму `value` для узла дерева (`07-media-tree.md`); сам заголовок TOC этого не описывает.

Порядок секции TOC целиком: `[заголовок TOC][базовый TOC][индекс 1][индекс 2]...`.

## 6. Открытые вопросы

- Точный список нужных индексов сверх `frame_time_index` (по каналу/потоку отдельно от companion-колонок, по ключевым кадрам, другие) — зависит от паттернов чтения, не все определены.
- Какие из шести колонок §3.4 реально нужны читателям (все сразу, или только те, по которым делают SIMD-скан, например `role`/`size`) — избыточные колонки увеличивают размер TOC без пользы.
- Тип `value` для нечисловых атрибутов (например, маркер `I`/`P` у `frame_kind_video`, код кодека у `frame_codec_audio`) — фиксированный enum или иначе, согласовать с `07-media-tree.md` §6.
- Ширина счётчиков `(role, индекс)` при конкурентной записи (атомарные uint32/uint64, переполнение) — вопрос реализации WritePool, не формата; связано с открытым вопросом о выделении `id`/`sibling` в `05-data-format.md` §6.
