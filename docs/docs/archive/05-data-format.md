# Бинарный формат данных

## 1. Назначение документа

Документ описывает структуру, в которой потребитель организует данные внутри секции «Контент» фконтейнера (см. `03-storage-format.md` §8) — дерево на базе массивов (array-based tree). Тот же набор смысловых полей узла (без самого `value`, но с добавлениями) переиспользуется в TOC, в другой физической раскладке и другом порядке узлов — см. `06-toc-format.md`.

Документ **не описывает**:
- Формат самого TOC как оглавления (расположение, ссылки на данные) — см. `06-toc-format.md`.
- Физическое разбиение данных при записи/чтении на уровне Storage — см. `03-storage-format.md`, `04-storage-operations.md` §7.3–7.4.
- Публичный API заполнения дерева потребителем — см. `09-fcontainer-write-path.md`. Механизм, которым несколько потоков-производителей конкурентно размещают узлы внутри одного фконтейнера (выделение `id`/смещений, продолжение цепочки `sibling`) — внутренняя реализация заполнителя, не специфицируется нигде в документации.

## 2. Почему дерево на базе массивов

Fcontainer пишется один раз и не изменяется (write-once, read-many после перехода fblock в `ready`). Это режим, для которого деревья на базе массивов (parent vector), предложенные Aaron W. Hsu (co-dfns, мир APL), хорошо подходят: узел, зная id родителя, дописывается в структуру независимо от остальных, без указателей и перебалансировки.

Важное отличие от каталога фблока: каталог пишет один процесс (Storage — единственный писатель на диск, ADR-005), а в фконтейнер параллельно добавляют узлы много потоков-производителей. Это делает **Structure of Arrays непригодной** для дерева фконтейнера: добавление узла в SoA требует согласованной записи сразу в несколько массивов (`parent`, `size`, `value`, ...), и читатель может увидеть узел, у которого одни массивы уже обновлены, а другие ещё нет. Вместо этого используется **массив элементов** (Array of Structs) — добавление узла становится одной операцией записи в одно место.

Преимущества для farc:
- **Атомарное добавление узла.** Один узел — один элемент массива. Поток резервирует место (id узла + смещение под `value`) и пишет элемент целиком, не координируясь с другими писателями за пределами резервирования места. Публичный API, которым потребитель добавляет данные — `09-fcontainer-write-path.md`; само резервирование места — внутренняя реализация заполнителя.
- **Самодостаточность.** Дерево не содержит внешних ссылок — читается и валидируется независимо, как и весь фконтейнер (требование самодостаточности, `00-requirements.md`).
- **Задел под TOC.** TOC переиспользует то же понятие узла в SoA-раскладке (`06-toc-format.md` §4); по нему можно обходить дерево, искать по значению атрибута и по структуре поддерева, не читая данные целиком.

Hsu сжимает полную матрицу связей узлов дерева (path / node coordinate matrix) в пару векторов — `parent` и `sibling` — и держит их как **structure of vectors** (SoA), потому что весь AST уже целиком в памяти к моменту построения: компилятор работает пакетно, дерево не меняется во время самого построения этой пары. Farc использует ту же пару полей `parent`/`sibling` для той же задачи, но в форме **vector of structs** (AoS) — по причине, изложенной выше: писать нужно немедленно, по мере поступления данных от параллельных потоков-производителей, а не после того как дерево уже известно целиком. Structure of vectors для этой же пары появляется позже и отдельно — в TOC (`06-toc-format.md` §5), который строится на этапе финализации фконтейнера, когда дерево уже неизменно и выполняется то же условие, что и у Hsu.

## 3. Представление дерева

Дерево — это последовательность элементов, каждому при создании присваивается **id** — монотонно возрастающий номер (позиция элемента в массиве). Id не хранится явно в элементе — он равен индексу элемента.

Элемент в секции «Контент»:

Ширина этих полей фиксирована для любого элемента и не связана с закрытым набором `type` из §3.1 — это ширина самих мета-полей, а не выбор физического представления `value` (совпадение имён вроде "uint32" в обоих местах — просто совпадение единиц счёта, не одна и та же вещь):

| Поле      | Размер  | Значение                                                                                                                                                     |
| --------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `type`    | 1 байт  | Физическое представление `value` — закрытый, не растущий вместе с доменом набор примитивов формата (полный список — §3.1): как механически разобрать байты `value`, независимо от их смысла (`07-media-tree.md` §3). |
| `role`    | 2 байта | Семантика узла — какое понятие домена он несёт (`channel`, `frame_time`, `frame_kind`, ...); определяет ветку и смысл `value`. Открытый, растущий вместе с доменом словарь (`07-media-tree.md` §3), в отличие от `type`. |
| `parent`  | 4 байта | Id родительского узла. Корень — элемент, у которого `parent == свой id` (сам себе родитель).                                                                 |
| `sibling` | 4 байта | Id предыдущего (левого) соседа — узла, созданного перед этим под тем же родителем. Если это первый ребёнок родителя — `sibling == свой id` (сам себе сосед). |
| `size`    | 8 байт | Размер `value` в байтах.                                                                                                                                     |
| `value`   | `size` байт (переменный) | Сами данные узла, длиной `size`; физическая интерпретация зависит от `type` (§3.1).                                                        |

Текстовые данные — отдельный физический тип `string` (§3.1), а не `bytes`: кодировка UTF-8, без BOM (общее соглашение формата, `03-storage-format.md` §2).

### 3.1. Набор типов (`type`)

`type` — закрытый набор физических представлений `value`: как механически разобрать байты `value`, независимо от их смысла. В отличие от `role` (открытый, растущий вместе с доменом словарь), набор `type` один на весь формат и не специфичен для домена.

| `type`     | Размер `value`         | Интерпретация |
| ---------- | ----------------------- | ------------- |
| `void`     | 0 байт                  | `value` отсутствует; узел — контейнер или тег ветки (например, `channels`, `video`, `configs`, `07-media-tree.md` §3). `size` = 0. |
| `uint8`    | 1 байт                  | Целое без знака, 1 байт. Компактный физический носитель для перечислимых/флаговых значений (например, `frame_kind`, `codec`, `07-media-tree.md` §3) — как в EBML, где нет отдельного enum-типа: набор допустимых значений и их смысл для конкретного узла определяет `role`, `type=uint8` фиксирует только размер. |
| `uint32`   | 4 байта                 | Целое без знака, little-endian (`03-storage-format.md` §2). |
| `uint64`   | 8 байт                  | Целое без знака, little-endian. Для доменных значений, не являющихся временем (для времени — `timestamp`/`duration` ниже). |
| `int32`    | 4 байта                 | Целое со знаком, little-endian, дополнительный код. |
| `int64`    | 8 байт                  | Целое со знаком, little-endian, дополнительный код. |
| `float32`  | 4 байта                 | Число с плавающей точкой, IEEE 754 одинарная точность (binary32), little-endian. |
| `float64`  | 8 байт                  | Число с плавающей точкой, IEEE 754 двойная точность (binary64), little-endian. |
| `timestamp` | 8 байт                | Точка во времени: целое без знака, little-endian, Unix-наносекунды (общее соглашение формата, `03-storage-format.md` §2). Физически как `uint64`, но семантика фиксирована самим типом, а не `role`: любой узел `timestamp` — абсолютный момент времени, независимо от роли (`frame_time`, `config`, `07-media-tree.md` §5). |
| `duration` | 8 байт                 | Длительность/протяжённость: целое без знака, little-endian, наносекунды. Не привязана к эпохе — в отличие от `timestamp`, это разница/интервал, а не точка. Физически идентична `timestamp`, но семантически не взаимозаменяема с ней (складывать `timestamp` c `timestamp` бессмысленно, `timestamp + duration` — осмысленно). |
| `string`   | `size` байт (переменный) | Текст, кодировка UTF-8, без BOM (`03-storage-format.md` §2). `size` — длина в байтах закодированной строки, не в символах/рунах. Гарантия валидности UTF-8 — на стороне писателя; формат её не проверяет и не хранит терминирующий ноль. |
| `bytes`    | `size` байт (переменный) | Непрозрачная последовательность байт без предполагаемой кодировки — интерпретация целиком за `role` (например, сырые байты кадра у `frame_data`, `07-media-tree.md` §5). Если данные — текст, используется `string`, а не `bytes`. |

Из всего набора выше в дереве сегодня реально используются `void`, `uint8`, `uint32`, `float64`, `timestamp`, `bytes` (`07-media-tree.md` §3). `uint64`, `string`, `int32`, `int64`, `float32`, `duration` зарезервированы заранее — ни одна `role` в них пока не нуждается (для `string` это уже отмечено выше). Набор закрыт в том смысле, что не растёт вместе с доменом произвольно — новые `role` переиспользуют существующий `type`, если он механически подходит (пример — `config`/`frame_time`, оба `timestamp`, §3 ниже).

Дети узла `P` находятся сканированием — элементы, у которых `parent == P` (дерево Aaron Hsu, parent vector, §2). При сканировании в порядке `id` они уже идут в порядке создания, поэтому отдельное поле `order` не нужно. Глубина (`depth`) тоже не хранится отдельно — при необходимости считается проходом по цепочке `parent`.

Элемент не несёт универсального поля времени: время (как и любые другие типизированные данные) — это `value` конкретной роли узла, которой оно нужно (например, `frame_time`, `07-media-tree.md` §5), а не свойство узла вообще. Быстрый поиск по времени без чтения «Контента» и без обхода дерева обеспечивает поиск по значению в TOC (`06-toc-format.md` §7), а не базовый элемент.

Элемент переменной длины (`value` разного размера у разных узлов) — массив в «Контенте» является **последовательностью**, а не индексируемым по `id * sizeof(элемент)` массивом.

**Инвариант порядка:** и `parent`, и `sibling` узла всегда ссылаются на уже существующий id, то есть `parent <= id` и `sibling <= id` (кроме самоссылок). Родитель и предыдущий сосед физически создаются раньше своего ребёнка/следующего соседа. Это позволяет потокам создавать новый узел, зная только id уже существующих родителя и (если есть) предыдущего соседа, и восстанавливать дерево последовательным сканированием «Контента» от начала, если TOC утрачен или повреждён.

**Пропуск неизвестной роли:** `role` не обязана быть известна читателю. `type` — закрытый набор примитивов формата, не растущий вместе с доменом (§3 выше), поэтому даже для узла с нераспознанной `role` читатель, зная только `type`, умеет механически разобрать или скопировать `value`. Поскольку `size` (в «Контенте») и `value_or_offset`+`size` (в TOC, `06-toc-format.md` §4) есть у каждого элемента независимо от `role`, узел с нераспознанной `role` пропускается целиком — как при последовательном сканировании «Контента», так и по TOC, без знания его внутреннего устройства. Это позволяет расширять дерево новыми понятиями домена (в том числе новыми детьми существующих узлов), не ломая код, написанный до их появления.

## 5. Граница с физической записью

Storage пишет и верифицирует данные порциями фиксированного размера (единица write-verify — `04-storage-operations.md` §7.3), и это разбиение в иерархию дерева не входит. Payload одного узла может занимать часть такой порции, ровно одну порцию или несколько подряд — это вопрос физической записи, не структуры дерева. Дерево не должно знать об этих границах, а код физической записи не должен знать о форме дерева.
