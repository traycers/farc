# Бинарный формат данных

## 1. Назначение документа

Документ описывает структуру, в которой потребитель организует данные внутри секции «Данные» фконтейнера (см. `03-storage-format.md` §8) — дерево на базе массивов (array-based tree). Эта же структура, без самих данных, используется для TOC (`06-toc-format.md`).

Документ **не описывает**:
- Формат самого TOC как оглавления (расположение, ссылки на данные) — см. `06-toc-format.md`.
- Физическое разбиение данных на фчанки при записи/чтении — см. `03-storage-format.md`, `04-storage-operations.md`.

## 2. Почему дерево на базе массивов

Fcontainer пишется один раз и не изменяется (write-once, read-many после перехода fblock в `ready`). Это режим, для которого деревья на базе массивов (parent vector), предложенные Aaron W. Hsu (co-dfns, мир APL), хорошо подходят: узел, зная id родителя, дописывается в структуру независимо от остальных, без указателей и перебалансировки.

Важное отличие от каталога фблока: каталог пишет один процесс (Storage — единственный писатель на диск, ADR-005), а в фконтейнер параллельно добавляют узлы много потоков-производителей. Это делает **Structure of Arrays непригодной** для дерева фконтейнера: добавление узла в SoA требует согласованной записи сразу в несколько массивов (`parent`, `size`, `value`, ...), и читатель может увидеть узел, у которого одни массивы уже обновлены, а другие ещё нет. Вместо этого используется **массив элементов** (Array of Structs) — добавление узла становится одной операцией записи в одно место.

Преимущества для farc:
- **Атомарное добавление узла.** Один узел — один элемент массива. Поток резервирует место (id узла + смещение под `value`) и пишет элемент целиком, не координируясь с другими писателями за пределами резервирования места.
- **Самодостаточность.** Дерево не содержит внешних ссылок — читается и валидируется независимо, как и весь фконтейнер (требование самодостаточности, `00-requirements.md`).
- **Задел под индексы.** TOC — тот же массив элементов без `value` (см. §4); по нему можно обходить дерево и строить производные индексы, не читая данные целиком.

## 3. Представление дерева

Дерево — это последовательность элементов, каждому при создании присваивается **id** — монотонно возрастающий номер (позиция элемента в массиве). Id не хранится явно в элементе — он равен индексу элемента.

Элемент в секции «Данные»:

| Поле      | Тип     | Значение |
|-----------|---------|----------|
| `type`      | uint16  | Тег вида узла (какие данные несёт узел). |
| `parent`    | uint32  | Id родительского узла. Корень — элемент, у которого `parent == свой id` (сам себе родитель). |
| `sibling`   | uint32  | Id предыдущего (левого) соседа — узла, созданного перед этим под тем же родителем. Если это первый ребёнок родителя — `sibling == свой id` (сам себе сосед). |
| `timestamp` | uint64  | Unix-время в наносекундах (соглашение всего бинарного формата, `03-storage-format.md` §2). Имеет смысл только для отдельных типов узлов (например, кадров, см. `07-media-tree.md`) — `0`, если для типа узла время не определено. |
| `size`      | uint32  | Размер `value` в байтах. |
| `value`     | bytes   | Сами данные узла, длиной `size`. |

Поле `sibling` образует обратный связный список детей одного родителя: чтобы перечислить всех детей узла `P`, нужно знать id последнего добавленного ребёнка `P` и идти по `sibling` назад, пока не встретится самоссылка. Список отдаёт детей в порядке, обратном созданию — при необходимости прямого порядка потребитель переворачивает список при чтении. Порядковый номер (`order`) и глубина (`depth`) отдельно не хранятся: явный порядок среди детей не нужен, а глубина при необходимости считается проходом по цепочке `parent`.

`timestamp` — часть базового элемента, а не `value`, специально: TOC (§4) хранит его наравне с остальными полями формы, поэтому поиск узла по времени (например, «кадр около момента T») выполняется по TOC без чтения «Данных».

Элемент переменной длины (`value` разного размера у разных узлов) — массив в «Данных» является **последовательностью**, а не индексируемым по `id * sizeof(элемент)` массивом.

**Инвариант порядка:** и `parent`, и `sibling` узла всегда ссылаются на уже существующий id, то есть `parent <= id` и `sibling <= id` (кроме самоссылок). Родитель и предыдущий сосед физически создаются раньше своего ребёнка/следующего соседа. Это позволяет потокам создавать новый узел, зная только id уже существующих родителя и (если есть) предыдущего соседа, и восстанавливать дерево последовательным сканированием «Данных» от начала, если TOC утрачен или повреждён.

## 4. TOC — тот же элемент без данных

TOC (`06-toc-format.md`) — массив элементов той же формы, но вместо `value` хранится ссылка на него:

| Поле      | Тип     | Значение |
|-----------|---------|----------|
| `type`      | uint16  | Как в «Данных». |
| `parent`    | uint32  | Как в «Данных». |
| `sibling`   | uint32  | Как в «Данных». |
| `timestamp` | uint64  | Как в «Данных». |
| `size`      | uint32  | Размер `value` в «Данных», в байтах. |
| `offset`    | uint64  | Смещение `value` от начала секции «Данные». |

В отличие от «Данных», элемент TOC — **фиксированного размера**, поэтому TOC индексируется напрямую по id (`toc[id]`), в том числе для обхода дерева по `parent`/`sibling`, без сканирования. Собственно данные (`value`) в TOC не дублируются.

## 5. Граница с фчанком

Фчанк (`00-requirements.md`, `03-storage-format.md`) — единица записи-верификации на уровне Storage (physical write/read granularity), и в иерархию дерева не входит. Payload одного узла может занимать часть фчанка, целый фчанк или несколько фчанков подряд — это вопрос физической записи, не структуры дерева. Дерево не должно знать о границах фчанков, а код работы с фчанками не должен знать о форме дерева.

## 6. Открытые вопросы

- Конкретный состав `value` и значения `type` (какие виды узлов существуют, какие данные несёт каждый) — зависит от предметной области (видео/аудио потоки) и будет определён отдельно.
- Механизм выделения id и смещения под `value`, а также отслеживание «последнего ребёнка» родителя для заполнения `sibling` при конкурентной записи (например, атомарные счётчики/CAS) — вопрос реализации, не формата; будет описан при проектировании WritePool/API для потребителя.
