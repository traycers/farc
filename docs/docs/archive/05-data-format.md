# Бинарный формат данных

## 1. Назначение документа

Документ описывает структуру, в которой потребитель организует данные внутри секции «Данные» фконтейнера (см. `03-storage-format.md` §8) — дерево на базе массивов (array-based tree). Эта же структура, без самих данных, используется для TOC (`06-toc-format.md`).

Документ **не описывает**:
- Формат самого TOC как оглавления (расположение, ссылки на данные) — см. `06-toc-format.md`.
- Физическое разбиение данных на фчанки при записи/чтении — см. `03-storage-format.md`, `04-storage-operations.md`.

## 2. Почему дерево на базе массивов

Fcontainer пишется один раз и не изменяется (write-once, read-many после перехода fblock в `ready`). Это ровно тот режим, для которого деревья на базе массивов (parent vector), предложенные Aaron W. Hsu (co-dfns, мир APL), эффективны: структура строится целиком за один проход и затем только сканируется, без точечных вставок/удалений и перебалансировки указателей.

Преимущества для farc:
- **Без указателей.** Дерево — это несколько параллельных массивов (Structure of Arrays), что совпадает со стилем, уже принятым для каталога фблока (ADR-009).
- **Самодостаточность.** Дерево не содержит внешних ссылок — читается и валидируется независимо, как и весь фконтейнер (требование самодостаточности, `00-requirements.md`).
- **Расширяемость.** Форма дерева (иерархия) и содержимое узлов (payload) — разные массивы. Добавление нового вида узла или атрибута — это новый параллельный массив, не изменение существующих.
- **Задел под индексы.** Поскольку TOC — та же форма без данных (см. §4), по ней можно строить производные индексы (например, по времени или диапазону), не читая данные целиком.

## 3. Представление дерева

Дерево — это N узлов, пронумерованных `0..N-1`, и три параллельных массива фиксированной длины `N`:

| Массив   | Тип      | Значение |
|----------|----------|----------|
| `parent` | uint32   | Индекс родителя узла. Корень — узел, у которого `parent[i] == i` (сам себе родитель). |
| `order`  | uint32   | Порядковый номер узла среди детей одного родителя — обеспечивает детерминированный порядок обхода при сериализации/чтении. |
| `depth`  | uint32   | Глубина узла относительно ближайшего корня (у корня `depth == 0`). Позволяет фильтровать/группировать узлы по уровню без обхода дерева. |

Порядок узлов в массивах не обязан совпадать с порядком обхода дерева — обход при необходимости строится по `parent`/`order`, массивы хранятся в порядке, удобном для записи (как правило — порядке создания узла).

Payload (полезная нагрузка) узла хранится отдельно от формы — см. §4.

## 4. Разделение формы и содержимого

Дерево описывает **форму** (`parent`, `order`, `depth`). Содержимое узла — payload — хранится в отдельном массиве (или наборе массивов) той же длины `N`, где `payload[i]` соответствует узлу `i`.

- **В секции «Данные» фконтейнера** дерево хранится с payload: форма + фактические данные узла.
- **В TOC** (`06-toc-format.md`) хранится та же форма (`parent`, `order`, `depth`) той же длины `N`, но вместо payload — лёгкий дескриптор ссылки на данные (например, смещение и размер участка в секции «Данные»). Само содержимое узла в TOC не дублируется.

Это разделение позволяет читать и обходить структуру (TOC), не читая данные, и наоборот — работать с данными, не заботясь о форме, если она уже известна.

## 5. Граница с фчанком

Фчанк (`00-requirements.md`, `03-storage-format.md`) — единица записи-верификации на уровне Storage (physical write/read granularity), и в иерархию дерева не входит. Payload одного узла может занимать часть фчанка, целый фчанк или несколько фчанков подряд — это вопрос физической записи, не структуры дерева. Дерево не должно знать о границах фчанков, а код работы с фчанками не должен знать о форме дерева.

## 6. Открытые вопросы

- Конкретный состав payload узла (какие данные потребитель хранит в дереве) — зависит от предметной области (видео/аудио потоки) и будет определён отдельно.
- Точные типы и размеры полей дескриптора для TOC (offset/length и др.) — см. `06-toc-format.md`.
