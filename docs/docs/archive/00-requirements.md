# Требования к системе хранения данных

## 1. Бизнес-контекст

Система предназначена для хранения видео, звука и других данных архива. Данные потребителя упакованы в **фконтейнеры** — самодостаточные единицы, которые могут (вне нашей ответственности) передаваться по сети или обрабатываться независимо друг от друга. Каждый фконтейнер хранится в **фблоке** — физическом слоте хранилища фиксированного размера (ADR-013).

**Ключевая идея:** фконтейнер содержит данные архива, актуальные за промежуток времени; фблок обеспечивает его физическое хранение. Система обеспечивает хранение этих данных в течение заданного срока (N дней).

## 2. Терминология

| Термин                                 | Описание                                                                                                                                                                                                |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Фблок (fblock)**                     | Физический слот хранилища фиксированного размера: пролог, каталог, контрольные суммы, область данных, эпилог. Вмещает один фконтейнер (ADR-013).                                                        |
| **Фконтейнер (fcontainer)**            | Структура и данные, заполняемые потребителем (секции «Данные» и TOC). Самодостаточен: интерпретируется без других фконтейнеров и без метаданных хранилища.                                              |
| **Фчанк (fchunk)**                     | Часть фблока, единица операций записи с верификацией (write-verify). Внутренняя деталь реализации.                                                                                                      |
| **Порция чтения**                      | Небольшой фрагмент данных, читаемый за один системный вызов. Размер выбирается меньше фчанка, чтобы не блокировать запись (см. 4.4). Внутренняя деталь реализации.                                      |
| **Битый фчанк**                        | Фчанк с физическим дефектом, запись в который невозможна.                                                                                                                                               |
| **Битый фблок**                        | Фблок, содержащий хотя бы один битый фчанк. Считается непригодным.                                                                                                                                      |
| **Защищённый фблок**                   | Фблок, помеченный потребителем как read-only. Защищает лежащий в нём фконтейнер от перезаписи.                                                                                                          |
| **Потребитель**                        | Процесс, использующий библиотеку. Заполняет фконтейнеры, запрашивает чтение, работает с метриками и уведомлениями. Один потребитель может работать с несколькими независимыми хранилищами одновременно. |
| **Хранилище (storage)**                | Место хранения данных: файл или блочное устройство.                                                                                                                                                     |
| **Время начала актуальности (begin)**  | Timestamp первого по времени фрагмента данных, помещённого в фконтейнер. Задаётся потребителем при заполнении.                                                                                          |
| **Время окончания актуальности (end)** | Timestamp последнего по времени фрагмента данных, помещённого в фконтейнер. Задаётся потребителем при заполнении.                                                                                       |
| **Срок хранения (retention)**          | Минимальный срок в днях, в течение которого фблок с фконтейнером не может быть перезаписан, отсчитывается от `end` фконтейнера. Глобальный параметр Storage.                                            |
| **Каталог (catalog)**                  | Необязательная копия заголовков всех фблоков Storage на быстром диске (SSD), ускоряющая старт (ADR-007).                                                                                                |
| **Номер канала**                       | Целое число (не более 65535), которым потребитель идентифицирует источник данных внутри фконтейнера. Список номеров не фиксирован потребителем заранее (см. ADR-014).                                   |

## 3. Требования к фконтейнеру как самодостаточной единице

### 3.1. Независимость
- Фконтейнер содержит всю информацию, необходимую для интерпретации своих данных.
- Для чтения фконтейнера не требуются метаданные других фконтейнеров или глобальный заголовок хранилища.

### 3.2. Идентификация

| Идентификатор        | Назначение                                           | Кто использует        |
| -------------------- | ---------------------------------------------------- | --------------------- |
| **Индекс фблока**    | Физический адрес для циклической записи (0..N-1)     | Внутренняя реализация |
| **UUID фконтейнера** | Логический идентификатор данных, уникальный навсегда | Потребитель           |

- UUID генерируется библиотекой **до записи** фконтейнера в хранилище.
- UUID хранится в индексах хранилища.
- Формат: UUIDv4 (128 бит).

### 3.3. Инварианты
- Размер фблока фиксирован при инициализации хранилища и не меняется в течение всей его жизни, включая операции расширения и сужения.
- Индекс фблока лежит в диапазоне `0..N-1`, где `N` — текущее количество фблоков в хранилище.
- UUID каждого записанного фконтейнера уникален в пределах хранилища и не переиспользуется.
- Максимальный размер фконтейнера определяется геометрией хранилища и не опускается ниже доли `min_container_share` от размера фблока (ADR-013).

## 4. Функциональные требования

### 4.1. Инициализация хранилища

Инициализация выполняется лениво (ADR-006) и занимает секунды независимо от размера хранилища: записывается только нулевой фблок с параметрами хранилища, остальные фблоки остаются `uninitialized` и инициализируются по мере записи данных. Алгоритм — `04-storage-operations.md` §3.

Повторная инициализация запрещена без явного подтверждения. После инициализации хранилище готово к записи и чтению.

### 4.2. Запись фблока

1. **Выбор места:** система движется по кругу, выбирая первый доступный для записи фблок в следующем порядке приоритета:
   - `uninitialized` — сначала заполняем неинициализированные области диска (ADR-006).
   - `ready`, удовлетворяющий условиям доступности (см. 4.5): не `protected`, истёк срок хранения от `end`.

2. Если доступный для записи фблок не найден — авария «нет свободного места».

3. Запись выполняется пофчанково с проверкой (write-verify, честность обратного чтения — ADR-010). При обнаружении битого фчанка весь фблок помечается `bad`, запись переносится на следующий подходящий фблок.

4. После успешной записи потребитель получает уведомление с UUID. Механизм подтверждения на диске — ADR-002, `02-storage.md` §2.2.

**Важно:** частичная запись недопустима — фблок либо записан целиком, либо не записан.

### 4.3. Чтение фблока

- Поддержка частичного чтения: любой непрерывный диапазон внутри фконтейнера.
- Чтение не привязано к размеру фчанка.
- Внутренне одно логическое чтение разбивается на несколько порций чтения, чтобы не блокировать запись на длительное время (см. 4.4).

### 4.4. Приоритеты операций

- Запись имеет абсолютный приоритет над чтением.
- Чтение выполняется в паузах между записями.
- Между порциями чтения система проверяет очередь записи и при наличии готового к записи фблока прерывает чтение до завершения записи.

### 4.5. Управление состоянием фблока

У фблока четыре базовых состояния (`uninitialized`, `in_progress`, `ready`, `bad`) и один ортогональный модификатор `protected` (применим только к `ready`); полное описание состояний и переходов — `02-storage.md` §2.4/§5.

**Гарантированный срок хранения** — фблок в состоянии `ready` гарантированно не перезаписывается в течение `retention.days` дней после времени окончания актуальности (`end`) лежащего в нём фконтейнера. Срок хранения — глобальный параметр Storage, изменяемый потребителем без перезаписи существующих фблоков.

**Доступным для записи** является фблок в состоянии `uninitialized` (приоритет 1) либо `ready`, не `protected`, с истёкшим сроком хранения (приоритет 2). Поле `begin` на доступность не влияет — это бизнес-информация для Reader; `end` определяет точку отсчёта срока хранения.

Уменьшение `retention.days` потребителем может сделать ранее заблокированные фблоки доступными для записи раньше срока — это допустимо.

### 4.6. Защита от записи

- Потребитель может пометить фблок флагом `protected`. Применимо только к фблокам в состоянии `ready`.
- Флаг хранится в индексах и переживает перезапуск.
- Флаг не снимается автоматически — ни по истечении времени актуальности, ни при каких-либо других условиях. Только явным действием потребителя.
- Библиотека не ограничивает количество `protected` фблоков. Контроль разумной доли — ответственность потребителя. Метрика доли `protected` доступна через API.

### 4.7. Очередь записи и backpressure

- В памяти поддерживается пул буферов фиксированного размера.
- Готовые к записи фконтейнеры (в буферах) ставятся в очередь FIFO.
- При переполнении очереди библиотека сигнализирует потребителю о перегрузке (backpressure).
- Библиотека **не отбрасывает** данные и **не анализирует** их важность — только сигнализирует.
- Потребитель сам решает, какие данные перестать записывать в фконтейнеры.

### 4.8. API заполнения фконтейнера

Цикл работы потребителя при записи:

1. **Получение буфера:** потребитель запрашивает буфер для заполнения. Ответ содержит буфер, его максимальный размер (ADR-013) и текущий статус загрузки системы (норма, предупреждение, перегрузка, нет буферов).

2. **Заполнение буфера:** потребитель записывает данные фконтейнера в буфер произвольным образом, не превышая максимальный размер.

3. **Передача заполненного буфера:** потребитель возвращает буфер с метаданными (время начала и окончания актуальности). Буфер ставится в очередь записи.

Решение о том, какой фблок будет перезаписан, принимается библиотекой в момент выполнения записи из очереди (см. 4.2), а не в момент получения буфера.

### 4.9. Уведомления

Все уведомления асинхронны и содержат UUID соответствующего фконтейнера.

| Уведомление                         | Момент отправки                                                       |
| ----------------------------------- | --------------------------------------------------------------------- |
| **О начале записи фконтейнера**     | Перед первым обращением к диску для записи данных фконтейнера         |
| **О завершении записи фконтейнера** | После успешной записи и верификации всех фчанков                      |
| **Об удалении фконтейнера**         | Перед перезаписью фблока новыми данными — теряется прежний фконтейнер |

Уведомление о начале записи позволяет потребителю зарезервировать UUID до того, как данные окажутся на диске.

**При переносе фблока** (см. 8.2, сужение со стратегией «перенос») UUID переносимого фконтейнера сохраняется, поэтому уведомления о его удалении и о новом фконтейнере **не отправляются**. Уведомление «об удалении» отправляется только для фконтейнера, который перезаписывается в оставшейся зоне (если в целевом фблоке лежал чужой фконтейнер с непустым UUID).

### 4.10. Консистентность при сбоях

- При сбое питания фблок может остаться в незавершённом состоянии (часть фчанков записана, часть — нет).
- Незавершённость определяется по признакам целостности, заложенным в формат фблока (контрольные суммы, маркеры конца записи — конкретика в документе формата хранилища).
- В фоне система сканирует хранилище и помечает обнаруженные незавершённые фблоки как битые.
- Восстановление данных из частично записанных и битых фблоков выполняется отдельной CLI-утилитой (см. раздел 7).

### 4.11. Мониторинг состояния диска

- Отслеживание доли битых фблоков от общего числа фблоков в хранилище.
- Порог: 5% (настраивается при инициализации).
- При превышении порога — алерт потребителю, работа продолжается.
- Отдельно отслеживается доля защищённых фблоков (без жёсткого порога, для информирования потребителя).

### 4.12. Поиск по каналу и времени

- Один фконтейнер может содержать данные нескольких каналов одновременно, вплоть до постоянной записи всех каналов сразу — обычный, а не крайний режим эксплуатации.
- Потребитель может запросить у Storage список кандидатов (UUID и физических индексов) по номеру канала и диапазону времени `[t1, t2]`, не зная заранее конкретный UUID (ADR-014).
- Поиск по каналу сокращает число кандидатов, но не заменяет чтение TOC: точное подтверждение присутствия и диапазонов данных канала — по-прежнему обязанность потребителя через чтение TOC конкретного фконтейнера (см. 4.3).
- Ёмкость под одновременно используемые номера каналов ограничена и фиксируется при инициализации хранилища (`max_channels`, ADR-014); превышение — авария, аналогичная «нет свободного места» (см. 4.2).

## 5. Нефункциональные требования

### 5.1. Масштабируемость
- Хранилища до 20 ТБ и более.
- Количество фблоков: до нескольких миллионов.
- Поддержка расширения и сужения хранилища без перезаписи существующих фблоков (см. раздел 8).

### 5.2. Производительность
- Инициализация хранилища — секунды, независимо от размера диска (ADR-006).
- Старт Storage — секунды при наличии каталога на SSD (ADR-007). Без каталога — fallback на полное сканирование (минуты–часы в зависимости от размера).
- Запись с проверкой упирается в скорость диска.
- Частичное чтение без лишних операций ввода-вывода.
- Размер порции чтения выбирается так, чтобы задержка прерывания чтения для освобождения диска под запись не превышала разумного значения (конкретика — в документе операций).

### 5.3. Надёжность
- Контрольные суммы для критических данных (заголовок фблока, индексы, каждый фчанк).
- Копии критических метаданных (индексов) распределены по хранилищу (см. ADR-002).
- Внешний каталог — необязательная копия заголовков на быстром диске (ADR-007). При потере каталога данные хранилища не теряются, каталог пересоздаётся из хранилища.

### 5.4. Переносимость
- Фблок, созданный на одной платформе, читается на другой.
- Формат не зависит от файловой системы.
- Порядок байтов и выравнивание фиксируются в формате хранилища.

### 5.5. Версионирование формата
- Формат хранилища имеет номер версии, записанный в каждом фблоке.
- Библиотека отказывается работать с хранилищем несовместимой мажорной версии.
- Изменения формата в рамках одной мажорной версии обратно совместимы на чтение.

## 6. Модель конкурентности

- К одному хранилищу в каждый момент времени обращается **ровно один экземпляр библиотеки**. Защита от одновременного открытия несколькими процессами реализуется через файловую блокировку или эксклюзивное открытие устройства.
- Внутри одного экземпляра: один логический писатель и несколько одновременных читателей; порядок между ними определяется приоритетом из 4.4.
- Один потребитель может работать с несколькими независимыми хранилищами одновременно, каждое — через свой экземпляр библиотеки.
- Восстановительная CLI-утилита (раздел 7) работает только с хранилищами, которые не открыты библиотекой.

### 6.1. Топология развёртывания

Целевое развёртывание — **один процесс farcd на сервер**, а не по процессу на каждый диск/хранилище. Экземпляры библиотеки из 6 живут внутри одного процесса — по одному на каждое локальное хранилище, но без отдельного процесса на диск. Причина — экономия CPU: избыточно запускать N процессов ради N дисков одного сервера, когда все они могут разделять один процесс без потери изоляции между хранилищами (изоляция обеспечивается на уровне экземпляра библиотеки/файловой блокировки, а не процесса ОС).

## 7. Восстановление данных (требования к CLI-утилите)

- Чтение всего хранилища, включая повреждённые области.
- Извлечение фконтейнеров по UUID.
- Возможность полного или частичного восстановления фконтейнера.
- Работа в режиме read-only относительно исходного хранилища.

## 8. Расширение и сужение хранилища

### 8.1. Расширение
- Расширение выполняется добавлением новых фблоков в конец хранилища.
- Размер фблока не меняется.
- Существующие фблоки не перемещаются и не перезаписываются.
- Индексы новых фблоков становятся актуальны после подтверждения операции расширения.

### 8.2. Сужение

Сужение — **редкая и долгая** операция, выполняется потребителем осознанно. Размер фблока не меняется.

В зоне сужения (последние `M` фблоков хранилища) могут оказаться фблоки любого состояния, включая актуальные и `protected`. farcd не отбрасывает такие данные молча — потребитель явно выбирает одну из стратегий:

| Стратегия                  | Поведение                                                                                                                                                                                                                                                            |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Перенос (copy)**         | Фконтейнеры из актуальных и `protected` фблоков зоны сужения копируются в доступные для записи фблоки оставшейся зоны с сохранением UUID, времён актуальности и флага `protected`. Если подходящего места недостаточно — операция отменяется без изменений на диске. |
| **Отбрасывание (discard)** | Все фконтейнеры зоны сужения теряются независимо от состояния фблока.                                                                                                                                                                                                |

Перед запуском farcd предоставляет потребителю сводку: сколько актуальных и `protected` фблоков попадает в зону сужения и сколько доступных для записи фблоков есть в оставшейся зоне. Потребитель решает, какую стратегию применить.

Операция должна быть возобновляемой после сбоя питания: промежуточное состояние сохраняется на диске, при следующем открытии хранилища farcd обнаруживает незавершённое сужение и предлагает продолжить или откатить. Детали — в документе операций (`04-storage-operations.md`).

## 9. Импорт

- Импорт — копирование фблоков из одного хранилища в другое.
- Предусловие: размер фблока у источника и приёмника совпадает.
- Импортируются только фблоки в состоянии `ready` у источника. Фблоки в состояниях `in_progress` или `bad` пропускаются.
- По умолчанию UUID импортированных фконтейнеров сохраняются.

### 9.1. Коллизии UUID

Коллизия UUID маловероятна (UUIDv4 — 128 бит случайности), но возможна при импорте из разных источников. Обработка:

| Условие                                                         | Действие                                                                                                        |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| UUID совпадает, время начала и окончания актуальности совпадают | Пропустить — это тот же фконтейнер, уже импортированный ранее.                                                  |
| UUID совпадает, время актуальности отличается                   | Импортировать как новый фконтейнер с новым сгенерированным UUID. Исходный UUID в приёмнике остаётся нетронутым. |

Детали протокола импорта — в документе операций (`04-storage-operations.md`).
