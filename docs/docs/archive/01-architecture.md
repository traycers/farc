# Архитектура системы хранения Farc

## 0. Обзор системы

**Farc** — система циклической записи видеопотоков с N источников на M независимых хранилищ.

- **Источники:** RTSP (опционально файлы для тестирования).
- **Выдача данных:** HTTP API (в перспективе RTSP).
- **Конфигурация:** Статический файл (JSON/YAML) на первое время.

### Системный контекст

```mermaid

    subgraph Ingest["Источник данных"]
        Writer["Запись:<br/>заполняет буферы фконтейнеров<br/>(begin/end, каналы)"]
    end

    subgraph Downstream["Нисходящие сервисы"]
        VideoGW["Video Gateway<br/>(готовит и отдаёт видео<br/>web-клиентам)"]
        Timeline["Timeline Service<br/>(хранит timeline в БД)"]
    end

    WebClient["Web-клиент"]

    Mon["Мониторинг<br/>Prometheus/VictoriaMetrics"]
    Config["Файл конфигурации"]

    Farc(["farcd / Archive"])
    Recovery["CLI восстановления<br/>(отдельная утилита)"]

    Disk[("Диск / блочное устройство<br/>N хранилищ")]
    SSD[("SSD-каталог<br/>опционально, ADR-007")]

    Writer -->|буфер + метаданные| Farc
    Farc -->|события + TOC фконтейнера,<br/>единый WebSocket push (EventPushServer), ADR-015| VideoGW
    VideoGW -->|данные для построения timeline| Timeline
    WebClient -->|timeline канала за (t1, t2)| Timeline
    WebClient -->|запрос видео| VideoGW
    VideoGW -->|чтение: офсеты (ADR-004)<br/>или (канал, время) — fallback, ADR-016| Farc
    Farc -->|/metrics| Mon
    Config -.->|при старте| Farc
    Operator -->|расширение, сужение,<br/>импорт — через Archive| Farc

    Farc --> Disk
    Farc --> SSD
    Recovery --> Disk
```

Ключевая граница: **CLI восстановления** — отдельная от Archive система. Она работает только с хранилищами, которые не открыты процессом farcd (раздел 4), и не проходит через тот же путь, что обычные операции расширения/сужения/импорта.

Другая граница: **Video Gateway** и **Timeline Service** — отдельные от farcd процессы, работающие через его внешний API (события и TOC по WebSocket-push, чтение). Их внутреннее устройство (как Video Gateway отдаёт видео web-клиенту — HLS, свой протокол по WebSocket и т.п.) не входит в архитектуру farc; farc фиксирует только свою сторону контракта.

### Топология развёртывания

Один процесс farcd обслуживает **все локальные хранилища сервера** (§6.1 `00-requirements.md`) — не по процессу на диск. Экономия CPU: N дисков одного сервера не требуют N процессов, каждое хранилище — это отдельный экземпляр библиотеки внутри одного процесса farcd.

### Режимы работы хранилища
1. **Циклическая запись** (перезапись по истечении срока актуальности).
2. **Запись до заполнения** (остановка записи с алертом при исчерпании места).

### Инициализация
Хранилище инициализируется однократно и лениво (ADR-006): записывается только нулевой фблок с параметрами хранилища и начальным снимком индексов. Инициализация занимает секунды независимо от размера диска; остальные фблоки остаются `uninitialized` и заполняются по мере записи.

### Модель данных: Фблок
Хранилище разбивается на последовательность **фблоков** фиксированного размера. Остаток в конце хранилища, меньший размера фблока, игнорируется. Фиксированный размер позволяет вычислять смещение любого фблока арифметически (`index * block_size`).

## 1. Структура хранилища и метаданные

### 1.1. Заголовок фблока
Заголовок, содержащий UUID и временные метки актуальности фконтейнера, а также флаги состояния фблока, располагается **внутри фблока**. Это упрощает расчет смещений и поддержку операций расширения/сужения хранилища.

### 1.2. Индексы хранилища
Индексы (статусы фблоков: свободен/битый/защищен) хранятся исключительно **внутри хранилища** для гарантии восстанавливаемости без внешних зависимостей.

**Расположение индексов:** В начале каждого фблока (распределенный вариант).
Это обеспечивает равномерный износ диска (отсутствие "горячих" зон частой перезаписи в начале или конце тома) и консистентность данных.

## 2. Подсистема записи (Write Path)

### 2.1. Компоненты и поток данных
1. **Recorder:** владеет пулом свободных буферов и очередью готовых к физической записи буферов (FIFO); заполняет фконтейнер данными, по его заполнении формирует TOC.
2. **IndexManager:** хранит индексы фблоков (свободен/битый/защищён, §1.2) и выбирает индекс для очередной записи.
3. **StorageEngine:** монопольный владелец доступа к диску (либо пишет, либо читает).

### 2.2. Алгоритм физической записи
- **Выбор позиции:** Циклический поиск первого доступного для записи фблока в порядке приоритета (ADR-006):
    1. `uninitialized` — сначала заполняются неинициализированные области диска.
    2. `ready`: не битый, не защищённый, с истекшим сроком хранения.
- **Процесс:**
    1. Запись выполняется небольшими проверяемыми порциями, не дожидаясь закрытия фконтейнера потребителем: очередная порция пишется по достижении заданного размера или по таймауту — что раньше (ADR-017).
    2. **Write-Verify:** после записи каждой порции выполняется её чтение и побитовое сравнение.
    3. При несовпадении — повторная запись (до N попыток).
    4. При фатальном сбое записи — весь фблок помечается **битым**, запись переносится на следующий подходящий блок.

Пошаговый алгоритм физической записи, включая единицу write-verify, — `04-storage-operations.md` §7.3–7.4.

### 2.3. Обратное давление (Backpressure)
При заполнении очереди готовых к записи буферов Recorder получает сигнал перегрузки. Система не отбрасывает данные самостоятельно.

### 2.4. Уведомления
Локальные события (перед перезаписью — удаление прежнего фконтейнера по UUID; после успешной записи — завершение с UUID нового) и TOC нового фконтейнера рассылаются наружу одним и тем же WebSocket-каналом (ADR-015): подписчик (например, Video Gateway) при подключении указывает, что ему нужно — компактные события, TOC целиком, либо оба. Получение TOC вместе с событием завершения экономит подписчику отдельный запрос на чтение TOC (3.2) для типового случая, когда он и так заинтересован в каждом новом фконтейнере.

## 3. Подсистема чтения (Read Path)

### 3.1. Механика чтения
1. **Reader:** обслуживает запросы на чтение, управляя собственным пулом буферов, чтобы не выделять память на каждый запрос.
2. **Группировка запросов:** Запросы к одному фблоку группируются в очереди чтения для минимизации IOPS.
3. **Приоритет:** Операции записи прерывают операции чтения (StorageEngine). Чтение выполняется в паузах записи.

### 3.2. API Чтения данных
Внешний API принимает запрос на диапазон данных (канал + время). Есть два режима, отличающиеся тем, знает ли потребитель смещения нужных данных заранее.

**Основной режим — потребитель уже знает смещения** (обычно потому, что уже разобрал TOC этого фконтейнера, например из push, 2.4):
1. UUID целевого фконтейнера определяется одним из двух способов: потребитель знает его заранее (своя внешняя БД), либо запрашивает у farcd список кандидатов по `(канал, t1, t2)` через регистр каналов (ADR-014) — маска сокращает кандидатов, но не заменяет проверку TOC.
2. Чтение выполняется в несколько этапов (ADR-004): StorageEngine читает индексы (TOC) фблока; потребитель по ним определяет смещения и размеры нужных данных; StorageEngine читает только запрошенные части.
3. Потребитель формирует из прочитанных частей ответ клиенту (видео/аудио).

**Fallback-режим — потребитель смещений не знает** (ADR-016): потребитель передаёт только `(fblock id/UUID, канал, t1, t2)`. farcd сам читает TOC фконтейнера, резолвит нужные узлы через поиск канала и скан по времени внутри диапазона его поддерева (`06-toc-format.md` §6–§8), вычисляет смещения и возвращает данные за один запрос. Используется, когда потребитель не получал или не обработал TOC этого фконтейнера заранее (не подписан на push 2.4, пропустил push из-за разрыва WebSocket-соединения и т.п.); не заменяет основной режим, а дополняет его.

Выдача фблока целиком по HTTP (ADR-003) — отдельный способ доставки данных внешнему клиенту для случаев, когда нужен весь фконтейнер (экспорт, кэширующий прокси), а не выбранный диапазон; сосуществует с частичным чтением выше, см. ADR-003 «Соотношение с ADR-004».

## 4. Консистентность и восстановление
- **Сбои питания:** Фблоки с незавершенной записью обнаруживаются фоновой проверкой и помечаются битыми.
- **Восстановление:** Вынесено в отдельную CLI-утилиту, способную сканировать сырое устройство и извлекать фблоки по известным сигнатурам.
