# Заполнение фконтейнера: конкурентная сборка дерева

## 1. Назначение документа

Документ описывает **механизм**, которым несколько потоков-производителей конкурентно добавляют узлы в дерево одного ещё заполняемого фконтейнера (`05-data-format.md` §2), — то есть *как* дерево строится в памяти, а не *что* в итоге лежит на диске. Формат (`05-data-format.md` §3) фиксирует только конечные инварианты (`id` — позиция элемента; `parent`/`sibling` всегда ссылаются на уже существующий `id`) — какой конкретно алгоритм привёл к этому результату, реального читателя не касается.

Документ **не описывает**:
- Сам бинарный формат элемента и закрытый набор `type` — см. `05-data-format.md` §3, §3.1.
- Доменные роли дерева (`channel`, `frame`, ...) — см. `07-media-tree.md`.
- Работу с буфером фконтейнера целиком как единицей WritePool/WriteQueue Storage (`01-architecture.md` §2.1, `00-requirements.md` §4.7–4.8) — это соседний, более верхний уровень: то, что здесь описано, происходит **внутри** одного такого буфера, пока он не поставлен в очередь на физическую запись.

## 2. Проблема

`05-data-format.md` §2 обосновывает выбор Array of Structs именно тем, что в один фконтейнер параллельно добавляют узлы много потоков-производителей. Это оставляет два места, требующие координации между потоками:

1. **Выделение `id` и смещения под `value`.** `id` узла — это позиция элемента (`05-data-format.md` §3); смещение `value` — следующий свободный байт в «Данных». Два потока, одновременно решившие "я — следующий узел", не должны получить один и тот же `id`/пересекающееся смещение.
2. **Продолжение цепочки `sibling`.** Новый узел должен знать, кто был последним ребёнком его родителя *прямо перед его появлением* — иначе два потока, одновременно добавляющие детей одному родителю, могут оба сослаться на одного и того же прежнего последнего ребёнка, и цепочка порвётся.

Раньше это было открытым вопросом (`05-data-format.md` §6): решение — ниже.

## 3. Идея решения: единственный владелец сборки

Вместо синхронизации потоков-производителей друг с другом (атомарные счётчики, CAS-циклы) — единственный компонент, ниже называемый **сборщиком** (Assembler; конкретное имя/API — вопрос проектирования WritePool), монопольно владеет всем разделяемым состоянием:

- `next_id` — счётчик следующего свободного `id`.
- `next_offset` — курсор записи в «Данные» под `value`.
- `last_child[P]` — для каждого уже существующего родителя `P` — `id` его текущего последнего ребёнка.

Поскольку сборщик один, все три — обычные последовательные переменные, без атомарных операций. Это тот же архитектурный паттерн, что уже применяется к `StorageEngine` — единственному владельцу записи на диск (ADR-005) — только уровнем выше: единственный владелец сборки дерева в памяти, а не единственный владелец диска.

## 4. Что готовят потоки-производители

Поток не пишет напрямую в общий массив узлов. Вместо этого он независимо, без какой-либо синхронизации с другими потоками, готовит **фрагмент** — самодостаточный набор новых узлов (целое поддерево или плоский список, например несколько кадров одного потока данных подряд).

Внутри фрагмента узлы пронумерованы **локально, начиная с 0** (порядок в списке, который строит поток). Для каждого узла `parent` и `sibling` — это либо:
- **локальная ссылка** — число `0..N-1`, указывающее на другой узел этого же фрагмента;
- **внешняя ссылка** — специальный маркер (например, зарезервированное значение sentinel, раз локальные номера фрагмента заведомо малы), означающий "мой настоящий `parent`/`sibling` — не внутри этого фрагмента, а в уже существующей части дерева".

Вместе с фрагментом поток передаёт единственный внешний ориентир — `anchor`: реальный (глобальный) `id` родителя, к которому присоединяется фрагмент. Это уже существующий узел, `id` которого потоку известен заранее (например, `id` контейнера `frames`, созданного до начала параллельной записи кадров, `07-media-tree.md` §2).

## 5. Что делает сборщик, получив фрагмент

Обработка одного фрагмента — последовательная (следующий фрагмент обрабатывается только после этого):

1. `base := next_id`.
2. Для каждого узла фрагмента по локальному номеру `k = 0..N-1`, в порядке следования во фрагменте:
   - реальный `id := base + k`;
   - `parent`: локальная ссылка `j` → `base + j`; внешняя ссылка → `anchor`;
   - `sibling`: локальная ссылка `j` → `base + j`; внешняя ссылка → текущее значение `last_child[anchor]`, если оно уже есть, иначе (это первый когда-либо ребёнок `anchor`) — самоссылка на собственный `id` (как и предписано для первого ребёнка, `05-data-format.md` §3);
   - узел физически дописывается в «Данные» по `next_offset`; `next_offset += size` этого узла.
3. `last_child[anchor]` обновляется на `id` узла фрагмента, ставшего новым последним ребёнком `anchor` (для плоского списка — последний элемент списка; для поддерева — его корень, единственный узел фрагмента с внешним `parent`).
4. `next_id := base + N`.

## 6. Частный случай: плоский список без общего поддерева

Если фрагмент — не поддерево, а несколько независимых листовых узлов под одним `anchor` (например, N кадров одного потока подряд), внешнюю ссылку для `sibling` использует только **первый** узел списка (он продолжает цепочку от того, что уже было в дереве до этого фрагмента); остальные `N-1` узлов ссылаются друг на друга локально (`sibling = k-1`) — фрагмент уже сам выстраивает свою внутреннюю цепочку, сборщику остаётся пришить только самое начало к уже существующему хвосту.

## 7. Свойства решения

- Атомарные операции и CAS не нужны — всё разделяемое состояние (`next_id`, `next_offset`, `last_child`) мутируется только в одном потоке.
- Параллелизм остаётся там, где он дёшев: независимая подготовка фрагментов не требует вообще никакого общего состояния между потоками-производителями.
- Единственная точка последовательности — присоединение готового фрагмента (несколько целочисленных сложений и копирование байт) — на порядки дешевле дисковых операций, которые и так уже монопольны (ADR-005); нового узкого места не создаёт.
- Передача фрагмента от потока-производителя к сборщику — естественная очередь (FIFO), по аналогии с WriteQueue (`01-architecture.md` §2.1), только на уровень раньше конвейера — до того, как фконтейнер целиком станет буфером на физическую запись.

## 8. Открытые вопросы

- Конкретное представление маркера "внешняя ссылка" (sentinel-значение, отдельный флаг в API фрагмента, что-то ещё) — вопрос конкретного интерфейса между потоком-производителем и сборщиком, не принципа.
- Backpressure на очередь фрагментов к сборщику — по аналогии с общей моделью backpressure Storage (`00-requirements.md` §4.7), но для этой конкретно внутренней очереди детали не проработаны.
- Фрагмент с несколькими независимыми поддеревьями под одним `anchor` за одну передачу — сводится ли это к последовательности отдельных фрагментов (каждый со своей внешней `sibling`-ссылкой), или нужен как самостоятельный случай — не решено; вероятно, проще всегда требовать один `anchor` на фрагмент.
