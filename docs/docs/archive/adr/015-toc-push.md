# ADR-015: Push TOC подписчикам по WebSocket при завершении записи фблока

**Дата:** 2026-07-29
**Статус:** Принято

## Контекст

Помимо farc, в системе есть сервисы, которым интересен факт появления новых данных: Video Gateway обязан обрабатывать TOC каждого нового фконтейнера, чтобы позже отдавать видео web-клиентам, Timeline Service должен пополнять timeline канала (`01-architecture.md`, системный контекст). Текущий контракт уведомлений (`00-requirements.md` §4.9) передаёт только UUID нового фконтейнера — подписчику приходится отдельным запросом на чтение получать TOC (ADR-004), хотя farc и так только что построил его при финализации фблока (`06-toc-format.md` §3.3). При постоянном потоке записи это лишний обязательный round-trip на каждое уведомление для типового подписчика.

## Сравнение

### 1. Оставить как есть — UUID в уведомлении, TOC подписчик читает сам
- ✔ Не меняет существующий контракт (`00-requirements.md` §4.9).
- ❌ Лишний обязательный запрос на чтение TOC на каждое уведомление для подписчика, которому TOC нужен почти всегда (Video Gateway).
- ✔ Подписчик, которому TOC не нужен (например, чисто мониторинговый), не платит за передачу лишних данных.

### 2. Push TOC вместе с уведомлением по существующему каналу событий
- ✔ Один канал уведомлений, не нужно поддерживать второй протокол.
- ❌ Требует зафиксировать транспорт уведомлений (сейчас никак не зафиксирован) как способный нести произвольный объём данных, а не только компактное событие — меняет уже принятый и более простой контракт §4.9 для всех подписчиков, а не только для тех, кому нужен TOC.

### 3. Push TOC по отдельному WebSocket-каналу для подписавшихся сервисов
- ✔ Существующее UUID-событие (§4.9) не меняется, обратная совместимость.
- ✔ Явная подписка — не платят за TOC те, кому он не нужен.
- ❌ Два канала уведомлений вместо одного (событийный + TOC-push) — сложнее эксплуатационно.
- ✔ WebSocket даёт постоянное соединение без поллинга — уместно, когда подписчик почти всегда online.

## Решение

Push TOC нового фконтейнера по отдельному WebSocket-каналу подписавшимся сервисам, в дополнение к существующим событиям из `00-requirements.md` §4.9, которые не меняются.

## Обоснование

Отдельный канал не трогает уже принятый и более простой контракт UUID-событий и даёт явную подписку: сервисы вроде Video Gateway получают TOC проактивно и не тратят отдельный запрос на его получение, а сервисы, которым TOC не нужен, не подписываются и не получают лишний трафик. Транспорт — WebSocket, а не поллинг: подписчик почти всегда online, разрыв соединения обнаруживается сразу же.

Основной путь чтения (потребитель сам разбирает TOC и вычисляет смещения, ADR-004) не меняется — push лишь избавляет от одного из двух шагов (получение TOC), которые и так уже входят в этот путь.

## Открытые вопросы

- Формат push-сообщения: весь TOC как есть из `06-toc-format.md`, либо только базовый TOC без производных индексов — зависит от того, что реально нужно Video Gateway.
- Поведение при разрыве соединения подписчика: буферизация пропущенных TOC на стороне farc или обязанность подписчика дочитать пропущенное отдельным запросом (ADR-004/ADR-016) — не решено, для этого случая как раз и предусмотрен fallback-режим ADR-016.
