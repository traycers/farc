# ADR-015: Единый WebSocket-сервер для всех исходящих событий (уведомления + push TOC)

**Дата:** 2026-07-29
**Статус:** Принято (пересмотрено 2026-07-31 — слияние с `EventStream` в единый WebSocket-сервер)

## Контекст

Помимо farcd, в системе есть сервисы, которым интересен факт появления новых данных: Video Gateway обязан обрабатывать TOC каждого нового фконтейнера, чтобы позже отдавать видео web-клиентам, Timeline Service должен пополнять timeline канала (`01-architecture.md`, системный контекст). Текущий контракт уведомлений (`00-requirements.md` §4.9) передаёт только UUID нового фконтейнера — подписчику приходится отдельным запросом на чтение получать TOC (ADR-004), хотя farcd и так только что построил его при финализации фблока (`06-toc-format.md` §5). При постоянном потоке записи это лишний обязательный round-trip на каждое уведомление для типового подписчика.

Независимо от TOC, в системе уже есть компактные события (`fblock.write.started/completed`, `fblock.deleted`, `storage.alert`, `job.*` — `02-storage.md` §7), которые ретранслирует `EventStream` через Server-Sent Events. Оба механизма адресованы во многом одним и тем же подписчикам (Video Gateway, Timeline Service) и оба требуют постоянного соединения — держать для этого два разных сервера с разными транспортами (SSE и WebSocket) означает два порта, два протокола, два набора реконнект-логики ради одной и той же по сути задачи push-доставки.

## Сравнение

### 1. Оставить как есть — UUID в уведомлении, TOC подписчик читает сам
- ✔ Не меняет существующий контракт (`00-requirements.md` §4.9).
- ❌ Лишний обязательный запрос на чтение TOC на каждое уведомление для подписчика, которому TOC нужен почти всегда (Video Gateway).
- ✔ Подписчик, которому TOC не нужен (например, чисто мониторинговый), не платит за передачу лишних данных.

### 2. Push TOC вместе с уведомлением по существующему каналу `EventStream` (SSE)
- ✔ Один канал уведомлений, не нужно поддерживать второй протокол.
- ❌ Требует, чтобы транспорт `EventStream` умел нести произвольный объём данных, а не только компактное событие — меняет контракт §4.9 для всех подписчиков, а не только для тех, кому нужен TOC.
- ❌ SSE — однонаправленный HTTP-стрим; для явной посообщенной подписки клиента на конкретные каналы (а не на всё хранилище) неудобен без дополнительного канала для управления подпиской.

### 3. Push TOC по отдельному WebSocket-каналу, `EventStream` (SSE) остаётся отдельно для компактных событий
- ✔ Существующее UUID-событие (§4.9) не меняется, обратная совместимость.
- ✔ Явная подписка — не платят за TOC те, кому он не нужен.
- ❌ Два параллельных сервера исходящих событий (SSE `EventStream` + WebSocket TOC-push) — два порта, два протокола, два набора логики восстановления соединения ради, по сути, одного и того же класса задачи (push подписчику).
- ✔ WebSocket даёт постоянное соединение без поллинга — уместно, когда подписчик почти всегда online.

### 4. Единый WebSocket-сервер для обоих типов сообщений (компактные события + TOC)
- ✔ Один сервер, один порт, один протокол — меньше эксплуатационной поверхности, чем варианты 2 и 3.
- ✔ Явная подписка на уровне соединения: клиент указывает, что ему нужно — только компактные события, только TOC, или оба; не платит за лишний трафик.
- ✔ WebSocket одинаково хорошо обслуживает оба сценария (мониторинговое событие и полный TOC) — нет причины держать для компактных событий отдельный SSE-транспорт.
- ❌ Отказ от текущего SSE-транспорта `EventStream` и его `Last-Event-ID`-навёрстывания — нужна собственная схема восстановления пропущенного при разрыве WebSocket-соединения (см. «Открытые вопросы»).
- ❌ Существующие SSE-подписчики (если появятся раньше миграции) нужно перевести на WebSocket-клиент.

## Решение

Единственный компонент **`EventPushServer`** (уровень Archive; заменяет `EventStream` и ранее предложенный отдельный `TocPushServer`, `10-service-composition.md` §4.4) держит один WebSocket-сервер — единственную точку исходящих push-событий farcd. При подключении клиент указывает, какие типы сообщений ему нужны: компактные события фблока (`00-requirements.md` §4.9), TOC целиком при завершении записи, либо оба. Источник обоих типов сообщений — один и тот же `NotificationBus` каждого `StorageUnit`.

Подписка на TOC остаётся по конкретным каналам (клиент подписывается на интересующие его номера каналов, а не на всё хранилище) — здесь ничего не меняется относительно исходного решения.

## Обоснование

Компактные события и TOC технически различаются только объёмом полезной нагрузки на сообщение, а не природой доставки — оба толкаются подписчику проактивно, без опроса, обоим нужно постоянное соединение и явная подписка, чтобы не платить за ненужный трафик. Раз это одна и та же задача, нет причины решать её двумя разными транспортами (SSE и WebSocket) с двумя раздельными серверами. Один WebSocket-сервер с типизацией сообщения (что именно шлётся — компактное событие или TOC) закрывает оба сценария при меньшей эксплуатационной поверхности.

Основной путь чтения (потребитель сам разбирает TOC и вычисляет смещения, ADR-004) не меняется — push лишь избавляет от одного из двух шагов (получение TOC), которые и так уже входят в этот путь.

## Открытые вопросы

- **Схема восстановления пропущенного при разрыве WebSocket-соединения** (замена SSE `Last-Event-ID`) — не решена. Для TOC подписчик может восстановиться через fallback-чтение по `(канал, t1, t2)` — ADR-016, тот же путь, что и для впервые подключившегося подписчика. Для компактных событий (`storage.alert`, `job.*` и т.п.) аналогичного fallback нет — нужно решить, критична ли для них повторная доставка, или потеря допустима.
- **Формат кадра сообщения:** как подписчик отличает "компактное событие" от "TOC" в одном потоке — нужен явный тип сообщения (например, JSON-конверт `{type, payload}`) — предмет отдельной спецификации протокола.
- Формат push-сообщения для TOC: целиком, как есть из `06-toc-format.md` — деления на «базовый TOC» и «производные индексы» больше нет (единая SoA-структура, `06-toc-format.md` §2), так что этот вопрос снят сам собой.
