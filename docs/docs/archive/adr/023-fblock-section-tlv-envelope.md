# ADR-023: TLV-конверт для верхнеуровневых секций фблока

**Дата:** 2026-08-24
**Статус:** Принято (уточнено по итогам обсуждения 2026-08-24 — снят блокирующий вопрос №1 первой редакции; конкретная структура эпилога и узла зафиксированы в §12.2–§12.4 `03-storage-format.md`)

## Контекст

Текущий формат фблока (`03-storage-format.md`, v1.0, реализовано в `fblock/prolog.go`, `catalog.go`, `header.go`, `epilog.go`) — это шесть жёстко заданных секций в фиксированном порядке: Пролог (фикс. часть + JSON-параметры) → Каталог → Контрольные суммы заголовка → Контент → TOC → Эпилог. Офсет каждой секции — арифметика над полями, часть которых (`toc_size`) лежит в эпилоге, то есть в конце фблока; отсюда правило «читаем с двух концов» (§3.2) и то, что валидный `magic_epilog` (последние 20 байт, физически пишется последним) — единственный сигнал «запись фблока завершена», на котором стоит восстановление после сбоя (ADR-017, `internal/storage/consistency.go`).

Первая редакция этого ADR (см. историю файла) предлагала однородный TLV-узел (`magic_start | type | size-до-конца | id | parent | sibling | size(value) | value | паддинг | crc32×2 | magic_finish`) для верхнеуровневых секций и не была принята — форвард-скан ломал единственный сигнал завершённости записи (ADR-017), а «size до конца» дублировало `value_size`. Ниже — итог предметного обсуждения (grilling, 2026-08-24), решающего оба вопроса и фиксирующего полную структуру.

## Сравнение

### 1. Текущая структура (v1.0, реализовано) — фиксированные секции, офсеты вычисляются

- ✔ Дешёвая (20 байт), находимая без сканирования проверка «фблок дописан полностью» — критично при старте farcd, когда сканируется состояние хранилища из миллионов фблоков (ADR-007 существует именно чтобы не тянуть это дороже).
- ✔ Минимальный фиксированный оверхед (112 байт/фблок), не растущий с числом секций.
- ❌ Порядок и число секций жёстко зашиты в код; несимметричное покрытие CRC (у секции «Контрольные суммы» и у `magic_epilog` своего CRC нет); контент физически дозаписывается нулями до полной вычисленной ёмкости (`fblock.ContentSize`, подтверждено кодом — `internal/storage/assemble.go`), только чтобы эпилог оставался на фиксированном смещении `fblock_size - 20` — то есть чтение задаром, но запись/CRC оплачивает лишние (иногда гигабайты) нулевых байт для короткого фконтейнера.

### 2. Принятая структура v2.0 — TLV-узлы верхнего уровня + прогрессивный эпилог-справочник

- ✔ Однородный кодек узла вместо специализированных `prolog.go`/`catalog.go`/`header.go`/`epilog.go`.
- ✔ Симметричное CRC-покрытие каждого узла (`crc32_header`+`crc32_value`), секция «Контрольные суммы» упразднена как отдельная сущность.
- ✔ Эпилог остаётся дешёвым, находимым без сканирования (фиксированный размер и офсет от конца фблока) — свойство v1.0 сохранено, а не потеряно, за счёт того, что его тело — не свободно растущая структура, а справочник по **малому фиксированному для текущей версии** набору узлов (5: root/params/catalog/content/toc).
- ✔ Эпилог перезаписывается атомарно (O(1), фиксированный размер) после завершения каждого узла — прогрессивный сигнал восстановления (`count` растёт 0→5), а не только бинарный `ready`/`in_progress`, как в v1.0.
- ✔ `value_size` узла — реальный размер данных, без искусственного дополнения нулями до вычисленной ёмкости (в отличие от v1.0) — экономит IO/CPU на CRC пустого пространства.
- ❌ Ломающее изменение формата — новая мажорная версия, несовместимая с v1.0; без миграции (тот же прецедент, что и сдвиг кодов кодека в `07-media-tree.md`, «Открытые вопросы»).
- ❌ `parent`/`sibling` на сегодняшних 5 узлах не решают задачу инкрементальной конкурентной записи (ради которой их придумал Hsu, `08-array-trees.md` §2) — это чистый задел на будущий рост состава узлов в следующих минорных/мажорных версиях, а не механизм, нужный сегодняшней топологии.

## Решение

### Область действия

TLV-конверт применяется **только** к верхнеуровневым секциям самого фблока (`03-storage-format.md`). Внутреннее устройство «Контента» — дерево фконтейнера и TOC (`05-data-format.md`–`08-array-trees.md`) — **не меняется**: миллионы листьев-кадров продолжают жить без magic/CRC/паддинга на каждый узел, ровно как сегодня. Для верхнеуровневого узла «Content» вся эта структура — непрозрачный `value`, как и «Контент» непрозрачен для Storage в v1.0.

### Фиксированная часть пролога (не узел дерева, смещение 0)

Остаётся отдельно от дерева — сохраняет контракт ADR-006 (детект `uninitialized` по отсутствию валидной магии в первых байтах) и `03-storage-format.md` §5.1 (структура первых байт не меняется между минорными версиями). Состав: `magic_prolog`, `format_version_major/minor`, `max_channels`, `write_sequence`, `catalog_time`, `fblock_size`, `catalog_entry_count`. Поля `params_size`/`catalog_size` **убраны** — они были нужны только для арифметики смещений v1.0, а в v2 расположение узлов даёт таблица эпилога; `catalog_entry_count` остаётся, но уже не для раскладки, а как доменная величина (число фблоков в Storage).

### Дерево верхнеуровневых узлов

Формат узла:

```
magic_start | type | id | parent | sibling | value_size | value | паддинг-до-alignment
| crc32_header | crc32_value | magic_finish
```

- `crc32_header` — CRC32 полей `type`..`value_size` (до `value`).
- `crc32_value` — CRC32 ровно `value_size` байт `value`; паддинг **не входит** в покрытие ни одного CRC — произвольные байты, не проверяются.
- Паддинг вставлен так, чтобы полный узел (`magic_start`..`magic_finish`) был кратен `alignment`; вычисляется из `value_size` и известных констант формата, отдельного поля «размер до конца узла» нет (устраняет дублирование размера из первой редакции).
- Узлы (все — дети `id=0`, порядок между собой — цепочка `sibling`):
  - `id=0`, `type=root` — физически материализованный пустой узел (`value_size=0`), `parent=0`, `sibling=0` (соглашение корня, как в дереве фконтейнера, `07-media-tree.md` §2).
  - `id=1`, `type=params` — JSON-параметры Storage (вынесены из фиксированной части пролога), `parent=0`, `sibling=0`.
  - `id=2`, `type=catalog` — снимок каталога (§6 v1.0, без изменений по содержанию), `parent=0`, `sibling=1`.
  - `id=3`, `type=content` — непрозрачный фконтейнер, `parent=0`, `sibling=2`.
  - `id=4`, `type=toc` — TOC, `parent=0`, `sibling=3`.

### Эпилог (не узел дерева — особая структура, как фиксированная часть пролога)

Фиксированного размера и смещения от конца фблока (вычисляется из `fblock_size`, находится без сканирования — то же свойство, что у эпилога v1.0). Тело:

```
magic_start | count | [type, id, offset, size, crc32]×5 | crc32_epilogue | magic_finish
```

- `count` (0..5) — сколько из пяти строк подтверждённо заполнены; растёт монотонно.
- Строка на узел — самоописывающаяся (`type`+`id`, не только позиционная), даёт реальные `offset`/`size`/`crc32` этого узла.
- `crc32_epilogue` — CRC32 над всем телом эпилога целиком (`magic_start`..строки), отдельно от `crc32` внутри каждой строки — защищает саму таблицу (например, от битового повреждения `count`), а не только то, на что она ссылается.
- Перезаписывается **атомарно, целиком, после завершения каждого узла** — цена O(1) (фиксированный размер, не растущая структура), даёт прогрессивный crash-recovery сигнал: валидный эпилог с `count = k < 5` означает, что первые `k` узлов подтверждённо целы, а не только «фблок либо весь `ready`, либо весь `in_progress`», как в v1.0.
- Между реальным концом последнего записанного узла и фиксированным смещением эпилога может быть разрыв — непроверяемое мёртвое пространство, не покрыто ничьим CRC (в отличие от v1.0, где именно Content физически дозаписывается нулями до полной ёмкости, чтобы эпилог остался на фиксированном смещении — в v2 та же гарантия достигается без этой цены, см. «Сравнение»).
- Узел, который ещё пишется в момент чтения (сегодня это может быть только Content, из-за потокового фчанк-письма) — проверяется как и сейчас, через `MagicTrailer` (ADR-017), эпилог этого не заменяет и не трогает.

### Версионирование

Формат получает новую мажорную версию — v2.0 (`03-storage-format.md` §4). CRC — везде CRC32 (IEEE), как и в v1.0; отдельного обоснования для CRC64 не нашлось.

## Обоснование

Ключевой сдвиг относительно первой редакции: закрепление, что множество верхнеуровневых узлов **для текущей версии формата мало и фиксировано** (5), позволило вернуть эпилогу главное свойство v1.0 — находимость без сканирования по фиксированному смещению — но с более информативным и дешевле обновляемым телом (справочник со `offset`/`size`/`crc32`, а не два CRC + `toc_size`). Это разрешает исходное противоречие между «эпилог как единственный сигнал завершённости» (ADR-017) и «TLV-узлы, найденные форвард-сканом» (первая редакция): вместо форвард-скана — фиксированный справочник, который сам растёт по `count`, а не по расположению.

Отказ от «дозаписи Content нулями до полной ёмкости» (v1.0) — не просто побочный эффект, а самостоятельный выигрыш: v1.0 платит IO и CPU на запись/CRC потенциально гигабайт нулевых байт только чтобы удержать фиксированное смещение эпилога; в v2 та же гарантия достигается структурно (через таблицу с явными `offset`/`size`), поэтому цена снята.

`parent`/`sibling` на сегодняшних пяти узлах признанно избыточны для *текущей* топологии — они принятое, осознанное решение на будущее (рост состава узлов в следующих версиях формата), а не механизм, нужный для решения сегодняшней задачи. Это принято как разумный, дешёвый (8 байт/узел) задел, а не как немедленно оправданная сложность.

## Открытые вопросы

- ~~Чем заменить `magic_epilog`-с-конца как сигнал завершённости записи~~ — решено: эпилог остаётся на фиксированном, вычисляемом из `fblock_size` смещении (см. «Решение»), а не переезжает вслед за форвард-сканом; прогрессивный `count` расширяет, а не заменяет исходную гарантию.
- ~~Область действия (верхний уровень фблока против дерева фконтейнера/TOC)~~ — решено: только верхний уровень; `05`–`08` не меняются.
- ~~Дублирование поля `size`~~ — решено: только `value_size`, «размер до конца узла» вычисляется.
- ~~Нужен ли паддинг до границы кластера/страницы~~ — решено: да, на уровне узла (не через дозапись Content нулями до полной ёмкости, как в v1.0) — паддинг маленький (до `alignment`), не покрыт CRC, значение узла о нём не знает.
- ~~CRC32 или CRC64~~ — решено: CRC32 везде.
- Точный побайтовый layout (размеры полей `type`/`id`/`offset`/`size` и т.п. в узле и в строке эпилога), нумерация `type` для `root`/`params`/`catalog`/`content`/`toc` — не зафиксированы этим ADR, остаются на этапе реализации (issue 04, `.scratch/fblock-tlv-sections/`).
