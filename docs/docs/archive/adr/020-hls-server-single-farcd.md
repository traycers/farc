# ADR-020: hlsd в v1 работает ровно с одним farcd

**Дата:** 2026-08-05
**Статус:** Принято

## Контекст

`internal/hlsconfig.Config` сегодня хранит `farcds` — список farcd-эндпоинтов (`id`, адрес `HttpApiServer`, адрес `EventPushServer`), а каждая запись `channels[]` ссылается на один из них полем `farcd` (`id` из списка). Формат допускает, что разные каналы одного `hlsd` обслуживаются разными `farcd`-процессами — `internal/hlsapi.Server` прямо на это рассчитан: он хранит `map[uint16]*hlsclient.Client` ("канал → клиент своего farcd"), а не один клиент на процесс.

Возник смежный вопрос: может ли **один и тот же** канал одновременно находиться на нескольких `farcd`. Ответ — нет: `hlsconfig.validate()` отклоняет две записи `channels[]` с одинаковым `id` как `duplicate id`, так что "один канал → несколько farcd" невозможно выразить в файле уже сегодня. Разбор этого вопроса, впрочем, вскрыл более широкий: `12-hls-server.md` §8 уже фиксирует как открытый вопрос отсутствие схемы синхронизации связки `канал → хранилище` между конфигурацией `farcd` и конфигурацией `hlsd` — а эта проблема тем более не решена для случая нескольких разных `farcd`.

Ни один реальный сценарий развёртывания (`docker-compose.yaml`: один сервис `farc`) сегодня не использует больше одного `farcd`. Список `farcds` и per-channel ссылка `farcd` — это заранее заложенная общность, для которой нет ни продуктовой потребности, ни решённой схемы синхронизации, ни тестового покрытия (все существующие тесты `internal/hlsconfig`, `internal/hlsd`, `internal/hlsapi` используют ровно один `farcd`).

## Решение

В v1 `hlsd` работает ровно с одним `farcd`. Конфигурация `hlsd` содержит один объект `farcd` (`http`/`ws`), а не список; запись канала — только `id` и `storage`, без ссылки на `farcd` (ссылаться не на что). `internal/hlsapi.Server` получает один `*hlsclient.Client` вместо `map[uint16]*hlsclient.Client`.

Поддержка нескольких `farcd` за одним `hlsd` (и тем более — одного канала на нескольких `farcd`, например на время миграции, ADR-014 §5.1.5) откладывается за пределы v1 и не реализуется, пока не появится конкретный сценарий развёртывания, которому она нужна.

## Обоснование

Список из одного элемента и per-channel ссылка на него — это сложность (лишнее поле в конфиге, лишняя проверка "ссылка существует", `map` вместо одного клиента в `hlsapi`) без текущей выгоды: она заложена под сценарий (несколько `farcd` за одним `hlsd`), для которого не решена смежная проблема — синхронизация связки `канал → хранилище` между двумя независимо редактируемыми конфигами (`12-hls-server.md` §8). Реализовывать API под сценарий с нерешённой моделью данных — не оправданный объём работы для v1; проще сузить формат сейчас и расширить его, когда появится реальный второй `farcd` и вместе с ним — ответ на вопрос синхронизации.

## Открытые вопросы

- Когда потребуется больше одного `farcd`, вернуться к списку `farcds` и заодно решить §8's вопрос синхронизации связки `канал → хранилище` — уже как часть того же изменения, а не как отдельный поднятый, но не закрытый вопрос.
