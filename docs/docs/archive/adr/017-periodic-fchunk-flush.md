# ADR-017: Периодическая запись готовых фчанков по таймауту

**Дата:** 2026-07-31
**Статус:** Принято (пересмотрено 2026-07-31 — выравнивание переносится на уровень фконтейнера/фблока; пересмотрено повторно 2026-07-31 — пишем только целыми выровненными блоками, без паддинга на каждом триггере, кроме закрытия фконтейнера; пересмотрено в третий раз 2026-07-31 — отдельного паддинга перед началом Данных не нужно: фблок пишется как один буфер целиком от собственного выровненного начала, см. «Решение»; пересмотрено в четвёртый раз 2026-07-31 — специфицирован механизм передачи `ready_bytes`: push от `Recorder` к `StorageEngine`, см. «Решение»; пересмотрено в пятый раз 2026-08-14 — реализовано: механизм magic-trailer для восстановления после сбоя, момент назначения физического индекса (при постановке в голову пула буферов), восстановление частично записанного `in_progress` фблока, и выбрано значение `T` по умолчанию — см. «Реализация» и обновлённые «Открытые вопросы»)

## Контекст

Текущая модель записи (`01-architecture.md` §2, `02-storage.md` §4.2.1/§4.2.4, диаграмма §6.1): потребитель заполняет буфер фконтейнера целиком через Заполнителя (`09-fcontainer-write-path.md`), затем одним вызовом «вернуть буфер» отдаёт его `Recorder`'у — только после этого буфер попадает в `WriteQueue`, и `StorageEngine` пишет его фчанками (`fchunk_size`, 4–16 МБ) одним проходом.

Фконтейнер может заполняться долго (время актуальности — от минут до часов, в зависимости от конфигурации канала). При текущей модели это означает, что все его данные лежат только в памяти вплоть до закрытия. Последствия:
- При падении процесса или потере питания до возврата буфера теряются данные фконтейнера целиком, а не только последний неполный фчанк.
- Объём памяти, занятой одним заполняемым фконтейнером, растёт вместе со временем его актуальности без верхней границы, кроме размера самого фблока.
- Запись на диск происходит одним длинным всплеском в момент закрытия фконтейнера, а не равномерно по мере поступления данных.

## Сравнение

### 1. Оставить как есть — пишем только по закрытию фконтейнера
- ✔ Простая модель: `StorageEngine` получает буфер целиком, разбиение на фчанки — чисто механическое.
- ❌ Данные фконтейнера уязвимы к потере целиком, а не частями, при сбое до закрытия.
- ❌ Нет верхней границы на объём несохранённых данных в памяти, кроме размера фблока.

### 2. Писать по достижении `fchunk_size`, без таймаута
- ✔ Данные попадают на диск равномерно по мере накопления, без ожидания закрытия.
- ❌ Для канала с низким битрейтом накопление `fchunk_size` (4–16 МБ) может занимать очень долго — на практике вырождается в вариант 1 для медленных потоков.

### 3. Писать по `fchunk_size` ИЛИ по таймауту `T`, хвост — с паддингом на каждом срабатывании
- ✔ Верхняя граница одновременно и на объём несохранённых данных (`fchunk_size`), и на время их жизни в памяти (`T`), без исключений.
- ❌ Каждое срабатывание таймаута, заставшее готовых данных меньше `fchunk_size`, тратит на паддинг до `alignment - 1` байт полезного объёма фблока — при частом таймауте на медленном канале это заметные накладные расходы.

### 4. Писать только целыми выровненными блоками; паддинг — только при закрытии фконтейнера (выбрано)
- ✔ Паддинг нужен ровно один раз на фконтейнер (в момент закрытия), а не на каждое срабатывание таймаута — никаких вхолостую потраченных байт в процессе записи.
- ✔ Механизм предельно простой: `writable = floor(ready_bytes / alignment) × alignment`; если `writable > 0` — пишем; иначе не пишем вовсе, ждём следующего триггера.
- ❌ Для канала, чей битрейт настолько низок, что готовые данные не пересекают границу `alignment` (4 КиБ) между срабатываниями, таймаут `T` перестаёт быть строгой гарантией окна потери данных — реальная задержка равна времени накопления одного выровненного блока, которое от `T` не зависит. Принимается как приемлемый компромисс для домена (видео/аудио RTSP-каналы почти всегда обеспечивают достаточный поток данных, чтобы 4 КиБ набиралось быстро) — если это окажется не так для конкретного канала, потребуется отдельное решение (см. «Открытые вопросы»).

## Решение

`StorageEngine` (через `WriteQueue`) пишет накопленные готовые байты фконтейнера, не дожидаясь его закрытия потребителем. Триггер проверки — то, что наступит раньше: накоплено `fchunk_size` готовых байт, или истёк таймаут `T` с момента предыдущей записи по этому фконтейнеру. По срабатыванию триггера пишется `writable = floor(ready_bytes / alignment) × alignment` байт — **целое число выровненных блоков, без паддинга**. Если `writable == 0` (готового ещё меньше одного блока выравнивания), ничего не пишется — остаток продолжает копиться в буфере до следующего триггера.

Паддинг возникает только один раз — **при закрытии фконтейнера**: на этот момент новых данных больше не будет, а хвост короче `alignment` всё равно нужно физически записать (`direct`-бэкенд не пишет неполный блок как есть, ADR-010). Именно этот финальный кусок дополняется до кратности `alignment` перед записью.

`StorageEngine` не занимается паддингом сам: он «не знает о структуре фблока кроме разбиения на фчанки и порции — все смещения и размеры даются в команде» (`02-storage.md` §4.2.4) и поэтому не может содержательно решить, чем дополнить финальный хвост. Ответственность переносится **на уровень формата фконтейнера и фблока** (`05-data-format.md`, `03-storage-format.md`) — то есть на то, что готовит буфер для `StorageEngine` (Recorder/Заполнитель) и вызывает финальную запись при закрытии.

Для самого первого куска отдельно выравнивать начало секции Данных не требуется. `StorageEngine` пишет не «сначала заголовок отдельной операцией, потом данные новой операцией», а один непрерывный **буфер фблока целиком** (заголовок + данные + TOC + эпилог, `02-storage.md` §4.2.4: «разбивает буфер фблока на фчанки») — заголовок полностью известен уже в момент перехода фблока в `in_progress`, то есть раньше, чем начнут поступать данные потребителя, и является просто первыми байтами того же потока. Чанкование по `fchunk_size`/таймауту идёт сквозно от смещения 0 фблока, которое уже выровнено (`fblock_size` кратен выравниванию, ADR-010; `offset(index) = index × fblock_size`) — граница очередного куска зависит только от накопленного объёма байт от начала фблока, а не от логических границ секций внутри него (кусок может закончиться и в середине заголовка). Поэтому выравнивание сохраняется по индукции без какого-либо специального паддинга перед Данными: выровненное начало (0) плюс смещение на длину, кратную выравниванию, снова даёт выровненное смещение (`03-storage-format.md` §10).

`T` — параметр конфигурации Storage (рядом с `fchunk_size`, `03-storage-format.md`), а не глобальная константа: разным каналам/хранилищам может требоваться разный баланс между частотой проверки и допустимым окном потери данных. Точное имя параметра и значение по умолчанию — открытый вопрос.

Механизм передачи `ready_bytes` — push, а не опрос: только `Recorder` знает момент, когда в буфере фконтейнера появились новые данные (Заполнитель пишет через него/в его буфер), и именно `Recorder` в этот момент сигнализирует `StorageEngine`, какие байты сейчас актуальны/доступны для записи. Сам Заполнитель ничего не знает про `fchunk_size` и не сравнивает с ним — это обновление объёма готовых байт (`ready_bytes`), а не сигнал «порог пересечён». Сравнение `ready_bytes` с `fchunk_size` и проверка таймаута `T` — исключительно на стороне `StorageEngine` (через `WriteQueue`), которому эти параметры и принадлежат (`02-storage.md` §4.2.4). Это сохраняет `fchunk_size` внутренней деталью `StorageEngine`, не протекающей выше по стеку.

## Обоснование

Фчанк как «единица write-verify» уже подразумевал разбиение на порции при записи (`00-requirements.md` §4.2, ADR-005) — это решение не меняет сам механизм write-verify, а меняет то, **когда** накопленные байты становятся кандидатом на запись: не только «буфер закрыт», но и «прошло время `T`» или «накопилось достаточно». Запись только целыми выровненными блоками (без паддинга «про запас» на каждый таймаут) убирает основную стоимость периодической записи: паддинг на каждом срабатывании таймаута мог бы регулярно тратить впустую до `alignment - 1` байт полезного объёма фблока; при частом `T` на большом числе каналов это накопилось бы в заметные потери. Откладывая незавершённый блок до следующего триггера (вместо немедленного паддинга), мы платим за это только смягчением гарантии таймаута для каналов с очень низким битрейтом (см. вариант 4 в «Сравнении») — этот компромисс принят как приемлемый для домена RTSP-архивирования.

Перенос выравнивания на уровень фконтейнера/фблока, а не в `StorageEngine`, следует из уже принятого разделения ответственности: `StorageEngine` — тонкий исполнитель команд «записать N байт по смещению» без знания структуры (`02-storage.md` §4.2.4, §4.2.5 про `IoBackend`); он не может сам придумать, чем дополнить финальный хвост до выравнивания, не нарушив формат. Только то, что понимает структуру фблока и фконтейнера, может корректно вставить паддинг при закрытии и позже (при чтении) отличить его от настоящих данных.

Таймаут `T` (в сочетании с записью по достижении `fchunk_size`) по-прежнему ограничивает и объём памяти, немедленно занятой одним активным фконтейнером, и — для каналов с достаточным битрейтом — окно потери данных при сбое; без него оба показателя росли бы без ограничения вместе с длительностью записи канала.

## Реализация

Реализовано в `internal/storage` (`pool.go`, `segment.go`) и `internal/storageengine` (`EnqueueOpenWrite`/`WriteHandle`), закрывая все вопросы, оставленные открытыми выше на момент четвёртого пересмотра.

**Момент выбора физического индекса N.** `Pool` держит до `size` сегментов (`fcontainer.Filler` + сопутствующее состояние), но физический индекс/`in_progress` назначается **только голове FIFO** — сегменту, который прямо сейчас пишется на диск. В штатном режиме (пул был пуст) это происходит сразу при получении буфера потребителем (`Unit.BeginSegment`), то есть до единого байта данных. Под нагрузкой (несколько уже полностью заполненных, но ещё не получивших индекс сегментов ждут в очереди) назначение откладывается до момента, когда предыдущий активный сегмент закрывается и освобождает место в голове очереди (`Pool.release`) — предыдущему это состояние соответствовало «?» на панели администратора (fblocks-grid).

**Механизм паддинга финального куска — комбинированная запись данные+magic.** Каждое срабатывание триггера (`fchunk_size` либо таймаут `T`) пишет, **одной write-verified операцией**: `writable` реальных байт контента + один блок размером `alignment`, содержащий зарезервированный 8-байтовый маркер `MagicTrailer` (`FARCTRLR`) плюс нулевой паддинг до `alignment`. Маркер отмечает «текущий живой конец потока контента» и физически перемещается вперёд каждым следующим срабатыванием (предыдущий экземпляр перезаписывается новыми реальными байтами + новым маркером дальше). Write-verify для этого комбинированного куска не отличается от обычного — та же процедура «записать, прочитать обратно, сравнить» (`internal/storageengine.stepWriteLocked`), просто данные куска теперь могут включать маркер вместо (или вместе с) паддинга нулями.

**Восстановление после сбоя во время частичной записи.** `ConsistencyCheck` (`internal/storage/consistency.go`) для `in_progress`-фблока с валидным заголовком, но невалидным эпилогом, теперь пытается настоящее восстановление вместо немедленного `Bad`: читает секцию Данных, находит последний (единственный сохранившийся) `MagicTrailer` (`fblock.FindTrailer`), декодирует `mediatree.Element`ы последовательно до этой границы (`mediatree.DecodeContentPartial` — останавливается по первому неполному элементу, не считая это ошибкой), строит TOC из того, что декодировалось чисто (`toc.Build`), и физически дописывает TOC + эпилог поверх маркера, переводя фблок в `Ready` с `end`, усечённым до времени последнего восстановленного кадра. Поскольку каждый более ранний триггер уже был подтверждён write-verify вместе со своим маркером, а маркер каждый раз полностью перезаписывается следующим, неоднозначность восстановления ограничена максимум одним элементом на границе (отбрасывается, не искажая остальное дерево). Если в Данных вообще нет маркера (сбой до первого срабатывания триггера) — фблок помечается `Bad`, как и раньше.

Это единственное намеренное исключение из принципа «`ConsistencyCheck` не пишет на основной диск, только меняет состояние `mgr`» — реконструкция и физическая запись TOC/эпилога это единственный способ сделать частично записанный фблок снова по-настоящему читаемым.

**Значение `T` по умолчанию.** `fblock.Params.FlushTimeoutNS` (JSON-ключ `flush_timeout_ns`, рядом с `fchunk_size` в `03-storage-format.md` §5.2) — 5 секунд по умолчанию (`fblock.DefaultFlushTimeoutNS`), применяется `DecodeParams`, если поле отсутствует или равно нулю.

**Низкобитрейтные каналы под нагрузкой:** под нагрузкой (в пуле больше одного занятого слота) таймаут `T` полностью игнорируется — пишем как можно быстрее, ограничиваясь только `fchunk_size`, пока очередь не разгрузится до одного активного сегмента.

## Открытые вопросы

- **Write-verify для финального куска** — снят: реализован без каких-либо отличий от обычного куска (см. «Реализация»).
- **Механизм паддинга финального куска** — снят: комбинированная запись данные+`MagicTrailer` (см. «Реализация»); маркер не путается с реальными данными, так как всегда находится строго после последнего подтверждённого байта контента и полностью перезаписывается следующим триггером.
- **Низкобитрейтные/простаивающие каналы** — снят для случая нагрузки на пул (таймаут игнорируется целиком, см. «Реализация»); для канала, вообще не набирающего `alignment` байт готовых данных при пустом пуле, ограничение остаётся тем же принятым компромиссом, что и в исходном решении.
- **Значение `T` по умолчанию и допустимый диапазон** — снят: 5 секунд по умолчанию, конфигурируется через `flush_timeout_ns` (см. «Реализация»); допустимый диапазон явно не ограничен, кроме положительности.
- **TOC и эпилог фблока** — без изменений, по-прежнему пишутся при закрытии фконтейнера (не затронуто).
- **Восстановление после сбоя во время частичной записи** — снят: см. «Реализация».
- **Момент выбора физического индекса N** — снят: см. «Реализация».
