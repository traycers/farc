# ADR-006: Ленивая инициализация хранилища

**Дата:** 2026-04-24
**Статус:** Принято

## Контекст

Полная инициализация хранилища (запись заголовков во все фблоки) на диске 18 ТБ занимает порядка суток. Это неприемлемо при вводе нового диска в эксплуатацию.

## Варианты

### 1. Полная инициализация при создании
- ✔ После инициализации все фблоки сразу в состоянии `ready` — простота логики.
- ❌ Время инициализации пропорционально размеру диска. Для 18 ТБ — порядка суток.
- ❌ Диск не может принимать данные, пока инициализация не завершена.

### 2. Ленивая инициализация
- ✔ Инициализация = запись одного фблока (секунды).
- ✔ Диск начинает принимать данные немедленно.
- ❌ Необходимо новое состояние фблока (`uninitialized`) и логика его обработки.
- ❌ При старте нужен способ отличить `uninitialized` от повреждённых данных.

## Решение

Ленивая инициализация.

### Состояние `uninitialized`

Добавляется четвёртое базовое состояние фблока — `uninitialized`. Фблок в этом состоянии:
- Не содержит валидного заголовка (на диске мусор или нули).
- **Перезаписываем** — доступен для записи Recorder'ом.
- **Не читаем** — попытка чтения данных возвращает ошибку.
- Определяется по отсутствию валидного magic number в заголовке фблока.

### Процесс инициализации

1. Создать файл нужного размера (или открыть блочное устройство).
2. Записать первый фблок (index=0) с заголовком, содержащим параметры хранилища: magic number, версия формата, размер фблока, размер фчанка, общее количество фблоков, начальный снимок индексов (все фблоки, включая нулевой, — `uninitialized`).
3. Инициализация завершена. Хранилище готово к работе.

**Исключение из инварианта `uninitialized`, специфичное для фблока 0.** Выше `uninitialized` определён как «не содержит валидного заголовка» — это верно для всех фблоков, кроме нулевого сразу после инициализации: у него заголовок физически валиден (иначе диск был бы нечитаем), но собственная запись в каталоге всё равно помечена `uninitialized`. Так сделано намеренно: bootstrap-запись фблока 0 не несёт реального фконтейнера и не должна считаться «настоящей» записью для алгоритма выбора следующего фблока (раздел «Приоритет при выборе фблока для записи» ниже) — иначе первая реальная запись всегда попадала бы на индекс 1, а не 0. Соответственно курсор при старте (см. `04-storage-operations.md` §6.1) тоже получает поправку на этот случай. На определение `uninitialized` по отсутствию magic number при полном скане диска (см. ниже) это исключение не влияет — оно касается только каталожного состояния индекса 0, а не того, как обнаруживаются физически неинициализированные фблоки.

### Приоритет при выборе фблока для записи

Recorder при движении по кругу выбирает фблоки для записи в следующем порядке приоритета:

1. `uninitialized` — сначала заполняем весь диск.
2. Перезаписываемый `ready` — `ready`, не `protected`, с истёкшим временем актуальности.

Это означает, что первый полный проход по диску заполняет все `uninitialized` фблоки. Со второго прохода работа идёт только с `ready` фблоками — обычный циклический режим.

### Определение `uninitialized` при старте

При загрузке индексов (из каталога или путём сканирования) фблок считается `uninitialized`, если его заголовок не содержит валидного magic number. Это надёжно отличает неинициализированный фблок от повреждённого (`bad`): у `bad` заголовок был валиден, но данные повреждены; у `uninitialized` заголовка никогда не было.

## Обоснование

Приоритет отдан скорости ввода диска в эксплуатацию. Усложнение логики (новое состояние, приоритет выбора) минимально и локализовано в `IndexManager`.
