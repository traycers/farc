# ADR-016: Fallback-резолв смещений по (канал, t1, t2) внутри farc

**Дата:** 2026-07-29
**Статус:** Принято

## Контекст

ADR-004 закрепляет модель, в которой потребитель сам читает TOC фблока и вычисляет смещения нужных данных — farc/StorageEngine лишь отдаёт байты по уже готовым смещениям. Это работает, когда потребитель (Video Gateway) уже получил и разобрал TOC этого фконтейнера заранее, например по push (ADR-015). Но возможна ситуация, когда потребитель не располагает разобранным TOC на момент запроса — не подписан на push, пропустил push из-за разрыва WebSocket-соединения, либо запрос идёт по данным, записанным до того, как этот экземпляр потребителя начал существовать. В этом случае у него есть только `(fblock id/UUID, канал, t1, t2)`, но не смещения.

## Сравнение

### 1. Требовать от потребителя всегда знать смещения (строго по ADR-004)
- ✔ Простая модель на стороне farc, TOC для farc остаётся полностью непрозрачным по семантике.
- ❌ Потребитель без разобранного TOC вынужден сначала отдельным запросом получить TOC целиком (уже возможно в рамках ADR-004 — «читаем индексы фблока»), разобрать его сам, затем сделать второй запрос за данными: два похода вместо одного.

### 2. farc сам резолвит (канал, t1, t2) → смещения по запросу
- ✔ Один запрос вместо двух для потребителя без готового TOC.
- ❌ farc перестаёт быть полностью безразличен к семантике TOC на уровне API (хотя бы в части «канал/время → offset») — расширяет поверхность, которую нужно поддерживать при изменениях формата TOC (`06-toc-format.md`).
- ✔ Не отменяет основной путь ADR-004 — это дополнительный режим по явному запросу, а не замена.

## Решение

Добавить к протоколу чтения (ADR-004) fallback-режим: потребитель может запросить данные, передав `(fblock id/UUID, канал, t1, t2)` без смещений; farc читает TOC самостоятельно — используя `frame_time_index` и companion-колонки `channel_id`/`stream_id` (`06-toc-format.md` §4) — находит нужные узлы и их смещения, читает и возвращает данные. Основной режим ADR-004 (потребитель сам вычисляет смещения) остаётся приоритетным и не меняется; fallback используется, когда у потребителя ещё нет разобранного TOC (см. ADR-015 про push).

## Обоснование

Экономит round-trip для небезразличного к производительности случая: первый запрос к каналу после (пере)запуска Video Gateway, разрыв WebSocket-подписки на TOC-push, — не отменяя более быстрый и уже принятый путь для типового случая, когда TOC уже на руках у потребителя. farc уже умеет проходить `frame_time_index` при построении и чтении собственного TOC-формата (`06-toc-format.md`), так что резолв — не новая компетенция с нуля, а использование существующей структуры данных с другой стороны вызова API.

## Открытые вопросы

- Нужен ли лимит на ширину диапазона `[t1, t2]` в fallback-запросе, чтобы резолв внутри farc не превращался в полный скан TOC большого фконтейнера.
- Должен ли fallback-режим идти через ту же FIFO-очередь чтения, что и основной путь ADR-004, или для него нужен отдельный приоритет — не решено, детали протокола очереди чтения выходят за рамки этого ADR.
