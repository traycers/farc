# ADR-018: Индекс `hlsd` строится из push TOC, а не резолвом на каждый запрос

**Дата:** 2026-08-04
**Статус:** Принято

## Контекст

`hlsd` (`12-hls-server.md`) должен по запросу плеера `(канал, t1, t2)` знать, из каких fcontainer собирать HLS-плейлист. У farcd для этого уже есть два независимых механизма: fallback-резолв `(uuid/канал, t1, t2)` → данные по явному запросу (ADR-016) и push TOC вместе с `fblock.write.completed` через `EventPushServer` (ADR-015). ADR-016 изначально спроектирован как fallback именно для подписчика без разобранного TOC на руках — «не подписан на push, пропустил push из-за разрыва соединения, либо запрос идёт по данным, записанным до того, как этот экземпляр потребителя начал существовать» — а не как основной путь работы.

Нужно решить, как `hlsd` получает TOC каждого fcontainer в обычном режиме работы: тем же fallback-резолвом на каждый запрос плейлиста, или подпиской на push с локальным индексом.

## Сравнение

### 1. Резолвить `(канал, t1, t2)` через ADR-016 на каждый запрос плейлиста
- ✔ `hlsd` не хранит состояние между запросами — проще горизонтальное масштабирование и перезапуск (нет индекса, который нужно восстанавливать).
- ✔ Не нужно поддерживать WebSocket-подписку и её переподключение.
- ❌ Каждый запрос плейлиста — обязательный round-trip к `farcd` за TOC, причём именно тот сценарий («TOC не разобран заранее»), ради которого ADR-016 задуман как fallback, становится основным путём вместо fallback-а.
- ❌ Построение плейлиста конкурирует с чтением данных сегментов и с приоритетом записи (ADR-005) за то же самое время `Reader`/`StorageEngine`, увеличивая нагрузку на горячий путь farcd без необходимости.

### 2. Push-подписка (ADR-015) + локальный индекс TOC, ADR-016 — только для бутстрапа
- ✔ Построение плейлиста — чтение уже разобранной локальной структуры в памяти (`ChannelIndex`, `12-hls-server.md` §4.2), без обращения к `farcd` на горячем пути отдачи плейлиста.
- ✔ Соответствует уже принятой в ADR-015 модели: push — основной путь получения TOC, fallback ADR-016 — для подписчика без готового TOC (первое подключение, разрыв соединения).
- ❌ `hlsd` становится stateful: нужно хранить индекс (в памяти, как минимум) и корректно обрабатывать разрыв WebSocket-подключения, включая часть событий, пропущенных за время разрыва.
- ❌ Бутстрап с нуля (первый запуск, либо длинный разрыв) требует резолва по всему сконфигурированному диапазону retention для каждого канала — потенциально тяжёлая операция при старте.

## Решение

Индекс `hlsd` строится из push TOC (`EventPushServer`, ADR-015): подписка на TOC по каждому обслуживаемому каналу, обновление локального индекса на `fblock.write.completed` и `fblock.deleted`. ADR-016 используется только для бутстрапа — при первом подключении и после разрыва WebSocket-соединения, чтобы получить TOC за диапазон, ещё не покрытый локальным индексом.

## Обоснование

Построение плейлиста — горячий путь, вызываемый на каждое обращение плеера к архиву; если он на каждый запрос идёт в `farcd` за TOC, `hlsd` систематически создаёт нагрузку на `Reader`/`StorageEngine`, которую сам ADR-016 не рассчитан нести как основной, а не аварийный путь. Локальный индекс переносит эту нагрузку на разовый бутстрап и на push-события, которые `farcd` и так рассылает независимо от того, есть у него подписчики или нет. Появившееся состояние (`ChannelIndex`) — цена, которую стоит платить: она ограничена памятью процесса `hlsd`, а не диском/IO `farcd`, и деградирует контролируемо (потеря индекса при падении процесса устраняется тем же бутстрапом, что и при первом запуске).

## Открытые вопросы

- Точная граница «непокрытого диапазона» после разрыва посреди работы (в отличие от первого запуска, где непокрытый диапазон — вся история канала) — не специфицирована, см. `12-hls-server.md` §8.
- Нужна ли `hlsd`'у персистентность индекса между перезапусками процесса (чтобы не гонять полный бутстрап на каждый рестарт), или это оправдано только при больших `retention.days` — не решено.
