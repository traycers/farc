# ADR-014: Поиск фблоков по каналу и времени — компактный регистр каналов

**Дата:** 2026-07-21
**Статус:** Принято (пересмотрено 2026-07-31 — поле `registry_used` убрано из формата: номер канала 0 зарезервирован, граница «когда-либо выделенных» позиций вычисляется из `channel_registry[]` при загрузке, а не хранится отдельно)

## Контекст

Каталог хранит по каждому фблоку только UUID, `begin`/`end` (время актуальности фконтейнера целиком) и флаги состояния (`00-requirements.md` §2, `03-storage-format.md` §6). Этого достаточно, чтобы найти фблоки, пересекающиеся по времени с `[t1, t2]`, но недостаточно, чтобы найти фблоки конкретного канала: один фконтейнер может содержать данные нескольких каналов одновременно, вплоть до постоянной записи **всех** каналов сразу — реальный режим эксплуатации, а не крайний случай.

Дополнительные ограничения предметной области:
- Список каналов не фиксирован — потребитель добавляет и удаляет каналы динамически.
- Номер канала — целое число, укладывающееся в `uint16` (не более 65535 каналов во всей системе).
- Канал может мигрировать из одного хранилища в другое; архив канала в старом хранилище должен оставаться корректно читаемым до тех пор, пока соответствующие фблоки не будут физически перезаписаны обычным циклом.

## Сравнение

### 1. Оставить как есть — поиск через внешнюю БД потребителя
- ✔ Без изменений формата.
- ❌ Потребитель обязан сам вести и синхронизировать индекс «канал → UUID/фблок» с событиями `fblock.deleted`/`fblock.write.completed`; при потере этой БД восстановить связку можно только полным сканированием TOC всех фблоков.

### 2. Bloom-фильтр по каналам на запись каталога
- ✔ Компактен, не требует знания заранее полного списка каналов.
- ❌ Вырождается именно в целевом сценарии: при постоянной записи всех каналов почти все биты фильтра установлены почти всегда, отсечение кандидатов не работает. Непригоден при реальном профиле нагрузки этого проекта.

### 3. Прямое отображение «номер канала = номер бита»
- ✔ Точное совпадение, без ложных срабатываний, без реестра.
- ❌ Ширина маски определяется теоретическим потолком номера (65535), а не реальным числом каналов: 8192 байта на запись каталога. Для 140 ТБ хранилища с реальными 64 каналами это вынуждает минимальный `fblock_size` ≈ 1.96 ГБ — непропорционально крупные фблоки только для покрытия теоретического максимума, который может не понадобиться никогда.

### 4. Компактный регистр «номер канала → позиция» + маска по позициям
- ✔ Ширина маски определяется реальным числом каналов с запасом (`C`, выбирается при инициализации), а не теоретическим потолком.
- ✔ Позиции можно безопасно переиспользовать после физической перезаписи старых данных канала — без риска перепутать каналы, потому что решение о переиспользовании основано на фактическом состоянии каталога, а не на догадке или таймауте.
- ❌ Требует нового раздела формата и логики обслуживания реестра — сравнимой по сложности с уже принятой архитектурой каталога, не принципиально нового класса.

## Решение

Компактный регистр каналов и плотная битовая маска по компактным позициям (вариант 4).

### Формат

Новое поле в фиксированной части пролога (`03-storage-format.md` §5.1), не меняющее общий размер фиксированной части (56 байт) — занимает 2 байта из существующего резерва по смещению 12:

```
max_channels   uint16   ёмкость регистра каналов (C) для этого хранилища
```

`C` фиксируется при инициализации хранилища, как и `fblock_size`, и не меняется без отдельной операции расширения ёмкости.

Новая секция в начале каталога, перед per-fblock массивами, покрывается тем же `crc32_catalog`:

```
channel_registry[]  C × 2 байта  uint16 — номер канала, занимающий позицию 0..C-1; 0 = позиция никогда не выделялась
```

Новый массив в per-fblock части каталога (SoA, рядом с `flags[]`/`uuid[]`/`begin[]`/`end[]`):

```
channel_bitmap[]   N × ceil(C/8) байт — бит на компактную позицию
```

`catalog_size = C×2 + N × (1 + 16 + 8 + 8 + ceil(C/8))`.

**Номер канала 0 зарезервирован** и не может быть реальным номером канала потребителя (номера — `1..65535`). Это не новое ограничение: `00-requirements.md` §2 уже определяет номер канала как «не более 65535 каналов», хотя `uint16` вмещает 65536 значений (`0..65535`) — то есть резерв одного значения уже заложен в существующий лимит, просто не был явно назван. Резервирование 0 убирает поле `registry_used`: `channel_registry[i] == 0` теперь однозначно означает «позиция `i` никогда не выделялась» (нулевой байт — естественное состояние незаписанной памяти/диска, ADR-006), а `channel_registry[i] != 0` — «когда-то выделялась» (текущим или уже переиспользованным номером; при переиспользовании старое значение перезаписывается новым и никогда не обнуляется обратно).

Поскольку выделение новых позиций всегда идёт по возрастанию первого свободного индекса (см. алгоритм ниже), когда-либо выделенные позиции всегда образуют непрерывный префикс `[0, k)` без дыр — поэтому `k` (аналог прежнего `registry_used`) вычисляется одним проходом по `channel_registry[]` наравне со счётчиками ссылок (см. ниже) и не хранится на диске отдельным полем.

### Регистрация номера канала

При появлении номера, отсутствующего в известных `IndexManager`'у позициях:

1. Если среди уже когда-либо выделенных позиций (`channel_registry[i] != 0`) есть хотя бы одна со счётчиком ссылок 0 — она переиспользуется: номер перезаписывается, счётчик начинает расти с нуля.
2. Иначе, если есть ещё ни разу не выделенная позиция (`channel_registry[i] == 0`, `i < C`) — выделяется позиция с наименьшим таким `i`.
3. Иначе — регистрация невозможна: `IndexManager` публикует алерт `channel_registry_full` (по аналогии с `no_free_fblocks`, `04-storage-operations.md` §6.4). Запись данных этого канала в это хранилище недоступна до освобождения позиции естественным циклом перезаписи или до операции расширения `C`.

Счётчик ссылок на позицию — сумма установленных битов этой позиции по всем `N` записям `channel_bitmap[]` в текущем состоянии `IndexManager`. Как и граница «когда-либо выделенных» позиций (пункт выше), не персистентен: пересчитывается одним проходом по каталогу при его загрузке (тот же проход, что уже выполняется при старте Storage, `04-storage-operations.md` §4–5), поэтому не требует дополнительного места на диске и переживает перезапуск без потери корректности.

### API и запросы

- Recorder принимает от потребителя список каналов буфера (`channels: []channel_number`) вместе с `begin`/`end`; резолвит каждый номер в компактную позицию (регистрируя новые по алгоритму выше) и выставляет соответствующие биты в снимке текущего фблока.
- Новый вид запроса к `IndexManager`, дополняющий существующие «выбрать индекс для записи» и «индекс по UUID»: по `(channel_number, t1, t2)` — резолвит номер в позицию через обратный индекс в памяти, отфильтровывает фблоки по пересечению `[begin, end]` с `[t1, t2]`, среди уцелевших — по установленному биту позиции. Возвращает кандидатов; точные диапазоны данных всё равно подтверждаются чтением TOC (ADR-004) — маска сокращает число кандидатов, а не заменяет TOC.
- Изменения регистра и маски проходят тот же механизм отложенного подтверждения, что и остальные индексы (ADR-002): решение принимается в памяти до записи, попадает в снимок текущего фблока, подтверждается на диске снимком следующего.

## Обоснование

Вероятностная структура (Bloom) неприменима именно в целевом режиме эксплуатации (постоянная запись всех каналов), а прямое отображение номера на бит платит за теоретический потолок в 65535 каналов, даже когда реально используются десятки. Компактный регистр платит только за реально когда-либо встреченные номера плюс осознанно выбранный запас, и переиспользует позиции без риска перепутать каналы — потому что переиспользование разрешено только когда счётчик ссылок фактически равен нулю, а не по предположению о времени. Все изменения регистра укладываются в уже существующий механизм отложенного подтверждения индексов (ADR-002) без нового протокола отказоустойчивости.

### Почему `registry_used` убрали

`registry_used` дублировался в заголовке каждого фблока (это снимок на момент начала его записи) — для хранилища с `N` фблоков это `2×N` байт только ради того, чтобы отличить «позиция никогда не выделялась» от «позиция выделена номером канала 0» (у номеров каналов нет своего зарезервированного значения). Резервирование 0 закрывает эту неоднозначность на уровне самой нумерации, без отдельного персистентного поля: `channel_registry[i] == 0` теперь само по себе означает «никогда не выделялась». Экономия скромная (для хранилища на 1 млн фблоков — около 2 МБ, см. пример в §6.2 `03-storage-format.md`), но она устраняет отдельное поле и отдельный источник рассинхронизации ради результата, который и так вычисляется тем же проходом по каталогу, что уже нужен для счётчиков ссылок.

Цена — по факту это требование к потребителю: номера каналов должны начинаться с 1. Библиотека не делает скрытый сдвиг «внешний номер → внутренний +1» — резерв 0 закреплён в публичной нумерации (`00-requirements.md` §2), а не спрятан внутри регистра. Если у потребителя номера каналов во внешней системе (например, видеошлюзе) начинаются с 0, обязанность отобразить их в `1..65535` перед передачей в farc лежит на потребителе.
