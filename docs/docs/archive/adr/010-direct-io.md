# ADR-010: Два бэкенда дискового ввода-вывода (O_DIRECT и стандартная библиотека)

**Дата:** 2026-07-21
**Статус:** Принято

## Контекст

Write-verify — ключевая гарантия надёжности: после записи каждого фчанка выполняется его обратное чтение и побитовое сравнение (см. `00-requirements.md` §4.2). При работе через page cache ОС обратное чтение возвращает данные из памяти, а не с носителя — верификация подтверждает лишь то, что данные дошли до кэша, и не обнаруживает физический дефект. Кроме того, «успешная запись» через кэш не означает, что данные легли на пластины.

Обойти page cache на Linux позволяет `O_DIRECT`, но:

- стандартная библиотека Go его не поддерживает — нужен `golang.org/x/sys/unix`;
- все буферы, смещения и размеры операций должны быть выровнены по границе логического блока устройства;
- флаг платформенно-зависим, а требование переносимости (`00-requirements.md` §5.4) предполагает работу и на Windows.

## Сравнение

### 1. Только стандартная библиотека
- ✔ Полная переносимость, один код на все платформы.
- ✔ Простота: `os.File`, никаких требований к выравниванию.
- ❌ Верификация фиктивна: обратное чтение обслуживается из page cache.
- ❌ Двойное копирование данных (пользовательский буфер → кэш → диск).

### 2. Только O_DIRECT
- ✔ Честная верификация: чтение идёт с устройства.
- ✔ Нет загрязнения page cache потоком архива.
- ❌ Работает только на Linux; на Windows аналог (`FILE_FLAG_NO_BUFFERING`) — отдельная реализация со своими правилами.
- ❌ Требования к выравниванию распространяются на весь пул буферов и размеры порций.

### 3. Два бэкенда за общим интерфейсом
- ✔ На целевой платформе (Linux, боевые сервера) — честная верификация через O_DIRECT.
- ✔ На остальных платформах (Windows, разработка, тесты) система работает через стандартную библиотеку.
- ❌ Два пути кода, различия в гарантиях нужно явно документировать.
- ✔ Прецедент уже есть: `04-storage-operations.md` разделяет сканирование при старте на Linux-оптимизированный путь и последовательное чтение через стандартную библиотеку.

## Решение

Два бэкенда за общим интерфейсом (вариант 3). `StorageEngine` работает с диском только через интерфейс `DiskIO`; реализации:

### Бэкенд `direct` (Linux)

- Открытие с `O_DIRECT` через `golang.org/x/sys/unix`.
- Выравнивание: размер логического блока устройства запрашивается при открытии (`ioctl BLKSSZGET` для блочного устройства, `statx` для файла); по умолчанию 4 КиБ. Буферы `WritePool`/`ReadPool` аллоцируются выровненными; размеры фблока, фчанка и порции чтения обязаны быть кратны выравниванию (проверяется при инициализации Storage).
- Долговечность: `O_DIRECT` обходит page cache, но не кэш самого устройства. После записи всех фчанков фблока и перед фиксацией `ready` в индексах выполняется `fdatasync`.

### Бэкенд `standard` (Windows и остальные платформы)

- Стандартная библиотека (`os.File`).
- После записи фчанка — `File.Sync()`, затем обратное чтение и сравнение.
- **Ограничение гарантий фиксируется явно:** обратное чтение может быть обслужено из page cache, поэтому верификация подтверждает целостность передачи данных в ОС, но не состояние носителя. Обнаружение битых фчанков на этом бэкенде опирается на ошибки записи/`Sync`, а не на сравнение.

### Выбор бэкенда

- По умолчанию — по платформе через build tags: Linux → `direct`, остальные → `standard`.
- `standard` — не Windows-специфичный путь, а fallback, доступный конфигурацией на любой платформе, включая Linux: отладка, файловые системы без поддержки O_DIRECT (например, tmpfs), и **сравнение производительности `direct` против `standard` на одном и том же боевом железе**.
- Выбранный бэкенд отражается в метриках и логе старта Storage — обязательно при сравнении производительности, чтобы результат замера был однозначно привязан к бэкенду.

## Обоснование

Верификация записи — причина существования фчанков; без обхода кэша она не выполняет свою функцию, поэтому на боевой платформе O_DIRECT обязателен. Полный отказ от переносимости противоречит требованиям, а честный `FILE_FLAG_NO_BUFFERING`-бэкенд для Windows сейчас не оправдан по трудозатратам — стандартная библиотека с явно задокументированной деградацией гарантий покрывает разработку и вторичные среды. Интерфейс оставляет место для добавления Windows-бэкенда без изменения `StorageEngine`.
