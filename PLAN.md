**Phase 11 notes.**
- **`internal/config`** implements the exact JSON schema from `04-storage-operations.md` §2.1, including its own worked example verbatim as a golden test (`internal/config/config_test.go`). Durations are a `Duration` wrapper type whose `UnmarshalJSON` calls `time.ParseDuration` — enforcing the doc's own explicit requirement ("`"30s"`, `"1h"`... не число секунд") at the type level rather than by convention. `capture_policy.type == "schedule"` and channel id `0` (ADR-014's reserved value) are both rejected at `Load` time with a clear error, not deeper in the process. Depends on stdlib only, per PLAN.md's package table — translating the config's plain strings into `ingest.PolicyType` is `internal/farcd`'s job, one layer up, so this package never needs to import `internal/ingest`.
- **`internal/farcd` never runs Initializer.** The config schema itself only carries `id`/`path`/`catalog_path` per Storage — no geometry, no `write_mode`/`retention.days` (§2.2: those live in the Storage's own on-disk header, set once at init time). This confirms the real lifecycle: an operator initializes a *new* disk once through a running process's `POST /storages` (Phase 10, which also registers it live), and only adds it to this config file afterward, for it to be auto-opened on subsequent restarts. `farcd.New` therefore only ever calls `storage.Open`, never `storage.Init` — consistent with the standing v1 decision that `JobRunner`/`GeometryManager`/`Importer` don't exist in this codebase at all.
- **`StorageUnit → CapturePolicy` backpressure signal** (10-capture-policy.md §8's open question, first resolved on paper during Phase 9/10 planning as "Recorder owns a `map[channelID]*atomic.Bool` updated on transitions") ended up simpler once actually wired: no atomic map or transition-tracking at all. `internal/farcd` hands each channel's `ingest.ChannelConfig` a plain closure, `func() bool { return unit.EngineLevel() == storageengine.LevelBackpressure }`, and `ChannelIngest.SetBackpressureSignal` calls it once per decoded frame (all four codec paths in `internal/ingest/rtsp.go`), skipping `CapturePolicy.HandleFrame` entirely while it's true. `EngineLevel()` (added in Phase 10 for metrics) is already a cheap mutex-guarded read, so caching it in a separate flag would only have added staleness for no benefit.
- **`cmd/arch/config`** (the empty stub `internal/config` was always meant to replace) is deleted outright, not deprecated in place — nothing else referenced it. `cmd/arch` gained a `--config`/`-c` flag (default `farc.config.json`), loads it, builds `farcd.Farcd`, and runs it under `signal.NotifyContext(SIGINT, SIGTERM)` for graceful shutdown; `main.go` dropped its leftover `fmt.Println("hello")` stub line.
- **RTSP timeouts (`ReadTimeout`/`WriteTimeout`) aren't in the documented config schema at all** — §2.1's channel entry has no timeout fields. `internal/farcd` uses a fixed 10s v1 default for both rather than inventing an undocumented config addition.
- **HTTP/WS/metrics genuinely run as three separate `http.Server`s** on their own configured addresses, matching §2.1's "это разные серверы (могут слушать разные порты)" literally rather than combining them onto one mux — Phase 10's `HttpApiServer` already supported both shapes (`push` is optional; `MetricsHandler()` was added this phase to split metrics out too), so this needed no changes to Phase 10 itself, only how `internal/farcd` calls it.
- **Verification:** `internal/config`'s tests cover the doc's own example plus every rejection path (schedule, channel 0, duplicate/unknown storage ids, malformed duration). `internal/ingest` gained a direct test of the backpressure signal (`channelingest_test.go`): frames sent while the signal is true never reach the resulting fcontainer's tree, frames sent after it flips false do. `internal/farcd`'s tests open a real (small) initialized Storage image, build real channel configs from a config value, and run a real `Run(ctx)` against real TCP listeners on ephemeral ports, hitting `/storages` and `/metrics` before cancelling the context and asserting clean shutdown. Beyond the Go test suite, the built `cmd/arch` binary itself was smoke-tested manually end to end: initialize a Storage, start the real binary against a real config file, confirm `/storages` and `/metrics` respond over real HTTP, send it a real `SIGINT`, confirm it exits 0.
- **Deliberately still left out, matching decisions made earlier in this plan, not new gaps found now:** `JobRunner`/`GeometryManager`/`Importer` (v1 scope, `farc-mvp-jobrunner-deferred`), `schedule` CapturePolicy (10-capture-policy.md §5.3), WS reconnect catch-up for compact events (ADR-015's own open question), and a resolve-width limit for `GET .../resolve` (ADR-016's own open question).

**Phase 10 notes.**
- **No spec existed for this package at all** (unlike every earlier phase) — `docs/docs/archive/` never mentions an HTTP/WS API. Implemented close to PLAN.md's own "Minimal HTTP/WS/metrics API" sketch (added during planning), with the open design choices in that sketch resolved as documented in `internal/api/api.go`'s package doc: read endpoints (`GET .../toc`, `GET .../fcontainers/{uuid}`) return raw bytes (`application/octet-stream`), not JSON, matching ADR-004's "consumer parses TOC itself, farcd just returns bytes" model; `GET .../resolve` (ADR-016 fallback) is the one JSON+base64 exception, since its entire purpose is serving a consumer with no parsed TOC to interpret raw offsets against.
- **`GET .../fcontainers/{uuid}` with no `ranges` query returns the fcontainer's whole Content section as physically stored** — which is zero-padded out to its full capacity (Phase 8 gap-fix #1), not trimmed to just the real tree bytes. There's no field anywhere (header, TOC, or otherwise) recording where real data ends and padding begins outside of the TOC's own node offsets — `05-data-format.md` §3's sequential-scan-if-TOC-lost fallback doesn't specify this boundary either, which is a genuine unresolved gap in the docs, not something this phase introduced or needed to solve (the TOC-driven path, `ScanByRole`+`ContentOffset`, is the correct/primary way to fetch a specific node's bytes, and that path is exact).
- **`GET .../resolve` (ADR-016) implemented close to the ADR's literal solution text**, including returning actual frame data (not just offsets) — chosen over the more conservative "just return offsets" alternative because ADR-016 was explicitly "Принято" with that data-returning contract, and the whole point is saving the caller a second round trip. No width limit on `[t1,t2]`; ADR-016 itself leaves that as an open question, not a decided bound, so none was invented here.
- **`toc.Columns` has no `FindChildByRole` equivalent** (that helper is `mediatree.FindChildByRole`, over `[]Element` — the pre-reorder write-time representation, not the post-reorder SoA `Columns` reads use) — added a small local `findChildByRole` in `internal/api/query.go` scoped to the resolve handler rather than exporting a new `toc` package function for a single caller.
- **EventPushServer's channel filter is a `channel_bitmap` "might contain" check**, not an exact per-frame match — no way to filter more precisely below TOC-scan granularity without doing a full resolve on every single push, which would defeat the point of an unsolicited push in the first place. Precise mid-fcontainer filtering is what `GET .../resolve` is for (an explicit pull).
- **New cross-package accessors added, each single-purpose for this phase:** `index.Manager.RetentionDays()`/`ChannelPos()`, `storageengine.Engine.QueueDepth()`, `storage.Unit.EngineLevel()`/`EngineQueueDepth()`/`ContentSize()`, `ingest.IngestManager.TriggerEvent()`. `gorilla/websocket` (already an indirect dependency via gortsplib's own WebSocket-transport support) promoted to direct for `EventPushServer`.
- **Verification:** `internal/api`'s own test suite (`go test ./internal/api/...`) covers every route — storage create/list/patch (real Init+Open through the HTTP handler, not just the registry), TOC/content/protected reads and writes, candidates/resolve against real multi-fcontainer fixtures (including a same-channel-across-two-fcontainers resolve aggregation test), capture-policy/events against a real `IngestManager` (RTSP connection itself fails fast against a closed port, but `CapturePolicy` is created synchronously before that, so it's still fully exercised), the Prometheus metrics text body, and the WS push path end-to-end over a real `httptest.Server` + real `gorilla/websocket` client, including the channel-bitmap filter. One incidental discovery while writing tests, not a Phase 10 bug: fblock 0 (Storage's own bootstrap header, not a real fcontainer) is left with a zero-value UUID by Init and is never given a real one, so once `ConsistencyCheck` promotes it to `Ready` it resolves via `ResolveUUID([16]byte{})` like any other fcontainer would — harmless in practice (real fcontainers get crypto/rand UUIDv4s, never all-zero), but it means an all-zero UUID is the wrong choice for a test fixture meant to represent "doesn't exist."

**Phase 9 notes.**
- **Go version action item closed:** confirmed via a scratch module (`go get github.com/bluenviron/gortsplib/v5@v5.6.2` in an empty module) that gortsplib/v5 v5.6.2's own `go.mod` only requires `go 1.25.0` — the `go 1.26.0` floor is specific to mediamtx's own `go.mod` (likely from one of its many *other* dependencies), not from gortsplib/mediacommon themselves. farc's `go.mod` stays at `go 1.25.3`, `gortsplib/v5`+`mediacommon/v2` added as direct deps via `go mod tidy`.
- **CapturePolicy is one shared state machine, not two strategy implementations.** Re-reading `10-capture-policy.md` §5.1/§5.2 side by side: continuous's `from_time` replay and event's `prerecord`/`event_time` replay are the *same* mechanic (open a segment, replay queued frames ≥ some cutoff), and continuous simply never sets `stop_at` while event does (`stop_at = max(stop_at, t+postrecord)`). Implementing this as one `CapturePolicy` type parameterized by `PolicyType`+`PolicyParams` (`internal/ingest/policy.go`) — rather than two types behind a shared interface — avoided an interface whose methods don't actually line up 1:1 across strategies (continuous's `StartRecording(from_time)`/`StopRecording` vs. event's `Trigger(t)` have different arities), while still letting §6 ("смена политики") swap `PolicyType`/`PolicyParams` in place without touching the queue, cached stream params, or an already-open segment.
- **FrameQueue is one logical per-channel queue, split internally per (stream, kind).** `10-capture-policy.md` §2 describes a single queue with GOP-atomic retention for video. A channel can carry more than one stream (e.g. video+audio); GOP-atomic eviction only makes sense within one video stream's own sequence, so `FrameQueue` (`internal/ingest/queue.go`) keeps a separate time-ordered slice per `(stream, kind)` internally and merges by time on read (`Since`) — invisible to callers, who still see one queue.
- **Frame.Time is derived from wall-clock arrival, not RTSP-provided NTP/PTS** — a deliberate v1 simplification, documented in `internal/ingest/channelingest.go`: many real cameras never send usable RTCP sender reports to synchronize `gortsplib.Client.PacketNTP`, and the docs don't specify how `ChannelIngest` should derive an absolute timestamp at all.
- **Verification:** `CapturePolicy`'s full state table (continuous from_time replay incl. the no-replay case, event prerecord replay + `stop_at` max-extension-never-shrinks + idle-on-timeout via `Tick`, §6 policy-swap preserving an open segment, multi-version config replay) is tested against a fake `Recorder` with no RTSP involved (`internal/ingest/policy_test.go`). The one slower test (`internal/ingest/rtsp_integration_test.go`) runs a real in-process `gortsplib.Server` over loopback serving synthetic H.264 (SPS/PPS carried in-band on the keyframe, as real cameras commonly do) to a real `*gortsplib.Client` via `ChannelIngest.Run`, asserting the resulting Content tree's SPS/PPS bytes and per-frame I/P `frame_kind` sequence match exactly.
- **Scope:** H264 and H265 (video), G711 and AAC/MPEG4Audio (audio) are all wired in `internal/ingest/rtsp.go`, following the same per-codec pattern (SPS/PPS/VPS cached at setup, updated in-band on change, IDR/CRA detection selects `FrameKindI`) — but only H264 has an end-to-end test; H265/G711/AAC are exercised only insofar as the shared `CapturePolicy`/`FrameQueue` code paths are (their format-specific decode/mux glue in `rtsp.go` is untested in isolation). `schedule` CapturePolicy remains out of scope per the docs' own framing (§5.3: "a version after event"), and there's no `PolicyType` value for it at all — not just a runtime rejection. The `StorageUnit ↔ CapturePolicy` backpressure link (§8) is left unresolved, matching the docs' own open question.

**Phase 8 gap resolutions (design work the docs left open, found while implementing).** All three are documented in `internal/storage`'s package doc comment (`internal/storage/storage.go`) with full reasoning; summarized here:

1. **Every fblock write occupies exactly `fblock_size` bytes, content zero-padded.** `03-storage-format.md` §10's own arithmetic (`content_size = fblock_size - 112 - params_size - catalog_size - toc_size`) only holds if TOC/epilog are always at the slot's fixed nominal end and content is padded to fill the gap — otherwise fixed-offset `index × fblock_size` addressing for the *next* fblock wouldn't work. `04-storage-operations.md` §3.1 step 4's "content and TOC size are zero" for Storage-init's fblock 0 is read as "zero real/logical data" (no tree at all, not even an empty `toc.Build` call), not "zero physical bytes" — the two docs are only consistent under this reading. `assembleFblock` (`internal/storage/assemble.go`) implements this.
2. **A fcontainer's identity must be recoverable after a crash.** `04-storage-operations.md` §7.2 only says the fblock-being-written's own catalog entry gets `channel_bitmap` bits set early (before the write completes) — it's silent on UUID/begin/end, which `IndexManager` otherwise only learns at `CompleteWrite`, i.e. *after* a successful write. A crash between a successful epilogue and the next fblock's write would make that data unrecoverable (UUID lives nowhere but the catalog, per ADR-001's self-containment requirement). Fix: Recorder patches a local `index.Manager.Snapshot()` copy with the real UUID/begin/end before encoding the header, generalizing the one exception the docs already grant to `channel_bitmap[N]`. Required adding `Manager.Snapshot()` (deep copy) and `Manager.SetChannelBit` (so the *live* in-memory catalog — not just Recorder's disk-bound copy — also reflects the bits Reader.Candidates depends on; caught by `TestWriteFcontainer_RoundTrip`'s `Candidates` assertion failing before the fix) to `internal/index`.
3. **The SSD catalog must mirror in-flight writes, not just completed ones.** ADR-007 only calls for updating the SSD mirror "after each successful write" — under that rule alone, a crash between the main disk's epilogue succeeding and Recorder's completion step would leave the SSD mirror not even knowing a write was in flight, so `ConsistencyCheck` (run uniformly "after loading indices via any path") would silently miss a fully-written fblock via the SSD-catalog path — a real data-loss bug, since path 2's header scan doesn't have this blind spot (it reads the main disk's own self-referential `in_progress` marker directly). Fix: Recorder saves the SSD catalog twice per fcontainer — right after `BeginWrite` (state `in_progress`, patched identity already known) and again after `CompleteWrite` (state `ready`).

Also note: the SSD catalog's own binary layout is never actually pinned by `03-storage-format.md` (ADR-007 just says "an array of headers... or an equivalent SoA structure" and defers to that doc, which doesn't define one) — `internal/storage/ssdcatalog.go` is this project's own format for it: `fblock.EncodeCatalog`'s payload verbatim, wrapped in a small envelope (magic + write_sequence + catalog_time + cursor + crc32). The `cursor` field is a second necessary gap-fill: `04-storage-operations.md` §6.1 recovers cursor from "the fblock with max `write_sequence`", but `write_sequence` is a per-fblock fixed-prolog field never stored in the catalog SoA itself — a catalog loaded from the SSD mirror alone has nothing to compare, so the envelope just carries the physical index directly instead.

**Phase 7 design note.** `storageengine.Engine` exposes a deterministic `Step()` (one fchunk write-verify or one read portion per call, chosen per ADR-005/ADR-011) instead of an opaque background loop, specifically so tests can drive it synchronously and assert exact M/K interleaving order without timing dependence; `Run(ctx)` is a thin convenience wrapper looping `Step()` on its own goroutine for production use, added even though no caller wires it up yet (Phase 8's Recorder will be the first). `EnqueueWrite`/`EnqueueRead` return tickets (`Wait()` blocks on a channel) rather than blocking the caller directly, so producer goroutines (Recorder, multiple Readers) and the single `Step()`-driving goroutine stay decoupled. Retry-on-a-new-index after a corrupted write-verify is explicitly **not** this package's job (`WriteResult.Corrupted` + `FailedOffset` is all it reports) — picking a new physical index belongs to Recorder/`IndexManager` in Phase 8, matching the dependency direction (`storageengine` depends only on `ioengine`, not `index`).

**Bug found during verification:** the M/K quota (ADR-011) must go fully dormant under BACKPRESSURE, not just get zeroed at the moment a `Step()` call observes it — an earlier version reset `quotaRemaining` to 0 only at the top of `Step()`, but `stepWriteLocked` unconditionally re-granted a fresh quota window after every `QuotaEvery`-th chunk regardless of level, so a grant earned while still under backpressure survived into the very next `Step()` call and fired a read one step early the instant the queue dropped back below the backpressure threshold. Fixed by also gating the grant logic itself on `level != LevelBackpressure` (both the reset and the accrual live under the same condition now) — caught by `TestQuota_DisabledUnderBackpressure`, which drains a saturated write queue down through the backpressure threshold and asserts every single step in that transition is a write.

## Context

`farc`'s design docs (`docs/docs/archive/*.md`, 17 ADRs) are complete and detailed, but the code is still just a `cmd/arch` cobra stub — `internal/` is empty (a prior prototype package, `traa`, was deleted). Over a long design-review session we closed every open scoping question blocking a v1 plan: removed a stray DDD aside, fixed a real drift between `01-architecture.md` and `11-service-composition.md` (Initializer now goes through Archive, not a standalone CLI), fixed a naming drift on `write_mode` across three docs, accepted ADR-011 as-is and ADR-012 in a simplified v1-only form (plain `now()`, no anomaly protection), decided v1 scope (RTSP ingest, SSD Catalog, and EventPushServer are IN; `GeometryManager`/`Importer` — and therefore any `JobRunner` orchestrator component — are OUT), and finalized the external JSON config schema (`04-storage-operations.md` §2.1). `TODO.md` tracks all of this as closed.

This plan turns that settled design into a concrete, phased Go build order. While exploring, three Explore agents extracted full byte-level format/algorithm detail from the remaining unread docs (`05-data-format.md`, `06-toc-format.md`, `07-media-tree.md`, `08-array-trees.md`, `09-fcontainer-write-path.md`, `00-requirements.md`, and 13 ADRs), and a repo scan surfaced an important asset: a gitignored `temp/mediamtx-1.19.3` reference copy of the mediamtx RTSP server, which depends on `github.com/bluenviron/gortsplib/v5` and `github.com/bluenviron/mediacommon/v2` — mature, MIT-licensed, actively-maintained libraries that do exactly the RTSP/RTP/SDP/codec-parameter work `ChannelIngest` needs. **Recommendation: use them as real dependencies instead of writing an RTSP/RTP client from scratch.** One caveat found during verification: mediamtx's own `go.mod` requires `go 1.26.0`; check whether `gortsplib/v5` itself forces that floor before bumping farc's `go 1.25.3` directive (Phase 9 action item, not a blocker).

A Plan sub-agent (fed the full distilled spec) proposed the package layout and build order below; I verified its two load-bearing claims directly against the docs and the mediamtx source before accepting them: the exact catalog-entry formula (`33 + ceil(C/8)` bytes/entry — confirmed against `03-storage-format.md` §6.2, byte-for-byte) and the `gortsplib.Client` usage shape (confirmed against `temp/mediamtx-1.19.3/internal/staticsources/rtsp/source.go`).

## Package layout

Two kinds of packages: **root-level** (`farc/...`) for pure format/algorithm libraries an external process (Video Gateway, a future recovery CLI per `01-architecture.md` §4) might need to import verbatim; **`internal/...`** for everything farcd-process-specific.

| Package | Depends on | Responsibility |
|---|---|---|
| `farc/fblock` | stdlib | fblock binary format: 56-byte fixed prologue, JSON params, catalog SoA (channel registry + per-fblock `flags/uuid/begin/end/channel_bitmap` arrays, exact formula from `03-storage-format.md` §6.2), 3×CRC32, epilogue, geometry math (`min_container_share` check, ADR-013). Pure `[]byte` encode/decode, no I/O. |
| `farc/mediatree` | stdlib | `role`/`type` const blocks (`07-media-tree.md` §3.1, append-only, never renumber), Content-node (AoS) encode/decode, sequential-scan validator (port of `08-array-trees.md` §13 checklist — doubles as corruption detection). |
| `farc/toc` | `farc/mediatree` | TOC binary format (64-byte-aligned SoA columns, `06-toc-format.md` §3-4), `Build()` (the DFS reorder algorithm — depth, subtree-size, DFS `pos` via prefix sum, permute+translate `parent`/`sibling`, §5), `Decode()`, and role-agnostic query primitives (`SubtreeRange`, `IsAncestor`, `ScanByRole`, `TimeRange`, `CoveringSubtreeRoot`/LCA-of-set) shared by both the ADR-004 client path and the ADR-016 farcd-side fallback. |
| `internal/fcontainer` | `farc/mediatree` | The **Filler**: `AddStreamParams`/`AddFrames` (`09-fcontainer-write-path.md`'s entire public contract) plus the concurrent id/offset/`lastchild` allocator (gap resolution, see below). |
| `internal/index` | `farc/fblock` | **IndexManager**: in-memory catalog + cursor, `select_next_index` (`04-storage-operations.md` §6.2, cyclic/fill_until_full), channel registration/reuse, UUID/candidate lookup, protected/retention mutation. |
| `internal/ioengine` | `golang.org/x/sys/unix` (linux) | `IoBackend` interface; `direct` (O_DIRECT, alignment probe, outward-rounding reads) and `standard` (portable, degraded verify guarantee) backends, chosen by GOOS or config override (ADR-010). |
| `internal/storageengine` | `internal/ioengine` | **StorageEngine**: fchunk write-verify loop, read/write arbitration (ADR-005 priority, ADR-011 M=16/K=4 quota, disabled under BACKPRESSURE). No fblock-structure knowledge — offsets/lengths only. |
| `internal/storage` | `farc/fblock`, `farc/toc`, `farc/mediatree`, `internal/fcontainer`, `internal/index`, `internal/storageengine` | **StorageUnit**: Recorder, Reader, NotificationBus, HealthMonitor, SSD Catalog — plus Initializer, the 3-path Startup, and ConsistencyCheck **inlined here as methods, no `JobRunner` package** (matches the v1 scope decision). |
| `internal/ingest` | `gortsplib/v5`, `mediacommon/v2`, `internal/fcontainer`, `farc/mediatree` | IngestManager, ChannelIngest, CapturePolicy (`continuous`, `event`; `schedule` rejected with a clear error, not silently stubbed — see below). |
| `internal/api` | `internal/storage`, `internal/ingest` | StorageRegistry, HttpApiServer, EventPushServer (WS), MetricsEndpoint — minimal new route set (below); no spec exists for this anywhere in the docs. |
| `internal/config` | stdlib | JSON config schema exactly per `04-storage-operations.md` §2.1 (`time.ParseDuration` for capture-policy fields); replaces the current empty `cmd/arch/config` stub. |
| `internal/farcd` | everything above | Process wiring: load config → open/init each Storage → build IngestManager per channel → wire the backpressure status link (below) → start the three servers → graceful shutdown. |

Dependency direction is a strict DAG; `internal/storage` is the only thing that touches disk; `internal/ingest` never touches `internal/storage` directly except through the Filler and the backpressure flag.

## Build order and verification

2. **`farc/mediatree` format half** (enum + node encode/decode + validator). Verify: hand-encode the 13-node tree from `08-array-trees.md` §2, decode, `Validate()` passes; flip one byte to break `parent[i]<=i`, assert it's caught.
3. **`farc/toc`.** Verify: golden test — feed Phase 2's tree into `Build`, assert `new2old`/`old2new`/`parent'`/`sibling'` match the docs' own worked tables (`08-array-trees.md` §8.3, `06-toc-format.md` §8) exactly; column padding offsets match the stated formula; `SubtreeRange`/`IsAncestor`/LCA-of-set checked against the docs' own worked answers.
4. **`internal/fcontainer` (Filler)** — implements the concurrency gap resolution below. Verify: N-goroutine torture test calling `AddStreamParams`/`AddFrames` concurrently across many (channel,stream) pairs, then run Phase 2's validator over the frozen result, under `-race`; a second test exercises the literal `09-fcontainer-write-path.md` contract (returned `configID` reuse, frame order preserved).
5. **`internal/index`.** Verify: table-driven tests transcribing the §6.2 pseudocode cases (wraparound, cyclic vs fill_until_full, `NO_SPACE`) and the §7.1.1 channel-registry reuse/exhaustion cases.

## Gap resolutions (design work the docs explicitly left open)

- **Channel-registry reuse race within one buffer (found while implementing Phase 5, not in the original plan).** `04-storage-operations.md` §7.1.1's reuse rule ("reuse a position whose reference count is 0") reads bit references from the *committed* catalog — but a position registered for a brand-new channel earlier in the very same buffer's channel list has no committed bit yet either (the bit is set later, in §7.2 step 3), so a naive per-channel implementation of the rule would let a later channel in the same list immediately steal an earlier one's just-issued position. Fixed by resolving a buffer's whole channel list in one call (`Manager.RegisterChannels`), excluding this-batch allocations from the reuse search; cross-buffer calls remain safe as-is because Recorder is single-writer and commits each write's bits before the next buffer is processed.

- **Filler concurrency** (the load-bearing gap — `05-data-format.md` §6 and `09-fcontainer-write-path.md` §5 both explicitly disclaim specifying this). Since Content `id` is pure sequence position with no gaps, reserving a node's id, its exclusive byte range in the buffer, and updating `lastchild[parent]` (for `sibling`) must happen as **one atomic transaction** — a single `sync.Mutex`-guarded `reserve(parent, valueLen) (id, sibling, offset)` critical section; the actual header+value byte copy happens lock-free afterward into the caller's exclusively-owned range. Rejected alternatives: per-parent atomics alone (doesn't solve the joint id/offset/lastchild coupling) and a single-writer funnel goroutine (adds latency for no benefit — the critical section is already O(1)).
- **ADR-017 `ready_bytes` plumbing**: Filler exposes a cheap `Len()`; Recorder polls it on a ticker (period ≤ `T`), computes `writable = floor(len/alignment)*alignment` minus already-flushed, pushes the delta to StorageEngine. Filler never initiates anything, matching "push-notified by Recorder, Filler uninvolved" literally.
- **`CapturePolicy.schedule`**: deferred explicitly, not silently stubbed. `10-capture-policy.md` §5.3 itself calls it "a version after event," and the finalized config schema's worked examples only cover `continuous`/`event`. `internal/config` rejects `capture_policy.type == "schedule"` with a clear "not implemented in v1" error at load time.
- **`StorageUnit → CapturePolicy` backpressure signal** (open question in `10-capture-policy.md` §8): extend the existing get-buffer/return-buffer exchange rather than invent a new component — Recorder owns a `map[channelID]*atomic.Bool` ("skip frames"), updated on NORMAL/WARNING/BACKPRESSURE transitions; `internal/farcd` wiring hands each `ChannelIngest` a read-only reference to its own channel's flag, checked once per frame.

## Minimal HTTP/WS/metrics API (new design — no spec exists in the docs for this at all)

- `POST /storages` (runs Initializer inline, registers in StorageRegistry) · `GET /storages`
- `GET /storages/{id}/fcontainers/{uuid}/toc` · `GET /storages/{id}/fcontainers/{uuid}?ranges=off:len,...` · `GET /storages/{id}/fcontainers/{uuid}` (whole export, ADR-003)
- `GET /storages/{id}/candidates?channel=&t1=&t2=` (ADR-014) · `GET /storages/{id}/resolve?channel=&t1=&t2=` (ADR-016 fallback, via the shared `farc/toc` query layer)
- `POST .../protected {value}` · `PATCH /storages/{id} {retention_days}`
- `POST /channels/{id}/capture-policy {type,params}` (`schedule` → `501`) · `POST /channels/{id}/events {t}` (plain one-shot POST, sidesteps the long-idle-timeout concern from `10-capture-policy.md` §8 since v1 isn't a long-poll shape)
- `GET /metrics` (Prometheus exposition, `02-storage.md` §8's metric table)
- WS: one subscribe message on connect (`{storage, want, channels}`); server pushes typed JSON frames for compact events and per-channel TOC. No reconnect catch-up for compact events in v1 (consciously deferred); TOC catch-up uses `/resolve`.
